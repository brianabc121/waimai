## 0. v0.2 改了什么（按堂食模式的实际实现）

堂食模式 PR #105 已经合并。和加单有关的实际做法，以及本方案跟着改的地方：

| 堂食实际做了什么 | 加单方案怎么跟 |
|---|---|

## 1. 要解决什么

brian 的原话：堂食在结账前、外卖在交接给骑手前，都可以进行加单操作。

- **堂食加菜**：PR #105（代客下单堂食模式）已经做好了：开台后每次点菜是一“轮”，送厨后随时可以再加一轮，结账前都能加。本方案不再重复，只把它和外卖的加单**做成同一套概念和显示**（第 8 节）。
- **外卖、自取加单**：现在完全没有。顾客打电话或在微信里说“再加一杯奶茶”，店员只能另下一单，结果是两张单、两个骑手（或一个骑手拿两单）、两次收钱、满减也没法合在一起算。这是本方案的重点。

## 2. 业内怎么做

| 产品 | 外卖/线上单下单后能不能加 | 做法 |
|---|---|---|
| DoorDash | 顾客不能直接改餐厅单 | 餐厅还没处理时，顾客找客服改。另有 DoubleDash：下单后十几分钟内可以从附近**另一家店**加东西，同一个骑手送，**不另收配送费**（服务费照收）。商家接口有“订单调整”：已接的单可以换菜、改数量 |
| Uber Eats | 餐厅单：商家接单后，顾客要直接打电话给商家 | 生鲜单有“Active Order Adjustments”：下单后到骑手在店里结账前，顾客都能自己加减商品 |
| GrabFood / ShopeeFood | 只有部分场景 | Grab 的骑手在非合作店代买时可以改单，顾客收到通知；ShopeeFood 商家端有“编辑订单”，只对部分商家、只对外卖单开放 |
| 美团 / 饿了么 | 顾客端没有“加菜” | 通常是另下一单，或者备注、联系商家；平台侧的“多店一起送”是下单前的事 |
| Toast | 线上单曾有“Update”按钮，改了会送到后厨；后来对自家线上单关掉了，建议作废重下，或者另开一张单加菜 | 堂食是“开着的账单”：随时加菜按 Send 送厨，送过的菜不能改，只能作废（void）或赠送（comp） |
| Square for Restaurants | 送厨后可以加新菜；已送的菜不能改规格、不能改备注，只能作废 | “Send & Stay”边点边送；“Open Checks”让账单一直开着 |

可以看出两条路：

1. **外卖平台**（DoorDash、Uber、美团）基本不让顾客改餐厅单，原因是他们是第三方：平台、商家、骑手三方都要同步，退款和线上支付也复杂。能改的都是**有明确截止点**的（Uber 生鲜：骑手结账前；DoorDash DoubleDash：下单后十几分钟）。
2. **餐厅自己的收银系统**（Toast、Square、美团收银）把一张单看成“开着的账单”：**送过的不动，只能往上加新的一批**，新的一批单独送厨。

我们是商家自己的系统、自己的骑手、目前全部货到付款，条件比外卖平台好得多，可以走第二条路，再借第一条路的截止点和“同一个骑手、不另收配送费”：

- **加单 = 同一张订单里新加一轮（批次）**，和堂食的“第 2 轮”是同一个东西。原单不动，送过厨的菜不能改。
- **截止点就是骑手取餐**（自取是顾客取走，堂食是结账）。系统里有明确的状态，不靠估计时间。
- **不另收配送费**，同一个骑手一起送，到门口收一次钱。
- **顾客自己加的，要商家确认**（像新订单要接单一样）；店员加的直接生效。

不照搬的：

- DoorDash 那种“下单后 N 分钟内才能加”的时间窗：我们用订单状态做截止，更准确，商家出餐慢的时候顾客也能加。
- 从别的店加（DoubleDash、美团多店一起送）：是另一件事，牵涉两家店的骑手和结算，不在这次范围。
- 改原单的菜（换规格、减数量）：送厨后不改，和 Toast、Square 一样。外卖要减菜见第 11 节问题 8。

## 3. 现在系统里已经有什么

| 已有 | 和加单的关系 |
|---|---|
| `order_batches`（批次） | 外卖单下单时已经建了第 1 批（`seq = 1`），堂食每轮一批。**加单直接加第 2、3 批**，不用新表。`placed_by`、`round_tags` 已经有了（PR #105） |
| `orders.manifest_version` | 订单内容一变就加 1，打包时要带上这个号，对不上就提示“订单变了，再核对一次”（`MANIFEST_CHANGED`）。加单正好用上，防止打包员漏装 |
| 打包、交接状态 | `packing_status`：等菜 → 可打包 → 已打包；`fulfillment_status`：已打包后是“等骑手”，交给骑手后是“配送中”。**截止点就是“配送中”** |
| 报价 `priceLines` / `ComputeTotals` | 按当前菜单重新计价、算税和服务费，加单直接复用 |
| 活动和券 `order_discounts` | 下单时锁定的活动和券，每项一行。加单时重算活动，券保留（第 5 节） |
| 货到付款 `cash_collections` | 骑手送达时按订单总额记“应收”。加单只要改订单总额，骑手到门口收新总额 |
| 堂食加菜 `AddBatch` | 幂等键、价格变了拒绝、按工位派单、整轮要求、点菜店员。外卖加单复用同一段逻辑 |
| 堂食账单的轮次抬头（`DineBill`）、顾客桌台页的分批显示（`BillLines.vue`） | 外卖订单详情按批次分段用同一种样子 |
| 后厨屏的“· 第 N 轮”、整轮要求、催菜标签（PR #105） | 外卖加单在后厨照这样显示 |
| 代客下单页 | 店员加单就用这个页面的“加单模式”（第 6 节） |

## 4. 什么时候能加（截止点）

| 订单类型 | 店员能加到 | 顾客自己能加到 | 说明 |
|---|---|---|---|
| 外卖 | 交给骑手之前（状态变“配送中”之前） | 同左 | 已打包的也能加，加了以后要重新打包（第 7.2 节） |
| 自取 | 顾客取走之前 | 同左 | |
| 堂食 | 结账关台之前 | 扫码顾客照旧能加（PR #5） | 见 PR #105 |
| 预约单 | 同外卖 / 自取 | 同左 | 预约单离送达还早，最适合加 |
| 待接单（商家还没接） | 能加 | 能加，直接并进原单 | 商家接单时看到的是合并后的整单，不用另外确认 |
| 已拒单、已取消、配送失败 | 不能 | 不能 | |

- 截止由后端判断：加单和交接都锁住同一张订单，所以“骑手刚好在这一秒取餐”时只会有一个成功。加单晚了一步，顾客看到“骑手已经取餐了，这次加的菜要另下一单”，并有“另下一单”按钮（把刚选的菜带过去）。
- 顾客端“加菜”按钮只在还能加的时候显示，并写明“骑手取餐前都能加”。
- 一张单顾客自己最多加 3 次（第 11 节问题 5），店员不限。

## 5. 钱怎么算

原则：**加单后整张单重新算一次，但顾客已经享受到的优惠只多不少；配送费不另收。**

| 项目 | 规则 |
|---|---|
| 菜品 | 新加的菜按**现在**的菜单价算；原单的菜保持下单时的价格 |
| 配送费 | 不变，不另收（同一个骑手一起送）。起送金额不再判断 |
| 包装费 | 不变（现在是按单收的固定金额） |
| 门店活动（满减等） | 按“原单 + 加单”的菜品原价重新选最省的活动。**只升不降**：如果新算出来比原来少（例如活动刚好过了时段），保留原来的 |
| 原单用的券 | 保留，不退不换。券的门槛按原价算，加单只会让金额变大，门槛仍然满足 |
| 加单时新用券 | 不能（第 11 节问题 4）。结算页写“这次加菜不能再用券” |
| 服务费、税 | 按重算后的菜品金额算，和现在一样 |
| 平台券 | 原单用的保留，金额不变 |
| 复购礼券（送券） | 按订单完成时的最终金额判断，加单后够门槛了也能送 |

例子（效果图 05）：原单菜品 ₱360，活动“满 ₱300 减 ₱30”，配送费 ₱49，原来应付 ₱379。顾客加一杯奶茶 ₱85 + 一份炸鸡 ₱120，菜品变成 ₱565，够上“满 ₱500 减 ₱60”：

| | 原单 | 加单后 |
|---|---|---|
| 菜品 | ₱360 | ₱565 |
| 满减 | −₱30 | −₱60（升档） |
| 配送费 | ₱49 | ₱49（不另收） |
| **应付** | **₱379** | **₱554** |
| 这次加菜要多付 | | **₱175**（菜 ₱205，满减多减 ₱30） |

### 5.1 付款

- **现在全是货到付款 / 到店付**：加单只改订单总额。骑手 App 和打包单上显示新的应收金额，并标“加单后金额已变 ₱379 → ₱554”，送达时按新总额收钱，核款也按新总额。
- **代客下单记了“已收款”的单**（代客下单方案里有，还没做）：以后做的时候，订单记“已收多少”，加单的差价自动变成“还要收 ₱175”，骑手只收差价。
- **以后做线上支付时**：加单单独付差价，付完才送厨；顾客取消这次加单不影响原单。这次不做，只在数据上留“这一批付了没有”的位置（第 9 节）。

## 6. 店员怎么加单（效果图 01、02、03）

### 6.1 入口

- **订单详情页**（`/merchant/orders/:id`）右边“操作”里加一个 **“＋加单”** 按钮，旁边一行小字说明还能加到什么时候：“骑手取餐前都能加”“已打包，加单后要重新打包”。截止后按钮消失，换成灰字“骑手已取餐，不能再加单”。
- **订单列表卡片**上也有“＋加单”，方便接电话时直接找。
- **代客下单页**下单成功的弹窗里加一个“＋给这单加菜”（顾客刚下完又想起来的情况最多）。
- **堂食**：代客下单页 → 堂食 → 桌台图右边栏的“＋加菜”（PR #105），不变。

### 6.2 代客下单页的“加单模式”

点“＋加单”打开 `/merchant/orders/new?append=<订单号>`，就是代客下单页，但是：

- 顶栏写“给 #A1086 加单”，带订单状态（“制作中”“已打包 · 已派骑手 王师傅”）。不显示“外卖 / 自取 | 堂食”切换。
- 左边表格上半部分是**原单**，灰底，锁着不能改，写“原单 · 12:41 · 顾客下单”；有过加单的再列“加单 1 · 12:55 · 店员 小林”。
- 下半部分是**这次加的菜**，用法和代客下单完全一样：右边“选择商品”输编号或菜名回车加入，规格、加料、口味模板（PR #102）都照旧。
- 右边的会员、电话、地址、配送费都**只读**（加单不改地址、不改配送费）。下面是**整轮要求**（点选，和堂食同一份预设：加急、分开装、先做饮料…，后厨看得到，存在 `round_tags`）和“店内备注”。
- 深色底栏换成**前后对比**：“原来 ₱379 → 加单后 ₱554，多收 ₱175”，满减升档时写“满减升档：满 ₱500 减 ₱60”。
- 按钮：**“确认加单 · +₱175”**。
- 和代客下单一样，价格或库存在这期间变了就提示新金额再确认。

### 6.3 加单之后（效果图 03）

- 弹窗：“已加单”，自动复制一段给顾客的消息（可改话术）：

  ```
  陈小姐，已为您在订单 #A1086 加了：
  C3 珍珠奶茶 ×1（少糖 去冰）₱85
  B7 盐酥鸡 ×1 ₱120
  满减升档：满₱500减₱60
  订单合计改为 ₱554（原 ₱379），和原来的菜一起送，不另收配送费。
  查看进度：https://…/o/xxxx
  ```

- 可以打**补单小票**：大字“加单 1”和原订单号、顾客称呼，只列这次的菜（第 7.1 节）。
- 骑手（如果已派单）收到推送（第 7.3 节）。
- 顾客收到站内消息（和订单状态通知同一个通道），订单详情页能看到加单的菜和新金额。

### 6.4 权限

- 外卖、自取加单：沿用代客下单的 `order.manual`。没有这个权限的员工看不到“＋加单”。
- 处理顾客发来的加单（确认 / 拒绝）：沿用接单的 `order.handle`。
- 堂食加菜：沿用 `table.use`（PR #105）。
- 不新增权限项，也不弹经理授权码（和堂食退菜一样）。加单只会让顾客多付钱，风险比退菜小。

## 7. 后厨、打包、骑手（效果图 06）

### 7.1 后厨

- 加单是一个新批次，按菜品工位派到后厨屏，**和原单在同一张订单卡里**。和堂食现在的样子一样：菜名后面写“· 加单 1”（堂食写“· 第 N 轮”），整轮要求在菜下面写“※ 加急”。订单卡标题旁多一个橙色“加单”标签，加单后 3 分钟内卡片描橙边，提醒厨师这是后补的。
- 补单小票：小票页加 `?batch=2`，只打这一批的菜，抬头大字“加单 1”（堂食是“第 2 轮”），写原单号和“和原单一起出”。代客下单的加单弹窗、订单详情、堂食账单都能点“打印这一批”。
- 原单已经全部做好、在等打包时，后厨屏把这张单重新顶到“制作中”，打包员那边显示“等加单的菜”。

### 7.2 打包

- 加单后 `manifest_version` 加 1，订单回到“等菜”（`packing_status = waiting_items`）。
- 已经打包好（甚至已经封袋）的单：状态回到“等菜”，打包单上写“**已打包 2 袋，加单后要再装 2 份**”，打包员确认袋数后重新点“打包完成”。
- 打包员如果拿着旧清单点“打包完成”，后端因为 `manifest_version` 对不上会拒绝（现有规则），提示“订单加了菜，再核对一次”。

### 7.3 骑手

- 还没派骑手：不用通知。
- 已派骑手（还没取餐）：推送“#A1086 加了 2 份菜，等后厨出餐，收款改为 ₱554”。骑手 App 的这张单标“加单”，应收金额旁边写“原 ₱379”。
- 骑手已取餐：不能再加（截止点），不会出现骑手手上的餐和单子对不上。
- 预计送达时间：按加单的菜的出餐时间顺延，顾客端显示新的预计时间。

## 8. 顾客怎么加菜（效果图 04、05）

### 8.1 入口

- **订单详情页**（`/o/:token`）状态卡下面一个按钮“＋ 加菜 · 骑手取餐前都能加，不另收配送费”。
- 点了进入这家店的点餐页，顶上一条金色横幅：“正在给订单 #A1086 加菜 · 和原来的菜一起送”，右边“退出加菜”。购物车是独立的（不影响顾客原来的购物车）。
- 点餐页、规格、口味和平时一样；只显示能外卖（或能自取）的菜。

### 8.2 加菜结算

- 结算页简化：不显示地址、配送时间、付款方式选择（都沿用原单，只显示一行“送到：…”）。
- 列出“原单 3 份 ₱360（已下单）”和“这次加 2 份 ₱205”，下面是重算后的费用，满减升档用金色高亮，配送费写“已付，不另收”。
- 底部：“确认加菜 · 多付 ₱175”。
- 提交后回到订单详情，这次加的菜显示“等商家确认”（橙色），商家确认后变成“已确认 · 制作中”。

### 8.3 商家确认

- 顾客加的菜像新订单一样**要商家确认**：订单台响铃，订单卡上写“顾客加菜 2 份 +₱175 · 等确认”，按钮“确认加菜”“拒绝”。
- 商家 5 分钟内不处理，自动拒绝这次加菜（原单不受影响），顾客收到“商家没有确认，这次加的菜没有生效”。
- 拒绝要选原因（菜卖完了、来不及做、骑手已出发…），顾客看得到。
- 确认前骑手取了餐：这次加菜自动失效，顾客收到提示。
- 待接单的订单：顾客加的菜直接并进原单，商家接单时一起看，不用单独确认。

## 9. 改动清单

### 9.1 数据库（一个迁移）

| 表 | 新字段 | 说明 |
|---|---|---|
| `order_batches` | `status TEXT NOT NULL DEFAULT 'accepted'` | `pending`（顾客加的，等确认）、`accepted`、`rejected`、`expired`、`cancelled`。老数据都是 `accepted` |
| `order_batches` | `total_before BIGINT`、`total_after BIGINT` | 加单前后的订单总额（消息、账单、对账用） |
| `order_batches` | `decided_by`、`decided_at`、`reject_reason`、`expires_at` | 商家确认或拒绝顾客加菜 |
| `order_batches` | `paid BOOLEAN NOT NULL DEFAULT false` | 预留给线上支付（这一批付了没有），这次只写不读 |

- 谁加的、整轮要求直接用 PR #105 已有的 `placed_by`、`round_tags`；来源用已有的 `source`（`staff` / `customer`），不再新加。
- 不新增订单状态。“这张单有没有等确认的加菜”从批次查。
- 后厨、打包、小票、账单、统计只算 `status = 'accepted'` 的批次里的菜。

### 9.2 后端

- 从堂食的 `AddBatch`（PR #105 已经带整轮要求和点菜店员）里抽出公共的 `appendBatch`：锁订单 → 判断截止 → `priceLines` 报价 → 写批次（`round_tags`、`placed_by`）和菜 → 占库存 → 重算金额 → `manifest_version + 1` → 派工位 → 推送。堂食加菜和外卖加单都用它（堂食不重算活动，因为堂食不参加优惠）。
- 外卖重算金额：新函数 `recomputeDelivery`，按第 5 节：活动只升不降、原券保留、配送费和包装费不变；`order_discounts` 里活动那一行更新金额。
- 已打包的单加单：`packing_status` 回到 `waiting_items`，`fulfillment_status` 回到 `none`，保留原来的袋数供参考。
- 截止判断：外卖 `fulfillment_status IN ('none','awaiting_handoff')`，自取 `('none','awaiting_pickup')`，且 `acceptance_status IN ('pending','accepted')`。
- 接口：
  - 店员：`POST /merchant/orders/{id}/append/quote`（试算）、`POST /merchant/orders/{id}/append`（带幂等键）。
  - 确认顾客加菜：`POST /merchant/orders/{id}/batches/{seq}/accept`、`/reject`（带原因）。
  - 顾客：`POST /api/orders/{token}/append/quote`、`POST /api/orders/{token}/append`、`DELETE /api/orders/{token}/append/{batchId}`（确认前撤回）。
  - 订单详情（店员和顾客）返回按批次分组的菜，和每批的状态、前后金额。
- 定时任务：每分钟把过期没确认的顾客加菜改成 `expired`，释放库存，通知顾客（和现在的接单超时同一个 Worker）。
- 骑手推送：新事件 `appended`，带新应收金额。
- 交接时如果还有 `pending` 的顾客加菜：自动改成 `expired`（骑手已经走了）。

### 9.3 页面

- 商家订单详情（`OrdersView.vue` 里的详情）：“＋加单”按钮和截止说明；菜品按批次分段，抬头和堂食账单一样；顾客加菜的“确认 / 拒绝”。分段抬头做成一个小组件，堂食账单 `DineBill`、顾客桌台页 `BillLines.vue`、外卖订单详情共用。
- 订单台卡片：“＋加单”；“顾客加菜 · 等确认”标记和响铃。
- 代客下单页 `ManualOrderView.vue`：`?append=` 加单模式（原单锁定、右栏只读、前后对比底栏、确认加单、加单消息话术）。
- 后厨屏 `KitchenView.vue`：现在只给堂食写“· 第 N 轮”，改成外卖第 2 批起写“· 加单 N”；卡片“加单”标签和橙边。
- 小票 `TicketView.vue`：`?batch=` 只打一批（堂食也能用）。
- 打包：批次分段、“要再装几份”。
- 骑手端（网页和 App）：“加单”标记、应收金额变化。
- 顾客订单详情 `OrderView.vue`：“加菜”按钮、批次分段、“等商家确认”。
- 点餐页 `StoreView.vue` 和结算页 `CheckoutView.vue`：加菜模式（横幅、独立购物车、简化结算）。
- 多语言：新文字进 12 种语言的语言包。

### 9.4 测试

- Go：截止判断（配送中、已取走、已取消都拒绝）；加单和交接并发只成功一个；活动只升不降；原券保留；配送费不变；已打包回到等菜、旧 `manifest_version` 打包被拒；顾客加菜确认、拒绝、超时、交接时自动失效；库存释放；幂等键重复提交只加一次。

堂食加菜（PR #105）和外卖加单在这些地方用同一套：

| | 堂食 | 外卖 / 自取 | 统一做法 |
|---|---|---|---|
| 叫法 | 第 1 轮、第 2 轮 | 原单、加单 1、加单 2 | 数据都是批次。外卖订单的按钮叫“＋加单”，堂食桌台里叫“＋加菜”（PR #105 已上线，不改），顾客端都叫“加菜” |
| 显示 | 账单按轮次分段：“第 1 轮 11:33 · 店员 小陈 · 先上饮料” | “原单 12:41 · 顾客下单”“加单 1 12:55 · 店员 小林 · 加急” | 同一个抬头组件：第几批、时间、谁加的、整轮要求 |
| 后厨 | 菜后写“· 第 N 轮”，下面“※ 整轮要求”，催菜红标签 | 菜后写“· 加单 N”，下面“※ 整轮要求” | 后厨屏同一套写法；补单小票 `?batch=` 两边都能打 |
| 权限 | `table.use`，不弹授权码 | `order.manual`，不弹授权码 | 都不新增权限项 |
| 整轮要求 | 先上饮料、菜齐再上、加急… | 加急、分开装… | 同一份预设（堂食设置里的“整轮要求的选项”），外卖加单也从这里选 |
| 截止 | 结账关台 | 骑手取餐 / 顾客取走 | 后端同一个 `appendBatch`，按订单类型判断截止 |
| 送过的菜 | 不能改，只能退菜 | 不能改 | 一样 |
| 优惠 | 不参加 | 活动重算只升不降、券保留 | 不同（堂食不参加优惠已确认） |
| 收钱 | 结账时一起收 | 骑手到门口收新总额 | 不同 |

## 11. 已确认（brian 2026-11-24：全部按括号里的推荐）

1. **加单的形式**：同一张订单里加一批（原单号不变），还是另开一张关联的新单？（同一张订单加一批。一个骑手、收一次钱、满减合在一起算，堂食也是这么做的）
2. **截止点**：外卖到骑手取餐前、自取到顾客取走前，已打包的也能加（要重新打包）？（是。brian 的原话就是“交接给骑手前”。如果担心骑手在店里等，可以改成“打包完成前”）
3. **顾客能不能自己加菜**，还是只能店员加？（能，但要商家确认，5 分钟不确认自动失效。店员加的直接生效）
4. **加单时能不能再用券**？（不能。原单用的券保留，活动按总额重算只升不降。加单再用券会让“一单一张”的规则变复杂）
5. **顾客自己加菜的次数**？（每单最多 3 次，店员不限）
6. **配送费**：加单不另收？（不另收，同一个骑手一起送。以后如果有按重量或份数收费的需求再加）
7. **确认超时**：顾客加的菜商家多久不确认就失效？（5 分钟，和设置里的接单超时分开，可在设置里改）
8. **外卖减菜、换菜**：这次要不要一起做？（这次不做，只做加。顾客要减菜照旧联系商家，商家走现有的取消或售后。堂食按份退菜 PR #105 已经做了，以后做外卖减菜可以直接用它的逻辑，再加上优惠重算）
9. **整轮要求共用**：外卖加单的“加急、分开装”和堂食的“整轮要求”用同一份预设？（共用。店主只维护一份，后厨看到的写法也一样。外卖用不上的“先上饮料”可以在设置里删）
10. **骑手已到店在等**的时候加单，要不要拦一下？（不拦，只在店员加单时提示“骑手 王师傅 已派单，加单后要等出餐”。系统现在没有“骑手已到店”这个状态）
