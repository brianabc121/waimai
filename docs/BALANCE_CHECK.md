# 余额验算方法

版本 v1.0 · 2026-11-27 · brian 定的铁规则：**凡是新增或改动涉及余额的功能（店铺退款余额、储值“充值送”、平台余额和奖励金、账本本身），都必须按本文重新验算，验算全部通过才能合并。** 这条规则和 [PRICING_CHECK.md](PRICING_CHECK.md)（订单金额验算）一样，没有例外。

余额的架构评审和业内做法见 [BALANCE_REVIEW.md](BALANCE_REVIEW.md)；业务规则见 [REFUND_BALANCE_DESIGN.md](REFUND_BALANCE_DESIGN.md)（退款余额）、[STORED_VALUE_DESIGN.md](STORED_VALUE_DESIGN.md)（储值）。本文只讲两件事：**余额是怎么记的**，以及**怎么证明没记错**。

## 0. 什么时候必须验算

改动只要碰到下面任何一项，就要走完第 6 节的流程：

- 用余额付款、订单变小退回余额、退款退到余额、撤回、冻结、限额
- 储值：充值、撤销充值、储值付款、退回储值、退储值（提现）、赠送、充值送的券
- 平台余额、平台奖励金、平台后台“调整钱包”
- 账户种类、凭证种类、记账规则表 `wallet_journal_rules`
- 对账、账单里和余额、储值有关的数（钱箱里的储值现金、储值卡片）
- 文件：`internal/app/wallet*.go`、`stored.go`、`voids.go`（退款拆分）、`me.go`、`me_admin.go`（平台钱包）、`reconcile.go`、`bills.go` 里的余额部分，`web/src/walletLedger.ts`、`stored.ts`、`credit.ts`
- 任何碰 `wallet_*` 表、`order_refunds`、`topups`、`stored_cashouts`、`orders.credit_paid / stored_*_paid` 的迁移或 SQL

拿不准算不算，就当算。余额的改动几乎都同时碰订单金额，所以 **PRICING_CHECK.md 的流程也要一起走**。

## 2. 余额是怎么记的

### 2.1 复式记账，一句话

每一次余额变动是一张**凭证**（`wallet_journals`），凭证下面至少两行**明细**（`wallet_postings`），每行是某个**账户**（`wallet_accounts`）的增减，**一张凭证的明细相加必须 = 0**。钱不会凭空出现或消失：顾客多了多少，店铺那边就有一个账户记了相反的数。

- 金额一律是整数“分”（1/100），不用浮点数。
- 顾客的账户余额是正数（店里欠顾客的），店铺那边的账户合起来是负数，两边相加 = 0。
- 凭证和明细**只能追加**，改错了用一张新凭证冲回（`reverses` 指向原凭证）。
- 账户余额是缓存，只能由记账触发器改；每个账户的明细按 `seq` 从 1 编号，每行带哈希，接成一条链（第 5.2 节）。

### 2.2 账户

| 账户 | 属于 | 正负 | 意思 |
|---|---|---|---|
| `store_credit` | 顾客 × 门店 × 币种 | ≥ 0 | 退款余额（退款存进来的） |
| `stored_principal` | 顾客 × 门店 × 币种 | ≥ 0 | 储值本金（顾客真金白银充的） |
| `stored_bonus` | 顾客 × 门店 × 币种 | ≥ 0 | 储值赠送 |
| `store_refund` | 门店 × 币种 | ≤ 0 | 退款时**现金那份**存进余额的累计（新进来的钱） |
| `store_sales` | 门店 × 币种 | 任意 | 用退款余额付的累计，减去退回的 |
| `store_topup` | 门店 × 币种 | ≤ 0 | 收到的储值本金（充值，减撤销） |
| `store_bonus` | 门店 × 币种 | ≤ 0 | 送出的赠送 |
| `store_stored_sales` | 门店 × 币种 | 任意 | 用储值付的累计，减去退回的 |
| `store_cashout` | 门店 × 币种 | ≥ 0 | 退储值时真正退出去的钱 |
| `store_clawback` | 门店 × 币种 | ≥ 0 | 退储值时扣回的（顾客原因要扣掉已用的赠送） |
| `store_bonus_void` | 门店 × 币种 | ≥ 0 | 退储值时作废的剩余赠送 |
| `platform_balance` | 顾客 × 币种（不属于门店） | ≥ 0 | 平台余额（已关闭，只剩老数据） |
| `platform_bonus` | 顾客 × 币种 | ≥ 0 | 平台奖励金（同上） |
| `platform_issued` | 平台 × 币种 | ≤ 0 | 平台发出去的余额和奖励金 |

门店的账户 `branch_id` 是门店；平台的三个账户 `branch_id` 为空，数据库约束保证 `platform_` 开头的账户一定没有门店、其他一定有门店。

### 2.3 凭证（每种业务记哪几行）

`x` 是这次的金额（正数）。规则表 `wallet_journal_rules` 写死了每种凭证能动哪些账户，记账函数和检查都按它拦。

| 凭证 | 什么时候 | 明细 |
|---|---|---|
| `refund` | 退款退到退款余额 | 退款余额 +x；退款里原本用退款余额付的那份 s：`store_sales` −s；现金那份 x−s：`store_refund` −(x−s) |
| `revoke` | 撤回存进余额的现金那份（顾客还没用掉） | 退款余额 −y，`store_refund` +y |
| `spend` | 用退款余额付款 | 退款余额 −x，`store_sales` +x |
| `return` | 订单变小，退款余额那份退回 | 退款余额 +x，`store_sales` −x |
| `topup` | 储值充值到账 | 本金 +P、赠送 +B；`store_topup` −P、`store_bonus` −B |
| `topup_revoke` | 撤销充值（没用过） | 上面反过来 |
| `stored_spend` | 用储值付款 | 本金 −p、赠送 −b；`store_stored_sales` +(p+b) |
| `stored_return` | 订单变小退回储值 | 本金 +p、赠送 +b；`store_stored_sales` −(p+b) |
| `stored_refund` | 退款时储值那份回储值 | 同 `stored_return` |
| `stored_cashout` | 退储值 | 本金 −P、赠送 −B；`store_cashout` +退的钱、`store_clawback` +扣回、`store_bonus_void` +B |
| `reclass` | 只在迁移 00085 用过：把老账按新科目重分类 | 只动门店自己的账户，顾客余额不变 |
| `platform_adjust` | 平台后台调整平台余额/奖励金 | 平台余额或奖励金 ±x，`platform_issued` ∓x |

所以从账本上能直接读出：

- 顾客的钱 = 各自账户余额；
- 门店收进来多少新钱：`store_refund`（退款转存）+ `store_topup`（充值）；
- 在店里消费掉多少：`store_sales` + `store_stored_sales`；
- 退出去多少钱：`store_cashout`；扣回多少：`store_clawback`；作废多少赠送：`store_bonus_void`。

### 2.4 唯一入口

应用代码只能调用数据库函数 `wallet_post_journal(...)` 记账（Go 里是 `postJournal` / `postNew`），一次写一张凭证和全部明细。它在数据库里：

1. 按幂等键（`idem_key`）查重：同一个键已经记过就直接返回原凭证，不重复记；
2. 找到或建好账户，**按账户 id 顺序加锁**；
3. 逐行插明细；触发器检查币种、门店、规则表、借贷平衡、顾客余额不小于 0，算出 `balance_after`、`seq`、哈希，更新账户余额。

任何一步不对整张凭证回滚。应用连接数据库用的是受限角色 `waimai_app`：只能读账本，不能直接 `INSERT/UPDATE/DELETE` 账本表，只能调这个函数（第 5.1 节）。

## 3. 规则（编号 W，必须永远成立）

W1–W15 原来写在 PRICING_CHECK.md 第 2.3 节，这里是全量；新增的是 W16–W20。

| 编号 | 规则 | 谁查 |
|---|---|---|
| W1 | 每张凭证至少两行、相加 = 0；全部是凭证自己的门店（平台凭证则全部是平台账户）和币种；每行的账户种类在规则表里允许 | 数据库拦 + `CheckWallet` |
| W2 | 每个账户：余额 = 明细之和 = 最后一行的 `balance_after`；明细编号 1…n 连续不缺；顾客账户不小于 0 | 数据库拦 + `CheckWallet` |
| W3 | 一张单动到的余额只能是本店、本币种的 | 逐单 |
| W4 | 0 ≤ 用余额付的 ≤ 应付；取消、拒单后 = 0；账本上这张单扣掉的 = `orders.credit_paid` | 逐单 |
| W5 | 各种退款之和 ≤ 应付 | 逐单 |
| W5a | 可退的上限是**实收**减已退：没付清的单（骑手少收或没收）实收 = 余额/储值付的 + 下单时预付的 + 骑手收到的现金；已付的单实收 = 应付 − 决定不收的差额（PRICING_CHECK.md 规则 P1、P2）。没收到的钱不能退成现金，也不能存进余额；退款拆现金、余额的比例按实收算（PRICING_CHECK.md 规则 D7b、样例 S14；`Refund` 里的 `orderReceived`） | `TestRefundOnlyWhatWasReceived` |
| W6 | 退款现金那份之和 ≤ 现金实付；用余额付的那份一定回到余额 | 逐单 |
| W7 | 退款记录写的存进余额（减撤回）= 账本上这张单的 `refund`、`revoke` 凭证 | 逐单 |
| W8 | 每张充值单和账本一一对应；撤销的净额为 0 | 全账本 |
| W9 | 储值消费按比例拆本金、赠送；订单变小按这张单用掉的比例退回（第 4 节 SV-S1、SV-S2、SV-S7） | 样例 + 逐单 |
| W10 | 0 ≤ 储值付的 ≤ credit_paid ≤ 应付 | 逐单 |
| W11 | 订单记的储值本金、赠送 = 账本上这张单扣掉的，分开相等 | 逐单 |
| W12 | 退款按累计目标拆现金、退款余额、本金、赠送四份，全部退完各自正好退回（SV-S3、SV-S4） | 样例 + 逐单 |
| W13 | 储值那份只回储值，退款记录的两份 = 账本 | 逐单 |
| W14 | 退储值：顾客原因退 max(0, 剩余本金 − 已用赠送)，门店原因退剩余本金；**账本上** `store_cashout` = 退的钱、`store_clawback` = 扣回、`store_bonus_void` = 作废赠送，和退储值记录一致（B-S1、B-S2） | 全账本 |
| W15 | 每家门店（和平台）每种币种，全部账户余额相加 = 0：顾客手里的 = 另一边的负数 | 全账本 |
| W16 | 每笔退款：账本上冲回的 `store_sales` = 退款里原本用退款余额付的那份；记进 `store_refund` 的 = 现金那份里顾客同意存进余额的（减撤回）。也就是 `store_refund` 只记**新进来的钱**（B-S3） | 全账本 |
| W17 | 平台余额只在平台账户之间流动：`platform_adjust` 只能动 `platform_*` 账户，门店凭证不能动平台账户；每种币种顾客平台余额 + 奖励金 = −`platform_issued`（B-S5） | 数据库拦 + W1、W15 |
| W18 | 哈希链：每个账户第 n 行的哈希 = sha256(第 n−1 行哈希、这一行、它的凭证)，账户的 `last_hash` = 最后一行的哈希；任何一行或凭证被改过、删过、插过，链就断 | `wallet_chain_breaks` |
| W19 | 日终：每个已关账的日子，每个账户 期末 = 期初 + 收 − 付，期初 = 前一天期末；每家门店每种币种期末之和 = 0；关账那天的期末 + 之后的明细 = 现在的余额（B-S4） | 全账本 |
| W20 | 幂等：同一个幂等键只记一次。订单派生的凭证用固定键（`spend:单号:n` 等），重放不重复；充值确认、退储值、平台调整要带请求头 `Idempotency-Key`，同一个键重试返回第一次的结果，换了内容返回 409 | 数据库唯一键 + 测试 |

逐单的规则每个 `checked` 都验；全账本的由 `CheckWallet` 查（测试最后、`make pricing-check-db`、线上每小时/每天）。

## 4. 手算样例

数字全部手算（另用计算器复核），**不许照着程序输出抄**。真库测试见各样例括号里的测试名。

### 已有的样例（不重复抄）

- **W-S1、W-S2、W-S3**：退款余额付的单按菜退款，现金那份 = ⌊退款 × 现金实付 ÷ 应付⌋，零头落在余额那份。见 PRICING_CHECK.md 第 4 节。
- **SV-S1 到 SV-S7**：储值消费拆本金/赠送、退款四份拆分、退储值金额、订单变小按比例退回。见 PRICING_CHECK.md 第 4 节。

下面是记账的样例：每一步每个账户该是多少。测试门店去掉了税、服务费、包装费，所以订单应付就是菜价：鸡 169.00 × 2 = 338.00，茶 69.00，水 30.00。

### B-S7 没付清的单退款：余额那份原样回余额（`TestBalanceSampleUnderpaidRefund`，规则 W5a）

（这一个样例用普通测试门店，有税、服务费、包装费和配送费。）外卖一杯茶应付 161.34：店铺余额付 50.00（`spend`：退款余额 −50.00，`store_sales` +50.00），还要收 111.34，骑手只收到 100.00。实收 150.00。

- 全部退回 150.00：现金那份 ⌊15000 × 10000 ÷ 15000⌋ = **100.00**（系统外退给顾客，不记账本），余额那份 **50.00**
- 凭证 `refund`：退款余额 **+50.00**，`store_sales` **−50.00**（x = s = 50.00，现金那份没有存进余额，`store_refund` 不动）
- 之后顾客余额 = 50.00，和下单前一样；门店 `store_sales` 这张单净额 0；W7、W16 成立
- 改之前（按应付 161.34 拆）：现金 ⌊15000 × 11134 ÷ 16134⌋ = 103.51，比骑手收到的 100.00 还多 3.51，余额只回 46.49

### B-S1 退储值，顾客原因：钱去了哪（`TestBalanceSampleCashout/customer`）

1. 充 1,000.00 送 200.00（这一档送两张 50.00 券）：本金 +1,000.00、赠送 +200.00；`store_topup` −1,000.00、`store_bonus` −200.00。
2. 两份鸡 338.00，用掉一张 50.00 券，应付 288.00，全部用储值：赠送 ⌊28800 × 20000 ÷ 120000⌋ = ⌊4800⌋ = **48.00**，本金 288.00 − 48.00 = **240.00**；`store_stored_sales` **+288.00**。剩本金 **760.00**、赠送 **152.00**。
3. 顾客原因退储值：退钱 = max(0, 760.00 − 48.00) = **712.00**，扣回 760.00 − 712.00 = **48.00**，作废赠送 **152.00**。凭证：本金 −760.00、赠送 −152.00、`store_cashout` +712.00、`store_clawback` +48.00、`store_bonus_void` +152.00，相加 −912.00 + 912.00 = 0。
4. 之后顾客两个账户都是 0；门店那边：−1,000.00 − 200.00 + 288.00 + 712.00 + 48.00 + 152.00 = **0**（W15）。

### B-S2 退储值，门店原因（`TestBalanceSampleCashout/store`）

前两步同 B-S1。门店原因退全部剩余本金：退钱 **760.00**，扣回 **0**，作废赠送 **152.00**。门店那边：−1,000.00 − 200.00 + 288.00 + 760.00 + 152.00 = **0**。

（M2 修之前，退储值只记“本金 −、`store_topup` +”，看不出退了多少钱、扣回多少；现在三个去向各有账户。）

### B-S3 退款时余额那份冲回消费，不算新钱（`TestBalanceSampleRefundShare`）

| 步骤 | 计算 | 退款余额 | `store_refund` | `store_sales` |
|---|---|---|---|---|
| A 单 338.00 付现金，退一份鸡 169.00 存进余额 | 全部是现金那份 | 169.00 | −169.00 | 0 |
| B 单 茶 + 水 = 99.00，全部用余额 | spend 99.00 | 70.00 | −169.00 | 99.00 |
| 退 B 单的茶 69.00（选退钱） | B 单全是余额付的：现金那份 ⌊6900 × 0 ÷ 9900⌋ = 0，余额那份 69.00 回余额，冲回消费 | 139.00 | −169.00 | 30.00 |
| C 单 338.00 = 余额 139.00 + 现金 199.00 | spend 139.00 | 0 | −169.00 | 169.00 |
| 退 C 单一份鸡 169.00，顾客同意全部存余额 | 现金那份 ⌊16900 × 19900 ÷ 33800⌋ = ⌊9950⌋ = **99.50**，余额那份 **69.50** | 169.00 | −268.50 | 99.50 |

最后：门店那边 −268.50 + 99.50 = −169.00 = 顾客手里 169.00 的负数（W15）。`store_refund` 268.50 = 169.00 + 99.50，正好是两次退款里真正的现金存进来的部分（W16）。修之前第三步会记 `store_refund` −69.00，把顾客自己的余额绕一圈当成新钱。

### B-S8 只有储值的顾客，代客下单凭验证码用余额（`TestBalanceSampleStoredValueByCode`）

顾客只有储值：本金 1,000.00、赠送 200.00，没有退款余额。店员代客下单自取两份鸡（微辣），不用券，应付 **338.00**。

- 发验证码时显示可用余额 = 1,000.00 + 200.00 = **1,200.00**（和下单扣款同一个算法：退款余额 + 本金 + 赠送，不含冻结的账户）。改之前只查退款余额，这位顾客得到“没有余额”
- 验证后扣款（规则 W9）：赠送 ⌊33800 × 20000 ÷ 120000⌋ = ⌊5633.33⌋ = **56.33**，本金 338.00 − 56.33 = **281.67**，柜台不用再收钱
- 之后本金 1,000.00 − 281.67 = **718.33**，赠送 200.00 − 56.33 = **143.67**
- 账户冻结时不发码（`CREDIT_NONE`）

### B-S4 日终试算（`TestBalanceSampleTrialBalance`）

B-S1 的第 1、2 步发生在同一天，当天关账后：

## 5. 运行时的保护（不靠测试也成立的）

### 5.1 数据库拦

- 账本表、规则表、日终表、老的平台钱包表：触发器拒绝 `UPDATE/DELETE`（追加型）。
- 账户余额：只有记账触发器能改（看 `pg_trigger_depth()`，会话变量开不了门）。
- 应用角色 `waimai_app` 没有账本表的写权限，只能调 `wallet_post_journal`；冻结、备注这几列可以改。迁移用表的所有者跑（`MIGRATE_DATABASE_URL`），应用用 `waimai_app`（`DATABASE_URL`），设置见 DEPLOY.md。用错了角色，后台“余额账本”页会显示安全警告 `APP_ROLE`。
- `order_refunds` 金额列不能改；存进余额 + 撤回 恒定；不能删。

### 5.1a 并发时的排队

- 同一个店员在同一家店退款进余额：`creditRefundLimits` 先拿“门店 + 店员”的事务锁再数今天已退多少，两笔同时提交也不会一起越过每日额度（`TestCreditDailyLimitUnderConcurrency`：额度 30.00，两张单各退 20.00 同时提交，只进一笔）。
- 充值档位的名额：确认充值时先锁档位行，再另一条语句数已付笔数，最后一个名额不会给两个人（`TestTopupLastPlaceUnderConcurrency`：名额 1，两位顾客同时确认，只有一笔入账 500.00 + 80.00）。

### 5.2 哈希链和指纹

每行明细的哈希接成链（W18），`wallet_chain_breaks(since)` 逐行重算。全部账户 `last_hash` 再算一个**指纹**（digest），每次检查都记在 `wallet_check_runs`，后台显示。把每天的指纹抄到账本之外（例如发到告警群），以后任何人改过历史，重算出来的指纹就对不上。

### 5.3 日终关账

每家门店（和平台）每天过了当地午夜 15 分钟，后台任务（每小时检查时顺带 `CloseWalletDays`）调 `wallet_close_day` 写下每个账户当天的期初、收、付、期末，关过的日子不能再改。商家后台“店铺余额 → 日终试算”、平台后台“余额账本 → 日终试算”能看到。

### 5.4 自动检查和告警

后台任务每小时查一次新记的账（W1、W2、W15、W16、W18 和新动过的订单），每 24 小时查一次全部（再加 W8、W14、W19）。发现问题：

- 平台后台左侧“余额账本”出红色数字，页面顶部列出每一条问题；
- 配了 `WALLET_ALERT_WEBHOOK`（企业微信、钉钉、Slack、Telegram 机器人都可以）就推送一条，6 小时内不重复推。

## 6. 改动流程（每个涉及余额的 PR 都要做）

1. **先想清楚记账**：这次的业务是哪种凭证？动哪几个账户、各记多少？钱从哪来、到哪去？第 2.3 节表里没有的，要先加凭证种类和规则表（迁移），并写进本文第 2 节。拿不准的业务规则先问 brian。
2. **只走一个入口**：只用 `postJournal` / `postNew`（数据库函数 `wallet_post_journal`），不要直接写账本表，也不要绕过规则表。
3. **幂等**：订单派生的凭证用固定的幂等键（同一件事永远同一个键）；顾客或店员按按钮触发的写操作，前端带 `Idempotency-Key`，后端用 `idemBegin`/`idemSave`。
4. **锁顺序**：先锁顾客（`lockCustomer`），再按 `store_sales → store_refund → store_stored_sales` 锁门店账户；`inTx` 遇到死锁会重试一次，但不要依赖它。
5. **写手算样例**：在 `internal/app/balance_check_test.go` 加样例（数字手算），并写进本文第 4 节：每一步每个账户该是多少，最后门店那边加起来 = 顾客那边的负数。
6. **写场景测试**：真库建单，每一步 `checked(t, "步骤", orderID)`，最后 `walletClean(t)`（全账本 W1–W20 都过）。新的检查规则要有一条“改坏数据能被抓到”的测试。
7. **改了规则**：同步更新 `wallet_check.go`、本文第 3 节、PRICING_CHECK.md 第 2.3 节的链接。
8. **跑验算**：`make balance-check` 全部通过；有真实数据时再跑 `make pricing-check-db DAYS=0`，结果 `balance books: 0 problems`。
9. **PR 描述里写“余额验算”一节**（可以和“金额验算”合在一起）：动了哪些凭证和账户、新加的样例和测试、`make balance-check` 的结果。
10. **验算发现现有的账本身不对（不是这次改动引起的）时，先停下告诉 brian**：哪个账户、哪条规则、差多少，等 brian 决定。

### 不允许

- 用浮点数算余额，或者多处各自取整再相加
- 直接 `INSERT/UPDATE/DELETE` 账本表、`wallet_accounts.balance`，或在迁移里关掉触发器改账（老账要改只能加冲回或重分类凭证，像 00085 那样）
- 让应用用数据库所有者或超级用户连接（线上）
- 为了让测试通过去改第 4 节样例的数字，或跳过、删掉验算测试和检查规则
- 关掉或忽略后台的账本告警

## 7. 告警了怎么办

1. 打开平台后台“余额账本”，看问题列表（每条带规则编号、账户或凭证号）。
2. 先停掉相关操作：平台后台冻结有问题的顾客账户或整家店的余额（冻结后不能再用、不能再存），必要时暂停该店的储值活动。
3. 按规则编号查：W18 先比对备份和指纹（有人改过库）；W1/W2/W15 看最近的凭证；W16/W14/W8 看对应的退款、退储值、充值单。
4. 告诉 brian，等决定。更正只能用新凭证（冲回或调整），不能改原来的明细。
5. 更正后手动跑一次全量检查（`make pricing-check-db DAYS=0`，或等下一次每日检查），确认 0 问题，后台的红色数字才会消失。
