# 一店多品牌（一个堂食品牌 + 多个外卖品牌）设计方案 v0.2（2026-11-26，已确认：brian 14:50 “按推荐的来，给我全部落实”，第 17 节全部按推荐）

brian 的要求：一家餐饮实体（一个厨房、一套员工）由**一个堂食品牌**和**多个外卖品牌**组成。比如堂食店叫“一品湘”，外卖上同时开“一品湘”“好吃党”“江西小吃”三个店。

1. 商家开户后可以建一个堂食品牌和多个外卖品牌；
2. 每个品牌有自己的品牌代码：一品湘 `YPX`，代客下单单号 `YPX000112`；好吃党 `HCD`，单号 `HCD000223`；
3. 外卖平台的单分得出“一品湘 Grab / 一品湘 foodpanda / 好吃党 Grab / 好吃党 foodpanda”；
4. 不同外卖品牌的会员列表互相独立，彼此不相干；
5. 送餐地址、热力图可以合并看，也可以分品牌看；
6. 账单、对账也可以合并看或分品牌看。

效果图在 `docs/multi-brand-screens/`（项目文件夹 `multi-brand-screens/` 同一份），原型 `docs/multi-brand-prototype/index.html`（加 `?s=1` 到 `?s=10` 看各屏）：

## 0. 结论先看

1. 分清两个概念：**门店**是实体（厨房、员工、桌台、骑手、钱箱、配送范围、税），**品牌**是顾客看到的“店”（店名、标志、品牌代码、菜单、会员、专属网址、商城里的店铺卡、平台上的店）。一个门店下面挂多个品牌。
2. 每个门店**最多一个堂食品牌**，外卖品牌可以有多个（推荐上限 10 个）；一个品牌可以同时做堂食和外卖（一品湘）。
3. 菜品**门店共用一个菜品库**（后厨按它做，估清一处改全部品牌生效），每个品牌从库里挑菜组成自己的菜单，可以改品牌菜名、图片、**品牌价**。
4. **品牌代码**取代现在的“商家代码”：代客单号 = 品牌代码 + 该品牌的会员号（`HCD000223`）；平台单显示 `好吃党 Grab GF-123`；网店、商城单号按品牌各自从 1 编，后台前面带品牌名。
5. **会员按品牌**：同一个电话在一品湘和好吃党是两个会员、两个号码，互相看不到。
6. 送餐地址/热力图、账单、对账：默认“全部品牌合并”，可切到单个品牌；**钱箱只按门店**（现金都在一个抽屉里）。
7. 老数据：现有每个店铺自动变成它的**主品牌**（堂食 + 外卖），店名、代码、店铺号、网址、会员号、订单号**全部不变**，商家不用做任何事。
8. 涉及金额的地方（品牌价、活动和券按品牌、平台价按品牌、按品牌对账）按 `docs/PRICING_CHECK.md` 验算：计价引擎不加新阶段，新增规则 D13–D15、R 规则一条、手算样例 S10/S10a、场景第 18 格（第 11 节）。

## 2. 业内怎么做

| 系统 | 做法 | 我们借鉴什么 |
|---|---|---|
| **Deliverect**（聚合接单） | 账号下“地点（Location）”是实体店，“品牌（Brand）”另加；每个品牌在每个平台各连一条“渠道连接”，进来的单带品牌 ID；同一份商品库，按品牌 / 渠道微调价格、图片、描述（Fine-Tune）；多一个品牌要多一份订阅 | **门店 ≠ 品牌**；商品库共用、品牌菜单可改价；平台按“品牌 + 平台”开通 |
| **Otter**（聚合接单 + 虚拟品牌） | 一家店所有品牌的单汇到一块屏；自己开的第三方虚拟品牌按品牌单独收费；它自己也承认“一个品牌一块平板”会把后厨弄乱 | 所有品牌的单进**同一个后厨流程**，靠品牌标签区分 |
| **Toast** | 虚拟餐厅要**另开一个“地点”**挂到餐厅组下，至少一台有线终端；虚拟品牌的单只打印、**进不了后厨屏（KDS）**；建议把用餐方式命名成“虚拟餐厅外卖”方便店员认 | 反例：把品牌建成独立门店，后厨就被拆开了，所以我们不这样做 |
| **Square** | 同一个云厨房可以开多个概念品牌，每个品牌一个自己的点餐网站，网站数量不限、不收佣金 | 每个品牌一个**专属点餐页面** |
| **DoorDash** | 虚拟品牌质量要求：同一地址**最多 10 个虚拟品牌**（大型中央厨房可申请例外），必须有执照、在合规厨房出餐 | 外卖品牌上限推荐 10 |
| **Grab、foodpanda** | 平台上每个品牌是一家独立的店（独立商户号、独立结算）；foodpanda 和 Rebel Foods 合作在亚洲 2000 多家店上开虚拟品牌，“插进现有厨房，几乎没有启动成本”；GrabKitchen 一个厨房十几个品牌 | “一品湘 Grab”“好吃党 Grab”是**两家平台店**，平台店铺号、佣金合同、到账都按品牌分 |
| **国内收银系统**（美团收银、客如云、天财商龙等） | 搜到的公开资料只有宣传页，没找到“一店多品牌”分账的权威文档；行业通行的问法是三点：多个品牌的菜单和订单能不能分开核算、会员能不能共享、报表能不能按品牌 / 渠道拆 | 这三点本方案都给了答案：菜单可分、会员不共享、报表可合可分 |

参考：[Deliverect 虚拟品牌](https://help.deliverect.com/en/articles/8100000-what-are-virtual-brands)、[Deliverect 添加品牌](https://help.deliverect.com/en/articles/7978963-add-brands-to-your-account)、[Deliverect 开发文档：账号品牌](https://developers.deliverect.com/v1.1-restaurants/docs/how-to-handle-account-brands)、[Lightspeed：Deliverect 多场地设置](https://o-series-support.lightspeedhq.com/hc/en-us/articles/31329301328667-Deliverect-advanced-settings-for-multi-site-venues)、[Otter 虚拟品牌](https://tryotter.com/products/virtual-brands)、[Otter：虚拟品牌问答](https://www.tryotter.com/blog/toolkit/your-questions-about-virtual-brands-answered)、[Otter 第三方品牌](https://helpdesk.tryotter.com/hc/en-us/articles/360052655553)、[Toast：设置虚拟餐厅](https://support.toasttab.com/en/article/Setting-Up-a-Virtual-Restaurant)、[Square 云厨房](https://squareup.com/ca/en/point-of-sale/restaurants/ghost-kitchens)、[DoorDash 虚拟品牌质量要求](https://help.doordash.com/en-us/merchants/article/official-doordash-virtual-brand-quality-requirements)、[foodpanda × Rebel Foods](https://mb.com.ph/2021/10/22/foodpanda-and-rebel-foods-form-long-term-partnership/)、[GrabKitchen 新加坡](https://www.grab.com/sg/press/tech-product/grabfood-unveils-merchant-solutions-and-1st-grabkitchen-in-singapore/)、[CloudKitchens：一个厨房跑多个品牌](https://cloudkitchens.com/blog/how-to-run-multiple-brands-from-one-kitchen)。Grab、foodpanda 对“同地址多个品牌”的具体规则没有公开文档，各国以商户经理说的为准。

结论：
- 做得好的（Deliverect、Otter）都是**一个实体店挂多个品牌**，后厨一块屏、一份商品库，品牌只是“门面 + 菜单 + 渠道”。Toast 把虚拟品牌建成另一个地点，结果后厨屏都用不了，正是我们要避免的。
- 平台上每个品牌是独立的店，所以平台开通、平台价、佣金、到账都要按“品牌 + 平台”记。

## 3. 两种做法，推荐 B

| | A：每个品牌建成一个独立“店铺”，再把几个店铺绑成一组 | **B（推荐）：门店下面加“品牌”** |
|---|---|---|
| 顾客端（菜单、会员、专属页面、商城卡片） | 现成的，几乎不用改 | 要让这些按品牌走 |
| 后厨、员工、桌台、骑手、钱箱、估清 | 每个品牌各一套；所有后台查询都要从“本店”改成“本组所有店” | 不变，还是一个门店 |
| 同一道菜 | 每个品牌各存一份，估清、改价、后厨工位要几处同步 | 菜品库一份，品牌菜单只是“挑菜 + 改名改价” |
| 配送范围、税、营业设置 | 几份要手工保持一致 | 一份 |
| 业内 | Toast 的做法（后厨屏用不了） | Deliverect、Otter 的做法 |

A 看起来改动少，其实是把“合并”的难题推到了每一个后台页面；brian 说的“一家餐饮实体”本来就是一个门店，所以推荐 **B**。

## 4. 数据关系

```
商家 merchants
 └─ 门店 branches（实体：厨房、员工、桌台、骑手、钱箱、配送范围、税、时区、菜品库）
     ├─ 品牌 brands：一品湘（堂食 + 外卖，主品牌）
     ├─ 品牌 brands：好吃党（外卖）
     └─ 品牌 brands：江西小吃（外卖）
```

### 4.1 新表 `brands`

| 列 | 说明 |
|---|---|
| `id`、`branch_id` | 属于哪个门店 |
| `name`、`name_en`、多语言名 | 品牌名（顾客看到的店名）；多语言照现在店名的规则（content_translations） |
| `code` | 品牌代码，2–8 位大写字母或数字，**全平台唯一**（顶替 `branches.store_code`） |
| `store_no`、`slug` | 专属页面店铺号（`10002.abcfood.com`）、商城网址名；和现在店铺用同一个序列，不会撞 |
| `dine_in`、`delivery` | 这个品牌做不做堂食、做不做外卖/自取；一个门店 `dine_in=true` 的品牌最多一个 |
| `is_main` | 主品牌（迁移时的那个，不能删；顾客打开老链接到的就是它） |
| `logo`、`cover`、`intro`、`color` | 标志、封面、简介；`color` 是后台订单标签的颜色 |
| `open_time`、`close_time`、`paused` | 品牌营业时间（空 = 跟门店）、品牌单独暂停接单 |
| `mall_visible` | 是否在河马商城显示 |
| `sort`、`status`、`created_at` | |

### 4.2 加 `brand_id` 的表

| 表 | 说明 |
|---|---|
| `orders` | 每张单属于一个品牌（非空）；另存 `brand_name` 快照，品牌改名后老小票、老单照样显示当时的名字 |
| `store_members` | 会员按品牌：唯一键改成 `(brand_id, member_no)`；电话查会员只查本品牌 |
| `menu_categories` | 品牌菜单的分类（见第 5 节） |
| `promotions`、`coupon_batches` | 活动、券属于哪些品牌（第 10 节） |
| `store_images`、`store_media`、`branch_categories` | 品牌的图片、宣传物料、商城分类 |
| `reviews`、`customer_favorites`、`chat_threads` | 评价、收藏、聊天会话按品牌 |
| `branch_domains` | 自有域名绑到品牌（每个品牌可以有自己的域名） |
| `branch_platforms` → 按品牌 | 主键改成 `(brand_id, platform_id)`：一品湘 Grab、好吃党 Grab 是两条，平台店铺号、佣金、加价各自填 |
| `item_platform_prices` | 加 `brand_id`：好吃党 Grab 的平台价按好吃党的品牌价算 |
| `platform_payouts` | 平台到账按“品牌 + 平台”录 |
| `order_counters` | 网店、商城单号按品牌编：`kind` 里带品牌（如 `web:12`） |

**不加** `brand_id`、仍按门店的：菜品库 `menu_items`（及规格、加料、口味）、后厨工位、桌台、排队叫号、骑手、员工考勤、配送范围和配送费、包装费、税率、服务费、钱箱 `cash_counts`、核款 `payment_checks`、门店时区和每日重置时间。

### 4.3 老数据迁移（一次 SQL，金额列一个都不碰）

1. 每个现有门店建一个品牌：`is_main=true`，名字、英文名、标志、封面、简介照抄店铺；`code = branches.store_code`；`store_no = branches.store_no`；`slug = branches.slug`；`dine_in`、`delivery` 按店里现在开没开桌台、开没开外卖/自取。**所以老链接、老代码、老会员号、老单号全部不变**。
2. 上面第 4.2 节各表的 `brand_id` 全部填成本店主品牌。
3. 品牌菜单：主品牌的分类就是现在的分类，菜就是现在的菜，品牌价、品牌菜名都空着（= 跟菜品库）。所以顾客看到的菜单一模一样。
4. `branch_platforms`、`item_platform_prices`、`platform_payouts` 挂到主品牌。
5. `branches.store_code`、`store_no`、`slug` 这一版先**保留**（只读，跟着主品牌同步），等所有代码都改成读品牌后，下一个版本再删。
6. `down` 迁移删掉新表和新列，老数据不受影响。
7. 迁移前后跑 `make pricing-check-db`，每张单的金额检查结果必须一致（第 11 节）。

## 5. 菜单：菜品库共用，品牌菜单可改名改价（效果图 03）

商家后台“菜单”页上面多一排：**菜品库 | 一品湘 | 好吃党 | 江西小吃**。

- **菜品库**（门店的）：就是现在的菜单页——菜品、编号、规格、加料、口味、后厨工位、估清、Excel 导入都在这里。后厨、出餐、估清都认菜品库。
- **品牌菜单**：每个品牌自己的分类和排序，从菜品库里勾菜放进来（同一道菜可以放进多个品牌）。每道菜在品牌里可以单独设：
  - **品牌菜名**（好吃党里“小炒肉”叫“辣椒炒肉”），多语言照常翻译；
  - **品牌图片**（换一张更“外卖风”的图）；
  - **品牌价**（空着 = 菜品库价）；
  - 在这个品牌里上架 / 下架。
- 规格、加料、口味跟着菜品库走，品牌里不能单独改（**待确认 3**，推荐先这样，要改再加）。
- 估清：菜品库里点“估清”，所有品牌里这道菜一起售罄（一个厨房，就是一份库存）。
- 后厨单、出餐看板显示**菜品库菜名**（厨师认这个），后面小字带品牌菜名；顾客小票显示品牌菜名。
- Excel 导入导出：菜品库照旧；每个品牌多一张“品牌菜单”表（编号、品牌分类、品牌菜名、品牌价、上架），按菜品编号对上。
- 新建品牌时可以“从某个品牌复制菜单”，再删改。

## 6. 品牌代码和订单号

| 订单类型 | 现在 | 一店多品牌之后 |
|---|---|---|
| 代客下单 | 商家代码 + 会员号 `YPX000123` | **品牌代码 + 本品牌会员号**：一品湘 `YPX000112`，好吃党 `HCD000223`；同日第二单照旧加 `-2` |
| 平台订单 | `Grab GF-123` | 后台前面带品牌名：`一品湘 Grab GF-123`、`好吃党 foodpanda #a8kx` |
| 网店订单 | `Online-1`（按店） | **按品牌各自编**：好吃党今天第 3 张网店单就是 `Online-3`；后台、后厨、取餐屏前面带品牌名 `好吃党 Online-3`（**待确认 5**） |

## 11. 金额验算（按 docs/PRICING_CHECK.md，铁规则）

### 11.1 哪些地方碰钱

| 改动 | 说明 |
|---|---|
| 品牌价 | 一道菜在品牌里的原价可以和菜品库不同。它只是计价引擎的**输入**（每道菜的单价），由 `loadMoney` 按订单的品牌取；下单、加单都写进 `order_items` 的单价快照，改单只读快照 |
| 活动、券按品牌 | `choosePromo` 和挑券只看订单所属品牌的活动、券；引擎本身不变 |
| 平台价按品牌 | `pricing.PlatformPrice` 的基数改成品牌价；算法、只取整一次的规则不变 |
| 佣金按品牌 | 佣金比例取“品牌 + 平台”的合同；`pricing.Commission` 不变 |
| 对账、账单按品牌 | 合并 = 各品牌之和 |

**计价引擎（`internal/pricing.Price`）不加新阶段，阶段顺序不变**；所有算钱仍只走 `loadMoney → choosePromo → priceMoney → saveMoney`，不另写一份。前端 `web/src/dishPromo.ts`（菜品活动的显示）要同步只取本品牌的活动，并补测试。

### 11.2 新规则（实现时加进 `App.CheckOrderMoney` 和 PRICING_CHECK.md 第 2.2 节）

| 编号 | 规则 |
|---|---|
| D13 | 订单的每条活动明细（`order_discounts` 里活动、菜品活动）对应的活动都适用于订单的品牌；每张店铺券的发券品牌 = 订单的品牌；平台券、平台单的两种平台优惠不受这条限制 |
| D14 | 平台单的“品牌 + 平台”在 `branch_platforms`（按品牌）里存在；佣金比例 = 下单时这个品牌在这个平台的比例（或手改的） |
| D15 | 代客单的会员和订单是同一个品牌；订单号前缀 = 下单时的品牌代码 |
| R（对账） | 对账页、账单页：各品牌的营业额、收款、平台应收、佣金之和 = “全部品牌”合并视图里的对应合计；合并视图的收款合计 = 现在按门店算的收款合计（钱箱算法不变） |

### 11.3 手算样例 S10（实现时写进 `TestPricingCheckSamples`，数字是手算的）

门店税 12% 含税，外卖，配送费 50.00，无包装费、服务费。菜品库：小炒肉 58.00、米饭 3.00。
- 一品湘：小炒肉用库价 58.00；活动“满 100 减 15”（只适用一品湘）。
- 好吃党：小炒肉叫“辣椒炒肉”，**品牌价 52.00**，米饭 3.00；活动“满 100 减 10”（只适用好吃党）。
- 同一个购物车：小炒肉 × 2 + 米饭 × 2。

**一品湘下单**
- 小计 = 58.00 × 2 + 3.00 × 2 = 116.00 + 6.00 = **122.00**；满 100 减 15
- 分摊：小炒肉 15 × 116/122 = 14.2623 → **14.26**；米饭 15 × 6/122 = 0.7377 → **0.74**（合计 15.00）
- 净额 101.74 + 5.26 = 107.00；税 107.00 × 12/112 = 11.4643 → **11.46**（每道菜 10.9007 → 10.90、0.5636 → 0.56，合计 11.46）
- 应付 = 122.00 + 50.00 − 15.00 = **157.00**

**好吃党下单**
- 小计 = 52.00 × 2 + 3.00 × 2 = 104.00 + 6.00 = **110.00**；一品湘的满 100 减 15 **不适用**；好吃党满 100 减 10
- 分摊：辣椒炒肉 10 × 104/110 = 9.4545 → **9.45**；米饭 10 × 6/110 = 0.5455 → **0.55**（合计 10.00）
- 净额 94.55 + 5.45 = 100.00；税 100.00 × 12/112 = 10.7143 → **10.71**（10.1304 → 10.13、0.5839 → 0.58，合计 10.71）
- 应付 = 110.00 + 50.00 − 10.00 = **150.00**
- 如果好吃党没有自己的活动：应付 = 110.00 + 50.00 = **160.00**（一品湘的活动不会跨品牌）

**券不跨品牌**：顾客有一张好吃党的“满 100 减 20”复购券，在一品湘下同样的单，应付仍是 **157.00**，结算页不列这张券；点名要用也被拒绝。

### 11.4 手算样例 S10a 平台价按品牌（`TestPlatformPrice` 加用例）

- 好吃党 Grab 加价 15%、取整 1：辣椒炒肉 52.00 × 1.15 = 59.80 → **60.00**；米饭 3.00 × 1.15 = 3.45 → **3.00**
- 一品湘 Grab 加价 20%、取整 1：小炒肉 58.00 × 1.2 = 69.60 → **70.00**；米饭 3.60 → **4.00**
- 好吃党 Grab 佣金 25%：小炒肉 × 2 + 米饭 × 2 = 120.00 + 6.00 = 126.00，无优惠，佣金 126.00 × 25% = **31.50**，预计到账 **94.50**；同样的单在一品湘 Grab：148.00，佣金 30% = **44.40**，到账 **103.60**

### 11.5 落在第 3 节哪几格

新增**第 18 格“一店多品牌”**：同一购物车在两个品牌下单按各自品牌价；活动、券不跨品牌（列表里不出现、点名也不用）；加单按订单品牌的菜单价，不会拿到别的品牌的价；店铺原因退菜、按菜退款照旧；平台单按品牌的平台价和佣金；对账、账单按品牌合计 = 合并。测试：`TestBrandPricing`（S10）、`TestBrandPromoCouponScope`、`TestBrandAddonPrice`、`TestBrandPlatformOrder`（S10a）、`TestBrandReconciliation`、`TestBrandMigrationMoneyUnchanged`（迁移前后 `CheckOrderMoney` 结果一致）。每个场景测试每一步都调 `checked(t, "步骤", orderID)`。

第 7 格（代客下单）、第 14 格（对账账单）、第 16 格（平台订单）、第 17 格（商城/网店）各补一个“非主品牌”的用例。
