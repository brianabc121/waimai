## 0. 结论先看

1. 订单只分 **5 类**：
   - **堂食订单** `DineIn-1`，再分“店员点单”和“扫码自助”；
   - **代客下单** `YPX000123`（商家代码 + 会员号）；
   - **平台订单** `Grab GF-123`（Grab、foodpanda 和管理员按国家加的平台）；
   - **商城订单** `Hippo-1`，顾客从河马商城进店下的单，每天当地 00:00 清零；
   - **网店订单** `Online-1`，顾客打开商家分享的链接下的单，按商家设的重置时间每天清零。
2. 商家分享的链接改成**店铺专属页面**：`https://67891.abcfood.com`（67891 是店铺号），页面上没有商城入口、没有别的店，“我的”里也只看得到这家店；商家可以绑定自己的域名，或者向平台申请购买。
3. 怎么分商城单和网店单：**看顾客在哪个网址下的单**。商城网址下进店 → 商城订单；店铺专属网址或商家自己的域名 → 网店订单。
4. 老订单**不改号**：只补“订单类型”，原来的 `W1126-001`、`D1126-001` 照旧显示和搜索。
5. 平台订单按**平台价**点菜，不套本店活动、券、服务费、配送费；平台优惠分“商家出资”“平台出资”录入；佣金单独记，不算进订单金额；平台单**不进钱箱**，对账页单独一块。
6. 涉及订单金额（平台单金额、平台券只限商城单），按 `docs/PRICING_CHECK.md` 验算：手算样例 S9、场景第 16、17 格、新规则 D10–D12（第 10 节）。

## 2. 业内怎么做

| 系统 | 做法 | 我们借鉴什么 |
|---|---|---|
| **Toast**（美国） | 每个外卖平台接进来都有自己的“用餐方式”（Dining Option）和“付款类型”，报表能按平台拆开；接入前店员要在平台平板上看单、再在 POS 里手动录一遍。自家有两种线上点餐：餐厅自己的点餐网站（Online Ordering / Digital Storefront，不收佣金）和 Toast 的点餐 App 市场（Toast Local），报表里分开 | 平台 = 一种订单类型；**自己网站的单和市场的单分开记** |
| **DoorDash** | 平台市场（Marketplace，收佣金，帮你拉新客）和商家自有点餐网站（原 Storefront，现在叫 Direct Ordering，不收佣金）是两个产品；自有网站给一个专属链接，付费版可以连商家自己的域名，没有域名也可以帮商家配一个 | **店铺专属页面 + 可绑自己的域名**；商城单和网店单分开 |
| **Square** | 外卖平台的单进交易记录“只作记录”，付款和退款由平台管；交易报表按“来源”筛选 | 平台单不进钱箱；对账按来源拆 |
| **Loyverse**（东南亚小店常用） | 用餐方式可以随便加，每张单存下所选方式；Grab 用插件 GrabConnect 把单拉进来。平台价一般做法是另建一份“Grab 价”的菜 | 平台由后台自定义添加；平台价用“加价比例 + 个别菜单独价” |
| **Otter、Deliverect、Klikit**（聚合接单） | 把各平台的单汇到一块屏，自动打印进后厨；支持按渠道设不同价格 | 所有平台的单进同一个后厨流程 |
| **GrabFood 商家端** | 每单有长单号和短单号（如 `GF-123`），小票上两个都印；佣金按订单金额收，各国大约 15%–30%；商家出资和平台出资的优惠分开列 | 平台单号存短单号；优惠分两种出资；佣金单独记 |
| **foodpanda 商家端** | 多种佣金套餐，费率注册时定；结算单里有佣金、“费用和调整”等扣项 | 佣金费率按店可改；“其他扣费”留一栏 |
| **美团收银 / 客如云** | 外卖平台的单自动接到收银机；订单按渠道（堂食、自营外卖、美团、饿了么）分；菜品可按渠道设价格；对账按渠道看营业额、补贴、佣金 | 渠道价、按渠道对账 |
| **Shopify 这类开店平台** | 每家店先给一个统一域名下的子域名（`店名.myshopify.com`），商家可以接自己买的域名；技术上是统一域名用一张通配证书，自己的域名在第一次访问时自动签证书（Caddy 的 on-demand TLS 就是干这个的，签之前先问我们的系统“这个域名是不是我们的店”） | `67891.abcfood.com` + 绑定自有域名，证书自动签 |
| **餐厅通用的取餐号** | 每天（营业日）从 1 开始的流水号；营业日在凌晨某个时间切换，深夜营业的店不会半夜断号 | 堂食、网店号按商家设的重置时间清零 |

参考：[Toast Grubhub 接入](https://support.toasttab.com/en/article/Grubhub-Integration-Overview)、[Toast Local 常见问题](https://support.toasttab.com/en/article/Local-by-Toast-FAQ)、[Toast 外卖平台佣金](https://pos.toasttab.com/blog/food-delivery-fees-and-commissions)、[DoorDash 自有点餐网站](https://merchants.doordash.com/en-us/products/storefront)、[Square 外卖接入](https://squareup.com/help/au/en/article/6649)、[Loyverse 用餐方式](https://help.loyverse.com/help/dining-options)、[Loyverse GrabConnect](https://loyverse.com/marketplace/grab-connect)、[Sapaad：堂食和 GrabFood 不同价](https://www-dr.sapaad.com/knowledge-base/how-can-i-have-different-menu-prices-for-dine-in-and-grabfood/)、[Grab 佣金说明](https://www.grab.com/th/en/blog/askgrab-merchant-commission/)、[GrabMerchant 手册](https://hodor-assets.grab.com/attachments/merchant/en-ph/articles/22150/rc-upload-1714107664018-2-GrabMerchant%20Handbook.pdf)、[foodpanda 商家](https://partner.foodpanda.sg)、[Otter + Square](https://helpdesk.tryotter.com/hc/en-us/articles/18755245669523-Otter-Square-Integration-Guide)、[Caddy on-demand TLS](https://caddyserver.com/on-demand-tls)、[Caddy 服务上万个域名的做法](https://caddy.community/t/serving-tens-of-thousands-of-domains-over-https-with-caddy/11179)。客如云、美团收银的帮助中心没搜到公开文档，上表写的是这类收银系统的通用做法。

结论：
- **手动录平台单**是接口没开通前业内最普遍的过渡做法；以后接通 Grab/foodpanda 接口，自动进来的单也落在同一个“平台订单”类型里。
- **“市场”和“商家自己的网站”分开**是大平台的通行做法：市场帮商家拉新客，自有网站留住老客、不把顾客引到别的店。brian 说的“商家介意客源流失”正是 DoorDash、Toast 单独做自有点餐网站的原因。

## 3. 五类订单

| 类型 | 代码 `order_type` | 包括哪些单 | 订单号 | 从哪来 |
|---|---|---|---|---|
| 堂食订单 | `dine_in` | 店员开台点菜（**店员点单**）；顾客扫桌上二维码、用桌上平板（**扫码自助**） | `DineIn-1` | 后台“堂食下单”、扫码点餐 |
| 代客下单 | `staff` | 店员替顾客下的外卖、自取单（微信、电话、LINE 等发来的） | `YPX000123` | 后台“外卖下单” |
| 平台订单 | `platform` | Grab、foodpanda 等外卖平台上的单，店员手动录入（以后接口自动进） | `Grab GF-123` | 后台新页面“平台下单” |
| 商城订单 | `mall` | 顾客在河马商城里点进这家店下的外卖、自取单 | `Hippo-1` | 商城网址 |
| 网店订单 | `web` | 顾客打开商家分享的链接（店铺专属页面）下的外卖、自取单 | `Online-1` | 店铺专属网址、商家自己的域名 |

`service_type`（外卖 / 自取 / 堂食）保留，它说的是**怎么交给顾客**，和**订单类型**是两件事。`channel` 列保留不删（很多查询在用），新加的 `order_type` 是以后所有页面、筛选、报表看的字段。

### 3.1 堂食再分“店员点单 / 扫码自助”

- 新列 `orders.dine_source`：`staff`（店员在“堂食下单”开台）或 `self`（顾客扫桌上二维码、用桌上平板自己开的单）。
- 一桌经常是混着的：店员开台，顾客后来自己扫码加菜。**待确认 8** 推荐：整张单按**谁开的台**算（订单列表、报表看这个）；每一批菜另外记是谁点的（`order_batches.placed_by_kind`：店员 / 顾客），订单详情和后厨单上每批标“店员点 / 顾客扫码加”。
- 订单列表堂食标签写成“堂食 · 店员”“堂食 · 扫码”，筛选可以只看其中一种。
- 实现说明（第一批）：桌台都由店员开，所以“谁开的台”实际按**第一批菜的来源**判断：第一批来自顾客手机扫码或桌上平板（`qr`/`ipad`）记 `self`，否则记 `staff`。老订单迁移也按这个规则。

### 3.2 商城订单和网店订单怎么分

**按顾客下单时所在的网址**，后端从请求的域名判断，前端不能改：

| 顾客在哪下单 | 订单类型 |
|---|---|
| 商城网址 `order.abcfood.com`，从商城首页、搜索、分类点进店铺（店铺页网址改成 `/mall/s/:slug`） | 商城订单 `Hippo-` |
| 店铺专属网址 `67891.abcfood.com`，或商家绑定的自己的域名 | 网店订单 `Online-` |
| 老链接 `order.abcfood.com/s/:slug`（以前商家分享出去的） | 直接打开时自动跳到这家店的专属网址，所以算网店订单 |
| 桌上二维码、平板 | 堂食订单（扫码自助），不管从哪个网址 |

**待确认 5**：推荐就按上面这样分。另一个做法是按“顾客第一次从哪进来”记一段时间（像广告归因），实现复杂、顾客换手机就不准，不推荐。

## 4. 订单号

### 4.1 每一类怎么编

| 类型 | 规则 | 例子 | 什么时候清零 |
|---|---|---|---|
| 堂食 | `DineIn-` + 当天第几张堂食单，不补零 | `DineIn-1`、`DineIn-128` | 每天，**商家设的重置时间** |
| 代客 | 商家代码 + 会员号（6 位，补零）；同一会员同一营业日第二单起加 `-2` | `YPX000123`、`YPX000123-2` | 会员号固定；后缀每天从头 |
| 平台 | 平台显示名 + 平台短单号（店员照平台平板或小票抄） | `Grab GF-123`、`foodpanda #a8kx-21qe` | 不由我们编 |
| 商城 | `Hippo-` + 这家店当天第几张商城单 | `Hippo-1`、`Hippo-37` | 每天**门店当地凌晨 00:00**（brian 指定） |
| 网店 | `Online-` + 这家店当天第几张网店单 | `Online-1`、`Online-15` | 每天，**商家设的重置时间** |

- 每一类**单独一个序号**：今天第 5 张堂食单就是 `DineIn-5`，不会被外卖单插号。序号存在新表 `order_counters (branch_id, kind, period, seq)`，同一事务里 `INSERT … ON CONFLICT DO UPDATE SET seq = seq + 1 RETURNING seq` 取号，并发下不会重号。
- **营业日和重置时间**：店铺设置一个“每日重置时间”（默认 04:00，可选 00:00–08:00），堂食和网店共用（**待确认 9**）。凌晨 1 点的堂食单仍算前一个营业日，序号接着排。商城单按 brian 说的固定当地 00:00 清零。门店时区照旧。
- 编号本身同一天会重复出现在不同店（每家店都有 `Hippo-1`），所以订单号是**店内**的号码；平台后台看订单时前面带店名。
- **取餐号 / 叫号**：排队叫号屏、取餐屏、骑手端显示完整订单号（`DineIn-12`、`Online-7`、`Hippo-3`、`Grab GF-123`）。`pickup_code` 存号码里的数字部分（平台单存平台短单号），给只放得下几位数的地方用。
- `DineIn-`、`Hippo-`、`Online-` 三个前缀**全球统一、不翻译**（小票、叫号屏、截图对得上）。页面上的类型名“堂食订单 / 商城订单”照常多语言。

**待确认 1：代客单号怎么拼？** brian 的例子 `YPX05112`，我理解为商家代码 `YPX` + 会员号。但现在会员号至少 6 位（`000001` 起），所以推荐 `YPX000123` 这样“代码 + 6 位会员号”，不加分隔符；如果 `YPX05112` 整个是商家代码，那号码就是 `YPX05112-000123`。

**待确认 2：同一会员同一天下第二单怎么办？** 推荐加 `-2`、`-3` 后缀，后厨和骑手能分清是两张单。

### 4.2 商家代码

- 店铺设置“订单编号”一栏：商家代码，2–8 位大写字母或数字，**全平台唯一**。
- 新店默认用店铺网址名（slug）的前 3 个字母自动生成一个不重复的，店主可改。改代码只影响以后的单，老单号不变。平台后台“商户管理”能看到、能改。

**待确认 3：商家代码按店（分店）还是按商家？** 推荐**按店**（`branches.store_code`）：会员是按店的，同一商家两家分店各有一套会员号。

### 4.3 数据库里存什么

| 列 | 说明 |
|---|---|
| `orders.order_type` | `dine_in` / `staff` / `platform` / `mall` / `web`，非空，有 CHECK |
| `orders.dine_source` | 堂食才有：`staff` / `self` |
| `orders.display_no` | 上面规则拼出来的订单号，所有页面、小票、叫号屏、搜索都用它 |
| `orders.biz_date` | 营业日，按重置时间算；日报、对账以后也可以按它分天 |
| `orders.order_host` | 顾客下单时的网址（商城、`67891.abcfood.com` 或自有域名），查问题用 |
| `orders.platform_id`、`orders.platform_order_no` | 只有平台单有；同一平台单号 7 天内重复会提示“这张平台单已经录过” |

### 4.4 老订单迁移

迁移只**补字段不改号**，跑一次 SQL：

1. `order_type`：`channel='dine_in'` 或 `service_type='dine_in'` → `dine_in`（`channel='dine_in'` 的 `dine_source='self'`，店员开台的 `staff`）；`channel='staff'` 且不是堂食 → `staff`；其余（`web`）→ `web`。
   - 老的顾客自助单分不出当时是从商城还是从商家链接进来的（以前只有一个网址），**待确认 14** 推荐全部记成网店订单；对账页“按类型”在上线日之前的数据会标“上线前未区分”。

### 5.4 技术做法（实现时）

- 服务器：`*.abcfood.com` 加一条通配 DNS 记录指向服务器；Caddy 用 **on-demand TLS**，每个新网址第一次被访问时自动签证书；签之前 Caddy 先问后端 `GET /internal/tls-ask?domain=…`，只有“存在的店铺号子域名”或“已验证的商家域名”才放行，防止被人拿乱七八糟的域名刷证书。DEPLOY.md 加一节。
- 后端按请求的域名认店：`order.` → 商城模式；`数字.主域名` 或 `branch_domains` 表里已验证的域名 → 网店模式，这家店。顾客接口（下单、报价、我的订单、消息）在网店模式下只返回这家店的数据。
- 下单时 `order_type` 由后端按域名定（`mall` 或 `web`），前端传什么都不算。
- 新表 `branch_domains (branch_id, domain, status, verified_at, requested_at, note)`；店铺号和自有域名都写进 Caddy 的放行名单。
- 前端同一个构建，启动时调 `GET /api/site` 知道自己是商城模式还是网店模式，路由和导航按模式切换。

## 9. 金额怎么记

### 9.1 一张平台单的钱

| 项 | 记在哪里 | 谁的钱 |
|---|---|---|
| 菜品平台价 | `order_items.unit_price`（下单时的快照） | |
| 商家出资优惠 | `order_discounts` 一行，`kind='platform_merchant_promo'`，`funded_by='merchant'`，规则快照存平台和金额 | 店铺承担 |
| 平台出资优惠 | `order_discounts` 一行，`kind='platform_promo'`，`funded_by='platform'`；走引擎现有的“平台出资”阶段（税后） | 外卖平台承担，不减店铺应收 |
| 包装费 | `orders.packaging_fee`（店员填） | |
| 税 | 按店铺税率，**平台单一律按含税算**（平台上的价就是顾客付的价），快照存在订单 | |
| 服务费、配送费 | 都是 0 | |
| 顾客实付 | `orders.total`（= 平台价小计 + 包装费 − 商家出资 − 平台出资） | |
| 商家应收 | `total + platform_subsidy`（和本店平台券同一个意思） | |
| 佣金、其他扣费 | **新表 `order_platform_fees`**（订单、类型 `commission`/`other`、比例、基数、金额、是否手改、原因），**不进订单金额** | 店铺付给平台 |
| 预计到账 | 商家应收 − 佣金 − 其他扣费（算出来显示，不单独存） | |
| 付款 | `pay_type='platform'`，`pay_channel_id` 为空，`platform_id` 说明是哪个平台；`payment_status='paid'`（钱在平台那里） | |

为什么佣金不进订单金额：订单金额（`total`、优惠、税）回答“顾客付了多少、店铺卖了多少”，验算的 D、R 规则都围绕它；佣金是店铺付给平台的**成本**，和本店卖给顾客的价无关，放在单独一张表，对账页用它算到账。这和 Toast、Square 把平台单记成一种付款类型、费用另算是同一个思路。

### 9.2 引擎里的位置（PRICING_CHECK.md 第 2.1 节阶段顺序不变）

单品 → 整单（**商家出资的平台优惠**在这里，固定金额，按各道菜剩下的钱分摊）→ 结账打折（平台单没有）→ 配送费（没有）→ 服务费（0）/ 税（含税）→ 平台出资（**平台出资的平台优惠**，已有阶段）→ 抹零（平台单没有）。

也就是说引擎不加新阶段，只在规则表 `rules.go` 加一个“固定金额、商家出资、不看门槛”的整单项（`platform_merchant_promo`），平台出资沿用现有的平台出资调整。

### 9.3 平台价怎么定

下单时：`平台价 = 菜品单独设的平台价`，没有就 `取整(店内价 × (1 + 加价比例))`；规格加价、加料加价同样乘加价比例再取整。算好后存进 `order_items`，之后改单（加单、退菜）只读订单上的快照（店铺之后改加价比例不影响老单），和 PRICING_CHECK.md 第 5 节“只读快照”一致。加价比例和取整方式也存在订单上（`orders.platform_markup_bp`、`platform_rounding`），给加单用。

### 9.4 商城单和网店单的钱

两类单的算法和现在顾客自助单**完全一样**（外卖活动、店铺券、包装费、配送费、税，`loadMoney → choosePromo → priceMoney → saveMoney`），只差一处：**平台券**（河马平台出钱发给顾客的券）。

**待确认 7** 推荐：平台券**只能用在商城订单**，网店订单只能用本店的券。理由：平台券是平台花钱给商城引流的，商家自己的网店不在商城里；网店页面本来也不显示平台的东西。结算页在网店模式下不列平台券。

### 9.5 对账页（效果图 06）

- **收款汇总**：付款类型多一行“外卖平台”，下面按平台分，金额是商家应收。**不进钱箱应有**（不是现金）。
- 新一块 **“平台订单”**：按平台一行：单数、平台价营业额、商家出资优惠、平台出资优惠、商家应收、佣金、平台扣款（退款）、预计到账；再加“实际到账”（店员照平台结算单填，按平台 + 日期段存一条 `platform_payouts`）和“差额”。点一行展开逐单明细，可导出。
- **让利记录**：多一类“平台优惠（商家出资）”；外卖平台出资的不算店铺让利，单列“平台补贴”。
- **营业额按类型**：堂食（店员 / 扫码）、代客、平台（各平台）、商城、网店分开列，商家能看出多少生意是商城带来的、多少是自己的链接来的。

**待确认 12：平台单的税怎么算？** 推荐**一律按含税算**，因为平台菜单上的价就是顾客最后付的价。

**待确认 13：佣金按什么算？** 推荐默认“商家出资优惠之后的菜品金额 × 佣金比例”，平台后台每个平台可改成“按菜品原价”，店员在单上也能手改（要写原因）。

### 10.3 手算样例 S9（实现时写进 `TestPricingCheckSamples`，数字是手算的）

门店同第 4 节样例（税 12%），平台单一律含税；Grab 加价 20%，取整到 1。

- 平台价：鸡 169.00 × 1.2 = 202.80 → 取整 **203.00**；水 30.00 × 1.2 = **36.00**
- 菜：鸡 203.00 × 2 = 406.00，水 36.00；平台价小计 **442.00**；无包装费、服务费、配送费
- 商家出资优惠 50.00（整单，按剩下的钱分摊）：鸡 50 × 406/442 = 45.9276，水 4.0724 → 45.92 + 4.07 差 1 分，鸡小数大 → **45.93 / 4.07**；净额 360.07 / 31.93 = 392.00
- 含税：税 = 392.00 × 12/112 = **42.00**；分摊 38.5789 / 3.4211 → 38.57 + 3.42 差 1 分给鸡 → **38.58 / 3.42**
- 平台出资优惠 20.00（税后，不改税）：顾客实付 = 442.00 − 50.00 − 20.00 = **372.00**
- 商家应收 = 372.00 + 20.00 = **392.00**
- 佣金 30% × 商家优惠后菜品金额 392.00 = **117.60**；预计到账 = 392.00 − 117.60 = **274.40**

S9 补一条退菜：店铺原因退一瓶水（还没做）→ 按现有店铺原因规则，商家出资优惠按剩下菜品比例保留：50.00 × 406/442 = 45.93（就是鸡原来分到的那份），平台出资 20.00 不变（固定金额，封顶到剩余）；实付 = 406.00 − 45.93 − 20.00 = **340.07**；应收 360.07；税 = 360.07 × 12/112 = 38.5789 → **38.58**；佣金 30% × 360.07 = 108.021 → **108.02**；预计到账 **252.05**。（实现时如果现有店铺原因退菜对“固定金额”优惠的保留规则和这里不同，以现有规则为准并先告诉 brian。）

## 14. 实现说明

- 第一批（订单类型和订单号）：新单号直接写进原来的 `orders.public_no`，订单列表、后厨、顾客页面不用改就显示新单号；老订单单号不变。`orders.order_type`、`dine_source`、`biz_date` 是新列，计数放在新表 `order_counters`（按店、类型、营业日/日期）。
- 顾客自己下的单按下单网址区分：商城 `Hippo-`，店铺专属页面 `Online-`（第二批）。
- 代客单号是商家代码 + 6 位会员号，同一会员同一营业日第二单起加 `-2`、`-3`；取餐码用会员号后 4 位。商家代码没填时按店铺网址自动生成，可以在“设置 → 订单编号”修改。
- 第二批（店铺专属页面和域名）：
  - 店铺号 `branches.store_no` 从 10001 起，老店按开店顺序补上。专属页面网址的主域名在平台后台“密钥设置 → 店铺专属页面”里填（或 `.env` 的 `STORE_SITE_DOMAIN`），没填时商家的链接还是老的 `/s/店铺`，打开后进入商城里的本店。本机开发用 `http://店铺号.localhost:端口` 就能看到专属页面。
  - 后端按请求的域名认店（`GET /api/site`）：`店铺号.主域名`、`店铺号.localhost`、`branch_domains` 里已生效的域名是网店模式，其他都是商城。报价和下单时后端按域名定 `own_site`，前端传什么都不算；商城的报价拿到专属页面下单会被要求重新确认。
  - 网店模式：根路径就是本店点餐页（结算在 `/checkout`），没有返回商城和收藏按钮，页底“由河马点餐系统提供”不带链接；底部导航“点餐 / 订单 / 我的”；“我的”只剩本店的券、收货地址、和本店的聊天、个人资料，订单列表只列本店的单。商城的页面（`/mall`、收藏、钱包、平台客服、入驻申请等）在专属页面打开会回到本店首页。
  - 商城里的店铺页改到 `/mall/s/:slug`；老链接 `/s/:slug` 在设了主域名时跳到专属页面，否则进入商城里的本店。商城店铺页加了 canonical 指向专属页面。
  - 商家后台“店铺装修 → 店铺链接”：专属网址、二维码、绑定自有域名（CNAME 指向 `店铺号.主域名`，worker 每几分钟检查一次，生效后每小时复查）、申请代买。平台后台“域名申请”：处理代买（待处理 / 已报价 / 已购买 / 已生效 / 已拒绝），也可以手动改自有域名的状态。
  - Caddy on-demand TLS：`GET /internal/tls-ask?domain=` 只对店铺页面的网址回 200，见 DEPLOY.md 5.1 节。
  - 平台券只限商城单：网店模式下顾客的券包不列平台券，点名要也不用；验算规则 D12、第 17 格 `TestMallVsWebOrder`。
