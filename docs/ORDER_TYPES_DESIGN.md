## 0. 结论先看

1. 订单只分 **4 类**：**堂食订单**、**代客下单**、**平台订单**（下分 Grab、foodpanda 和管理员加的各国平台）、**线上订单**（顾客自己在点餐页 / 商城下的外卖和自取，brian 没提到，见第 3 节待确认 1，推荐单独一类）。
2. 订单号按类型：
   - 堂食 `DineIn-001`，每天按商家设的重置时间（默认凌晨 4:00）从 001 重来；
   - 代客 `YPX000123` = 商家代码 + 会员号，同一会员当天第二单起加 `-2`、`-3`；
   - 平台 `Grab GF-123` = 平台名 + 平台自己的单号（店员照平台平板抄）；
   - 线上 `Online-001`，和堂食一样每天重置。
3. 老订单**不改号**：只补“订单类型”，原来的 `W1126-001`、`D1126-001` 照旧显示和搜索，顾客手里的链接都不失效。
4. 平台订单按**平台价**点菜（店铺给每个平台设加价比例，个别菜可单独定价），**不套本店的活动、券、服务费、配送费**；平台上的优惠分“商家出资”和“平台出资”两种录入，佣金单独记，不算进订单金额。
5. 平台订单**不进钱箱**，对账页单独一块，按平台列营业额、优惠、佣金、预计到账，店员可以照平台结算单填实际到账、看差额。
6. 涉及订单金额，按 `docs/PRICING_CHECK.md` 验算：新增手算样例 S9、场景表第 16 格、两条新规则 D10、D11（见第 9 节）。

## 2. 业内怎么做

| 系统 | 做法 | 我们借鉴什么 |
|---|---|---|
| **Toast**（美国） | 每个外卖平台接进来都有自己的“用餐方式”（Dining Option）和“付款类型”，报表能按平台拆开；接入前店员要在平台平板上看单、再在 POS 里手动录一遍 | 平台 = 一种订单类型 + 一种付款类型，报表按平台分 |
| **Square for Restaurants** | 外卖平台的单进交易记录“只作记录”，付款和退款由平台管；交易报表按“来源”（Source）筛选；可以把渠道映射到“营收中心”分开看营业额 | 平台单不进钱箱、不走本店收款；对账按来源拆 |
| **Loyverse**（东南亚小店常用） | 用餐方式（堂食、外带、外卖、自定义名字）可以随便加，每张单存下所选方式，不同方式可以用不同税；Grab 用插件 GrabConnect 把单拉进来变成收据。平台价一般做法是另建一份“Grab 价”的菜（Sapaad 等也这么教） | 平台由后台自定义添加；平台价不另建菜，用“加价比例 + 个别菜单独价” |
| **Otter、Deliverect、Klikit**（聚合接单） | 把各平台的单汇到一块屏，自动打印进后厨；支持按渠道设不同价格（Otter 的 advanced pricing） | 所有平台的单进同一个后厨流程；按平台定价 |
| **GrabFood 商家端** | 每单有长单号（Booking ID）和短单号（如 `GF-123`），小票上两个都印，短单号末尾字母表示单的类型；佣金按订单金额收，各国大约 15%–30%；商家出资和平台出资的优惠分开列；“净销售额”= 打到商家钱包的钱 | 平台单号存短单号；优惠分两种出资；佣金单独记；预计到账 |
| **foodpanda 商家端** | 有多种佣金套餐，费率注册时定；结算单里有佣金、“费用和调整”、税等扣项 | 佣金费率按店可改；“其他扣费”留一栏 |
| **美团收银 / 客如云** | 美团外卖、饿了么的单自动接到收银机并打印后厨；订单按“渠道”（堂食、自营外卖、美团、饿了么）分；菜品可按渠道设价格（渠道价）；对账按渠道看营业额、平台补贴、佣金和到账 | 渠道价、按渠道对账；平台补贴和商家补贴分开 |
| **餐厅通用的取餐号** | 堂食 / 快餐每天（营业日）从 1 开始的流水号；营业日在凌晨某个时间切换，不是零点，深夜营业的店不会半夜断号 | 堂食、线上号每日重置，重置时间由商家设 |

参考：[Toast Grubhub 接入](https://support.toasttab.com/en/article/Grubhub-Integration-Overview)、[Toast 外卖平台佣金](https://pos.toasttab.com/blog/food-delivery-fees-and-commissions)、[Square 外卖接入](https://squareup.com/help/au/en/article/6649)、[Loyverse 用餐方式](https://help.loyverse.com/help/dining-options)、[Loyverse GrabConnect](https://loyverse.com/marketplace/grab-connect)、[Sapaad：堂食和 GrabFood 不同价](https://www-dr.sapaad.com/knowledge-base/how-can-i-have-different-menu-prices-for-dine-in-and-grabfood/)、[Grab 佣金说明](https://www.grab.com/th/en/blog/askgrab-merchant-commission/)、[GrabMerchant 手册](https://hodor-assets.grab.com/attachments/merchant/en-ph/articles/22150/rc-upload-1714107664018-2-GrabMerchant%20Handbook.pdf)、[foodpanda 商家](https://partner.foodpanda.sg)、[Otter + Square](https://helpdesk.tryotter.com/hc/en-us/articles/18755245669523-Otter-Square-Integration-Guide)。客如云、美团收银的帮助中心没搜到公开文档，上表写的是这类收银系统的通用做法。

结论：**手动录平台单**是接口没开通前业内最普遍的过渡做法；关键是三件事做对：平台单有自己的类型和付款类型、按平台价、对账时佣金和到账单独算。以后接通 Grab/foodpanda 接口，自动进来的单也落在同一个“平台订单”类型里，页面和对账都不用改。

## 3. 四类订单

| 类型 | 代码 `order_type` | 包括哪些单 | 订单号 | 从哪来 |
|---|---|---|---|---|
| 堂食订单 | `dine_in` | 店员开台点菜、顾客扫桌上二维码、桌上平板 | `DineIn-001` | 后台“堂食下单”、扫码点餐 |
| 代客下单 | `staff` | 店员替顾客下的外卖、自取单（微信、电话、LINE 等发来的） | `YPX000123` | 后台“外卖下单” |
| 平台订单 | `platform` | Grab、foodpanda 等外卖平台上的单，店员手动录入（以后接口自动进） | `Grab GF-123` | 后台新页面“平台下单” |
| 线上订单 | `online` | 顾客自己在点餐页、商城下的外卖、自取单 | `Online-001` | 点餐页、商城 |

**待确认 1：顾客自己下的单归哪类？** brian 没提到这一类。三个选项：

- A（推荐）单独一类“线上订单”，`Online-001` 每日重置。理由：这类单没有会员号（顾客用手机号登录，不在按店会员表里），套不进“商家代码+会员号”；它也不是第三方平台的单，不收佣金、走本店收款；对账、活动（外卖活动、券）规则也和代客单一样但来源不同，单独一类最清楚。
- B 归进“代客下单”，号码用商家代码 + 顾客手机后 4 位。缺点：名字不符，手机号可能重复。
- C 归进“平台订单”，把“本店点餐页”当成一个平台。缺点：会被算佣金和平台价，对账会乱。

`service_type`（外卖 / 自取 / 堂食）保留，它说的是**怎么交给顾客**，和**订单类型**是两件事：代客单、线上单可以是外卖或自取；平台单默认“平台骑手取餐”（见第 6.4 节）。

`channel` 列保留不删（很多查询在用），新加 `order_type` 是以后所有页面、筛选、报表看的字段。

## 4. 订单号

### 4.1 每一类怎么编

| 类型 | 规则 | 例子 | 每日重置 |
|---|---|---|---|
| 堂食 | `DineIn-` + 当天第几张堂食单，至少 3 位，满 999 自动 4 位 | `DineIn-001`、`DineIn-1024` | 是，按商家设的重置时间 |
| 代客 | 商家代码 + 会员号（6 位，补零）；同一会员同一营业日第二单起加 `-2` | `YPX000123`、`YPX000123-2` | 不重置（会员号本身固定），只有后缀每日从头 |
| 平台 | 平台显示名 + 平台短单号（店员照平台平板或小票抄） | `Grab GF-123`、`foodpanda #a8kx-21qe` | 不由我们编 |
| 线上 | `Online-` + 当天第几张线上单 | `Online-007` | 是 |

- 每一类**单独一个序号**：今天第 5 张堂食单就是 `DineIn-005`，不会被外卖单插号。序号存在新表 `order_counters (branch_id, kind, biz_date, seq)`，同一事务里 `INSERT … ON CONFLICT DO UPDATE SET seq = seq + 1 RETURNING seq` 取号，并发下不会重号。
- **营业日**：店铺设置“每日重置时间”（默认 04:00，可选 00:00–08:00）。凌晨 1 点的单仍算前一个营业日，序号接着排。门店时区照旧。
- **取餐号 / 叫号**：`pickup_code` 改成“号码里的数字部分”：堂食、线上是三位序号，代客单是会员号后 4 位，平台单是平台短单号。排队叫号屏、取餐屏、骑手端显示完整订单号（屏幕放得下）。
- `DineIn-` 和 `Online-` 两个前缀**全球统一，不翻译**（小票、叫号屏、截图对得上，各语言店员都认得）。页面上的类型名“堂食订单 / 平台订单”照常多语言。

**待确认 2：代客单号怎么拼？** brian 的例子 `YPX05112`，我理解为商家代码 `YPX` + 会员号。但现在会员号至少 6 位（`000001` 起），所以推荐 `YPX000123` 这样“代码 + 6 位会员号”，不加分隔符；如果 brian 的意思是商家代码本身就是 `YPX05112`，那号码就是 `YPX05112-000123`，请 brian 说一下是哪种。

**待确认 3：同一会员同一天下第二单怎么办？** 推荐加 `-2`、`-3` 后缀（`YPX000123-2`），后厨和骑手能分清是两张单。不加后缀的话两张单号码一样，派单和叫号会混。

### 4.2 商家代码

- 店铺设置“订单编号”一栏：商家代码，2–8 位大写字母或数字（如 `YPX`），**全平台唯一**（以后平台后台按代码搜店，会员号也能看出是哪家店的）。
- 新店默认用店铺网址名（slug）的前 3 个字母自动生成一个不重复的，店主可改。改代码只影响以后的单，老单号不变。
- 平台后台“商户管理”能看到、能改每家店的代码。

**待确认 4：商家代码是按店（分店）还是按商家？** 推荐**按店**（`branches.store_code`）：会员是按店的，同一商家两家分店各有一套会员号，按商家代码会出现两家店都有 `YPX000123`。

### 4.3 数据库里存什么

| 列 | 说明 |
|---|---|
| `orders.order_type` | `dine_in` / `staff` / `platform` / `online`，非空，有 CHECK |
| `orders.display_no` | 上面规则拼出来的订单号，所有页面、小票、叫号屏、搜索都用它 |
| `orders.biz_date` | 营业日，按重置时间算；日报、对账以后也可以按它分天 |
| `orders.platform_id`、`orders.platform_order_no` | 只有平台单有；`(branch_id, platform_id, platform_order_no)` 7 天内重复会提示“这张平台单已经录过” |
| `public_no` | **保留**，继续按现在的规则生成（`W1126-001`），作为内部流水号：顾客订单链接、旧的搜索、聊天里引用订单都还能用；页面上只在订单详情小字显示“流水号” |

### 4.4 老订单迁移

迁移只**补字段不改号**，跑一次 SQL，几秒钟：

1. `order_type`：`channel='dine_in'` 或 `service_type='dine_in'` → `dine_in`；`channel='staff'` → `staff`；其余（`web`）→ `online`。没有老的平台单。
2. `display_no` = 原来的 `public_no`（`W1126-001`、`D1126-001`），顾客、店员手里的老截图都对得上。
3. `biz_date` = 下单时间按门店时区的日期（老单没有重置时间概念，就按零点）。
4. `branches.store_code`：按 4.2 自动生成；`branches.day_reset_time` 默认 `04:00`。
5. 新的 `order_counters` 从 0 开始；上线当天的新单从 `DineIn-001`、`Online-001` 起。
6. `down` 迁移删掉新列和新表，老数据不受影响。

迁移不碰任何金额列，`make pricing-check-db` 前后结果应一致（见第 9 节）。

## 5. 外卖平台（平台后台管理）

平台后台新页面 **“外卖平台”** `/admin/platforms`（效果图 05），放在“支付方式”旁边，管理员维护：

| 字段 | 说明 |
|---|---|
| 名称 | 多语言（Grab、foodpanda、ShopeeFood、LINE MAN、GoFood、Deliveroo、Uber Eats……） |
| 编号前缀 | 平台单号前显示的短名，如 `Grab`、`FP`、`Shopee`；平台内唯一 |
| 国家 | 可多选；店铺只能开通本国的平台 |
| 标志、颜色 | 订单列表、后厨屏上的平台标签 |
| 单号提示 | 店员录单时输入框的提示，如“平台平板上的短单号，如 GF-123”；可选格式校验（正则），不符合只提示不拦 |
| 默认佣金 | 比例（如 30%），可选“按商家优惠后金额 / 按菜品原价”计；店铺可以改成自己合同的费率 |
| 默认加价 | 平台价比店内价高多少（如 0%），店铺可改 |
| 启用 / 排序 | |

预置：Grab（菲律宾、新加坡、马来西亚、泰国、越南、印尼、缅甸、柬埔寨）、foodpanda（菲律宾、新加坡、马来西亚、泰国、台湾、柬埔寨、缅甸、老挝），其他国家的平台由管理员自己加。费率默认值管理员按当地情况填，代码里不写死。

### 店铺开通平台（效果图 04）

店铺设置“订单编号和外卖平台”一栏：勾选本店上了哪些平台；每个平台可填：本店在平台上的店铺 ID（对账用）、佣金比例（默认取平台的）、平台价加价比例和取整方式（不取整 / 取整到 1 / 取整到 5 / 取整到 10，默认取整到 1）。

菜单页每道菜多一列“平台价”（展开后每个开通的平台一格）：空着就是“店内价 × (1 + 加价)”再取整；填了就用填的。Excel 导入导出多几列 `平台价:Grab` 这样的列（菜单导入方案的列规则照旧）。

## 6. 平台下单页（效果图 01、02）

### 6.1 入口和权限

- 后台左侧“点单”下加第三个子页 **“平台下单”** `/merchant/order/platform`，在“堂食下单”“外卖下单”下面。本店一个平台都没开通时不显示。
- 权限新加 `order.platform`（店主、经理、接单员默认有）。店主在员工权限里可以关掉。

### 6.2 页面布局（和“外卖下单”同一套，键盘优先）

左边大表格是点的菜（编号、菜名、数量、**平台价**、小计、口味/加料、操作），右边是表单，从上到下：

1. **平台**：本店开通的平台大按钮（带标志和颜色），默认上次用的那个。
2. **平台单号** *（必填）：照平台平板上的短单号抄，录过的单号会红字提示“已录过：12:03 录入，查看”。
3. **取餐方式**：平台骑手取餐（默认）/ 顾客到店自取（平台自取单）。**预计取餐时间**：尽快 / 选时间（预约单）。
4. **顾客称呼**（选填，平台一般只给名字）；**订单备注**（照抄平台上的顾客备注，打在后厨小票上）。
5. **选择商品**：输编号或菜名，回车加入；价格自动按这个平台的平台价；规格、加料、口味模板和外卖下单一样。
6. **平台优惠**：两栏金额，“商家出资”（店铺自己在平台上报名的活动）和“平台出资”（平台补贴的券、免配送费不算，平台自己收配送费）；都可以留空。
7. **核对金额**：店员输入平台平板上显示的“订单金额”（顾客实付或商家应收，按平台 `核对口径` 设置，默认“菜品小计”），和系统算的不一样时标黄“差 ₱6，可能有菜价没同步”，可以点“仍然下单”。
8. **佣金和预计到账**（只读，可点开改佣金金额，要写原因）：佣金 = 佣金比例 × 基数；预计到账 = 商家应收 − 佣金 − 其他扣费。
9. **确认下单**：直接算“已接单”，进后厨、烹饪进度，打印后厨小票。不发短信、不给顾客链接（顾客在平台上看进度）。

左下深色底栏：数量、平台价小计、商家出资优惠、平台出资优惠、顾客实付、佣金、预计到账。

手机版：一栏，平台按钮横排可滑动，底部固定“确认下单 · Grab GF-123 · ₱649”。

### 6.3 不做的事

- 不套本店的外卖活动、堂食活动、店铺券、平台券（这些是本店点餐页的优惠，顾客没在本店下单）。
- 不收本店服务费、配送费；包装费默认 0，可填（有的平台让商家另收包装费）。
- 不能用“结账优惠”（打折、抹零、改实收）——平台单金额以平台为准。录错了就改单或取消重录。
- 没有会员、没有地址（平台骑手送，我们不派骑手）。

### 6.4 下单之后

- 状态：已接单 → 备餐中 → 已备好（等平台骑手）→ **平台骑手已取走**。“已取走”由店员点，或骑手取餐时扫后厨小票上的二维码（以后做）。顾客自取的平台单同样到“已取走”结束。
- 加单：平台上顾客改单很少，允许在“已取走”之前加菜（走现有加单流程，按平台价）。
- 退菜：在“已取走”之前可以退菜（走现有退菜流程，金额按平台价重算）。
- 取消：平台上取消了，店员在订单详情点“平台已取消”，填原因；已经做了的菜按现有退菜规则记损耗。
- 退款：平台单的退款平台自己处理，我们只**记录**：订单详情“记录平台扣款”，填金额和原因（如顾客投诉漏菜，平台从结算里扣了 ₱36），记进 `order_refunds`，付款方式 `platform`，进对账。

**待确认 5：平台单要不要支持“商家自配送”（平台单由本店骑手送）？** 推荐**首版不做**：平台单都是平台骑手取或顾客自取。需要时再加，到时候平台单也填地址、走派单。

## 8. 金额怎么记

### 8.1 一张平台单的钱

| 项 | 记在哪里 | 谁的钱 |
|---|---|---|
| 菜品平台价 | `order_items.unit_price`（下单时的快照） | |
| 商家出资优惠 | `order_discounts` 一行，`kind='platform_merchant_promo'`，`funded_by='merchant'`，规则快照存平台和金额 | 店铺承担 |
| 平台出资优惠 | `order_discounts` 一行，`kind='platform_promo'`，`funded_by='platform'`；走引擎现有的“平台出资”阶段（税后） | 外卖平台承担，不减店铺应收 |
| 包装费 | `orders.packaging_fee`（店员填） | |
| 税 | 按店铺税率，**平台单一律按含税算**（平台上的价就是顾客付的价），快照存在订单 | |
| 服务费、配送费 | 都是 0 | |
| 顾客实付 | `orders.total`（= 平台价小计 + 包装费 − 商家出资 − 平台出资） | |
| 商家应收 | `total + platform_subsidy`（和本店平台券同一个意思） | |
| 佣金、其他扣费 | **新表 `order_platform_fees`**（订单、类型 `commission`/`other`、比例、基数、金额、是否手改、原因），**不进订单金额** | 店铺付给平台 |
| 预计到账 | 商家应收 − 佣金 − 其他扣费（算出来显示，不单独存） | |
| 付款 | `pay_type='platform'`，`pay_channel_id` 为空，`platform_id` 说明是哪个平台；`payment_status='paid'`（钱在平台那里） | |

为什么佣金不进订单金额：订单金额（`total`、优惠、税）回答“顾客付了多少、店铺卖了多少”，验算的 D、R 规则都围绕它；佣金是店铺付给平台的**成本**，和本店卖给顾客的价无关，放在单独一张表，对账页用它算到账。这和 Toast、Square 把平台单记成一种付款类型、费用另算是同一个思路。

### 8.2 引擎里的位置（PRICING_CHECK.md 第 2.1 节阶段顺序不变）

单品 → 整单（**商家出资的平台优惠**在这里，固定金额，按各道菜剩下的钱分摊）→ 结账打折（平台单没有）→ 配送费（没有）→ 服务费（0）/ 税（含税）→ 平台出资（**平台出资的平台优惠**，已有阶段）→ 抹零（平台单没有）。

也就是说引擎不加新阶段，只在规则表 `rules.go` 加一个“固定金额、商家出资、不看门槛”的整单项（`platform_merchant_promo`），平台出资沿用现有的平台出资调整。

### 8.3 平台价怎么定

下单时：`平台价 = 菜品单独设的平台价`，没有就 `取整(店内价 × (1 + 加价比例))`；规格加价、加料加价同样乘加价比例再取整。算好后存进 `order_items`，之后改单（加单、退菜）只读订单上的快照（店铺之后改加价比例不影响老单），和 PRICING_CHECK.md 第 5 节“只读快照”一致。加价比例和取整方式也存在订单上（`orders.platform_markup_bp`、`platform_rounding`），给加单用。

### 8.4 对账页（效果图 06）

- **收款汇总**：付款类型多一行“外卖平台”，下面按平台分（Grab、foodpanda），金额是商家应收。**不进钱箱应有**（不是现金）。
- 新一块 **“平台订单”**：按平台一行，列：单数、平台价营业额、商家出资优惠、平台出资优惠、商家应收、佣金、其他扣费、平台扣款（退款）、预计到账；再加两列“实际到账”（店员照平台结算单填，按平台 + 日期段存一条 `platform_payouts` 记录）和“差额”。点一行展开逐单明细（订单号、平台单号、应收、佣金、预计到账），可导出。
- **让利记录**：多一类“平台优惠（商家出资）”，平台出资的不算店铺让利，单列“平台补贴”。
- 营业额报表按订单类型分：堂食 / 代客 / 平台（各平台）/ 线上。

**待确认 6：平台单的税怎么算？** 推荐**一律按含税算**（不管店铺设置是含税还是不含税），因为平台菜单上的价就是顾客最后付的价，平台不会另加我们的税。另一个选项是跟店铺设置走，那不含税的店会在平台价上再加税，和平台上的数对不上。

**待确认 7：佣金按什么算？** 推荐默认“商家出资优惠之后的菜品金额 × 佣金比例”（Grab、foodpanda 大多这么收），平台后台每个平台可改成“按菜品原价”，店员在单上也能手改（要写原因）。

### 9.3 手算样例 S9（实现时写进 `TestPricingCheckSamples`，数字是手算的）

门店同第 4 节样例（税 12%），平台单一律含税；Grab 加价 20%，取整到 1。

- 平台价：鸡 169.00 × 1.2 = 202.80 → 取整 **203.00**；水 30.00 × 1.2 = **36.00**
- 菜：鸡 203.00 × 2 = 406.00，水 36.00；平台价小计 **442.00**；无包装费、服务费、配送费
- 商家出资优惠 50.00（整单，按剩下的钱分摊）：鸡 50 × 406/442 = 45.9276，水 4.0724 → 45.92 + 4.07 差 1 分，鸡小数大 → **45.93 / 4.07**；净额 360.07 / 31.93 = 392.00
- 含税：税 = 392.00 × 12/112 = **42.00**；分摊 38.5789 / 3.4211 → 38.57 + 3.42 差 1 分给鸡 → **38.58 / 3.42**
- 平台出资优惠 20.00（税后，不改税）：顾客实付 = 442.00 − 50.00 − 20.00 = **372.00**
- 商家应收 = 372.00 + 20.00 = **392.00**
- 佣金 30% × 商家优惠后菜品金额 392.00 = **117.60**；预计到账 = 392.00 − 117.60 = **274.40**

S9 补一条退菜：店铺原因退一瓶水（还没做）→ 按现有店铺原因规则，商家出资优惠按剩下菜品比例保留：50.00 × 406/442 = 45.93（就是鸡原来分到的那份），平台出资 20.00 不变（固定金额，封顶到剩余）；实付 = 406.00 − 45.93 − 20.00 = **340.07**；应收 360.07；税 = 360.07 × 12/112 = 38.5789 → **38.58**；佣金 30% × 360.07 = 108.021 → **108.02**；预计到账 **252.05**。（实现时如果现有店铺原因退菜对“固定金额”优惠的保留规则和这里不同，以现有规则为准并先告诉 brian。）
