# 金额计算验算方法

版本 v1.0 · 2026-11-25 · brian 定的铁规则：**凡是新增或改动涉及商品价格、订单金额的功能，都必须按本文验算，验算全部通过才能合并。**

金额架构本身见 [PRICING_REVIEW.md](PRICING_REVIEW.md)（第 5 节目标架构、第 9 节实施记录）。本文只讲“怎么证明没算错”。

---

## 0. 什么时候必须验算

改动只要碰到下面任何一项，就要走完第 5 节的流程：

- 菜品价格、规格加价、加料（topping）、套餐、会员价、时段价
- 活动：满减、折扣、免配送费、指定菜品打折、第二份优惠，以及以后新加的任何活动类型
- 优惠券：店铺券、平台券、配送费券、复购券
- 结账优惠：打折、抹零、改实收
- 服务费、包装费、配送费、税（含税 / 不含税）
- 改单：加单、退菜（顾客原因 / 店铺原因）、按菜退款、换桌、堂食加菜和结账
- 对账、账单、金额流水、退款记录、币种
- `internal/pricing/`、`internal/app/money.go`、`rules.go`、`promos.go`、`coupons.go`、`checkout.go`、`addon.go`、`voids.go`、`dinein.go`、`quote.go`、`order.go`、`members.go`（代客下单）、`reconcile.go`、`bills.go`，以及 `web/src/dishPromo.ts`
- 任何直接改 `orders` 金额列、`order_items` 分摊列、`order_discounts`、`order_refunds`、`order_money_events` 的迁移或 SQL

拿不准算不算，就当算。

## 1. 一键运行

```bash
# 需要本地 PostgreSQL；空库即可，测试会自己建表
export TEST_DATABASE_URL='postgres://USER:PASS@localhost:5432/waimai_test?sslmode=disable'
make pricing-check
```

它跑三样东西：

| 部分 | 文件 | 查什么 |
|---|---|---|
| 计价引擎 | `internal/pricing/check.go`、`check_test.go` | 第 4 节手算样例逐分相等；5 万组随机订单全部满足第 2.1 节；第 3 节的“换个写法结果不变”；验算器自己能抓出故意改错的金额 |
| 真库上的订单 | `internal/app/money_check.go`、`pricecheck_chain_test.go`、`zz_pricecheck_test.go`（以及已有的 `pricing_fix_test.go`、`zz_ledger_test.go`） | app 包所有测试建出来的每一张订单（下单、代客下单、堂食、加单、退菜、退款、结账优惠、券、菜品活动）都满足第 2.2 节，并且**重放**结果和库里存的一分不差；一张订单从下单到全部退款每一步都验 |
| 前端预估 | `web/tests/dishpromo.test.mjs` | 购物车用的 `web/src/dishPromo.ts` 和后端算法给出一样的数 |

CI（`.github/workflows/ci.yml` 的 backend）每个 PR 都会跑 `go test ./...`，上面的 Go 部分都在里面，失败就不能合并。

查线上或本地真实数据（只读，不改任何数据）：

```bash
DATABASE_URL='postgres://...' make pricing-check-db          # 最近 30 天的订单
DATABASE_URL='postgres://...' make pricing-check-db DAYS=0   # 全部订单
```

有问题的订单会逐条列出违反的规则编号（如 `R2`、`D4`），退出码为 1。上线新版本前后各跑一次，结果应该都是 `0 broken`。

## 2. 不变式（必须永远成立的规则）

金额全部是整数，单位是该币种的 1/100（36800 = 368.00）；比例是基点（1200 = 12%）；每个金额只在算出来的那一步四舍五入一次（`MulDivRound`）。

### 2.1 计价引擎（`pricing.Check`，编号 C）

| 编号 | 规则 |
|---|---|
| C1 | 每道菜的结果就是输入的那道菜；优惠 0 ≤ 优惠 ≤ 原价，净额 = 原价 − 优惠，服务费、税不为负 |
| C2 | 小计 = 各道菜原价之和 |
| C3 | 每条优惠减的钱等于它自己的规则在“这一步还剩下的钱”上算出来的数：固定金额封顶到剩余；比例 = 剩余 × 比例（有封顶就封顶）；结账打折 = 剩余 − 剩余 × 还收的比例；免配送费 = 剩余配送费。阶段顺序固定：单品 → 整单 → 结账打折 → 配送费 → 服务费/税 → 平台出资 → 抹零/改实收，和传入顺序无关 |
| C4 | 每条菜品上的优惠分摊到它覆盖的菜：分摊之和 = 它减的钱；只分给它覆盖的菜（指定菜品活动不会落到别的菜上）；每份 ≤ 那道菜还剩的钱；每份和精确比例相差不到 1 分（最大余数法）；每道菜的优惠 = 各条优惠分给它的之和 |
| C5 | 订单的菜品优惠 = 单品 + 整单各条之和；结账打折、配送费优惠、平台出资、抹零同理；各道菜优惠之和 = 菜品优惠 + 结账打折；配送费优惠 ≤ 配送费 |
| C6 | 服务费 = 各道菜净额之和 × 服务费率（折后收服务费）；各道菜服务费之和 = 服务费 |
| C7 | 税 = (菜品净额 + 包装费 + 服务费) × 税率，含税时 × 税率 /(1 + 税率)；**配送费不计税**；各道菜的税之和 ≤ 税（差额是包装费那一份），没有包装费时相等 |
| C8 | 应付 = 小计 + 包装费 + 配送费 + 服务费 − 菜品优惠 − 结账打折 − 配送费优惠（+ 税，不含税时）− 平台出资 − 抹零；平台出资不超过平台出资前的应付；应付 ≥ 0 |
| C9 | 改实收时，应付就是输入的那个数 |

### 2.2 库里的订单（`App.CheckOrderMoney`，编号 D 和 R）

| 编号 | 规则 |
|---|---|
| D1 | 订单上任何金额、任何优惠明细行都不为负 |
| D2 | 应付 = 小计 + 包装费 + 配送费 + 服务费 − 总优惠 − 结账打折 − 抹零（+ 税，不含税时） |
| D3 | 店铺出资 + 平台出资 = 总优惠 |
| D4 | 优惠明细（`order_discounts`）之和 = 总优惠（活动、菜品活动、每张券各一行） |
| D5 | 退掉的菜不再分摊任何优惠、服务费、税 |
| D6 | 金额流水（`order_money_events`）的应收变化之和 = 现在的应付（流水只追加，改或删会被数据库拒绝） |
| D7 | 退款之和 ≤ 应付（逐单检查）；把菜全部退完时正好等于应付，不多不少一分（`TestPricingCheckChain` 验） |
| D8 | 各道菜服务费之和 = 服务费；各道菜税之和 ≤ 税，没有包装费时相等 |
| D9 | 各道菜优惠之和 = 各条优惠明细的分摊之和 + 结账打折 |
| D10 | 平台单（`order_type='platform'`）：服务费、配送费、结账打折、抹零都是 0；优惠明细只有 `platform_merchant_promo`（商家在平台上的活动，店铺出资）和 `platform_promo`（平台出资，税后）两种，不带本店的活动和券（docs/ORDER_TYPES_DESIGN.md 9.1） |
| D11 | 平台单：只有一条佣金（`order_platform_fees`）；佣金的基数 = 菜品小计 − 店铺出资优惠（或按原价时 = 菜品小计）；没手改时佣金 = 基数 × 佣金比例四舍五入到分（`pricing.Commission`）；预计到账 = 应付 + 平台出资 − 佣金 − 其他扣费 ≥ 0。佣金不进订单金额 |
| D12 | 网店单（`order_type='web'`，顾客在店铺专属页面下的单）没有平台出资的优惠行，平台出资 = 0：平台券只限商城单（docs/ORDER_TYPES_DESIGN.md 9.4） |
| R1 | **重放**：只用订单自己存的东西（下单时的税率/服务费率/包装费/配送费快照、还在的菜、菜品活动的规则快照、活动和每张券当时减的钱、结账打折比例、抹零）重新交给引擎算一遍，结果满足 2.1 节全部规则 |
| R2 | 重放出来的小计、服务费、税、总优惠、店铺/平台出资、结账打折、抹零、应付和库里存的**一分不差** |
| R3 | 重放出来每道菜的优惠、服务费、税分摊和 `order_items` 里存的一分不差 |

R 这一组是最重要的：任何一条改金额的路径如果绕开了 `loadMoney → choosePromo → priceMoney → saveMoney`，或者读了门店/活动“现在”的值，或者手写了一个金额，存进去的数就会和重放对不上。

被拒单、取消的订单只验 D1、D6、D7；没有任何菜品行的订单（`make seed` 写的演示销量）不做重放。

## 4. 手算样例

每个样例的每一个数都是手算的（另用一个独立脚本复核），写在 `internal/pricing/check_test.go` 的 `TestPricingCheckSamples` 里。**这些数字不能为了让测试通过去改**；如果改动让它们变了，说明算法变了，要先在文档里写清楚为什么变、新数怎么算，并经 brian 同意。

样例门店（和 PRICING_REVIEW.md 第 3 节同一家）：税 12% 不含税、服务费 5%、包装费 10.00、配送费 69.00；鸡 169.00 × 2 = 338.00，水 30.00。小计 368.00。

分摊的规矩：按各道菜还剩的钱的比例分，先都向下取整，差的几分按小数部分从大到小一分一分补，小数一样大时先补排在前面的菜。

### S1 外卖，无优惠

- 服务费 = 368.00 × 5% = 18.40（鸡 16.90、水 1.50）
- 税基 = 368.00 + 包装 10.00 + 服务费 18.40 = 396.40；税 = 396.40 × 12% = 47.568 → **47.57**
- 税分摊（权重 鸡 354.90、水 31.50、包装 10.00）：42.5898 / 3.7802 / 1.2001 → 42.58 / 3.78 / 1.20 差 1 分，鸡小数最大 → 鸡 **42.59**、水 **3.78**
- 应付 = 368.00 + 10.00 + 69.00 + 18.40 + 47.57 = **512.97**

### S2 满减 100 + 无门槛券 50（分摊到每道菜）

- 满减 100.00：鸡 100 × 338/368 = 91.8478，水 8.1522 → 91.84 + 8.15 差 1 分给鸡 → **91.85 / 8.15**；剩 246.15 / 21.85
- 券 50.00：鸡 50 × 246.15/268.00 = 45.9235，水 4.0765 → 45.92 + 4.07 差 1 分给水 → **45.92 / 4.08**
- 每道菜优惠：鸡 137.77、水 12.23；净额 200.23 / 17.77，合计 218.00
- 服务费 = 218.00 × 5% = 10.90（鸡 10.01、水 0.89）
- 税 = (218.00 + 10.00 + 10.90) × 12% = 238.90 × 12% = 28.668 → **28.67**（鸡 25.23、水 2.24）
- 应付 = 368.00 + 10.00 + 69.00 + 10.90 − 150.00 + 28.67 = **336.57**

### S3 满减 100 + 结账 9 折 + 配送费券 20 + 平台券 10 + 抹零 0.97

（测试里故意把这几条倒着传进去，证明顺序由阶段决定，和传入顺序无关。）

- 满减同 S2：91.85 / 8.15，剩 246.15 / 21.85 = 268.00
- 9 折：268.00 − 268.00 × 90% = **26.80**；鸡 26.80 × 246.15/268 = 24.615，水 2.185，小数一样大，先补前面的鸡 → **24.62 / 2.18**
- 净额 221.53 / 19.67 = 241.20；服务费 = 12.06；税 = (241.20 + 10.00 + 12.06) × 12% = 263.26 × 12% = 31.5912 → **31.59**
- 配送费 69.00 − 20.00；平台出资前应付 = 368.00 + 10.00 + 69.00 + 12.06 − 100.00 − 26.80 − 20.00 + 31.59 = 343.85
- 平台券 10.00 → 333.85；抹零 0.97 → **332.88**
- 平台券和抹零都在税后，不改变店铺的税和服务费

### S4 堂食，含税 12%，服务费 10%，8 折活动

菜：鸡 169.00、鸡 169.00（两行）、水 30.00；小计 368.00；无包装费、无配送费。

- 8 折活动减 368.00 × 20% = **73.60**，正好分成 33.80 / 33.80 / 6.00
- 净额 294.40；服务费 = 29.44（13.52 / 13.52 / 2.40）
- 含税：税 = (294.40 + 29.44) × 12/112 = 323.84 × 12/112 = 34.697 → **34.70**（只是“其中含税”，不加到应付里）
- 税分摊（权重 148.72 / 148.72 / 26.40）：15.936 / 15.936 / 2.829 → 15.93 + 15.93 + 2.82 = 34.68 差 2 分：水小数最大先补，再补第一行鸡 → **15.94 / 15.93 / 2.83**
- 应付 = 368.00 − 73.60 + 29.44 = **323.84**

### S5 第二份半价（只落在鸡上），再满 200 减 100

- 鸡 2 份，第二份半价减 169.00 × 50% = **84.50**，只落在鸡这一行，水不分
- 剩 253.50 / 30.00 = 283.50（满减门槛按这个折后金额判断）
- 满减 100.00：鸡 100 × 253.5/283.5 = 89.418，水 10.582 → 89.41 + 10.58 差 1 分给鸡 → **89.42 / 10.58**
- 每道菜优惠：鸡 173.92、水 10.58；净额 164.08 / 19.42 = 183.50
- 服务费 = 183.50 × 5% = 9.175 → **9.18**（四舍五入，逢 5 进）
- 税 = (183.50 + 10.00 + 9.18) × 12% = 202.68 × 12% = 24.3216 → **24.32**
- 应付 = 368.00 + 10.00 + 69.00 + 9.18 − 184.50 + 24.32 = **296.00**

### S6 满减 100 后改实收 300.00

- 服务费 = 268.00 × 5% = 13.40；税 = (268.00 + 10.00 + 13.40) × 12% = 34.968 → **34.97**
- 改实收前应付 = 368.00 + 10.00 + 69.00 + 13.40 − 100.00 + 34.97 = 395.37
- 改实收 300.00：抹去 **95.37**，应付 **300.00**；税仍是 34.97（改实收不改税）

### S7 含税 12%、包装费 5.00、免配送费：配送费不计税

菜 100.00，配送费 69.00 全免，无服务费。

- 税 = (100.00 + 5.00) × 12/112 = **11.25**（配送费不在税基里）
- 应付 = 100.00 + 5.00 + 69.00 − 69.00 = **105.00**
- 税分摊（权重 菜 100.00、包装 5.00）：10.714 / 0.536 → 10.71 + 0.53 差 1 分给包装 → 菜 **10.71**（各道菜的税之和 < 税，差的就是包装那一份，见 C7）

### S8 堂食 8 折后按菜退一瓶水（真库测试 `TestPricingFixDineRefundPromo`）

PRICING_REVIEW.md 问题 1 的门店：含税 12%、服务费 5%。鸡 169.00 × 2 + 水 30.00，8 折，实付 **309.12**（= 368.00 − 73.60 + 服务费 14.72）。

## 5. 改动流程（每个涉及金额的 PR 都要做）

1. **先想清楚算法**：新规则落在第 2.1 节哪个阶段？谁出钱（店铺 / 平台）？和现有活动、券能不能叠加？退菜、退款、加单时怎么变？拿不准的业务规则先问 brian，不要自己定。
2. **只走一条路**：所有算钱的地方都是 `loadMoney → choosePromo → priceMoney → saveMoney`（`internal/app/money.go`），引擎是 `internal/pricing.Price`。新活动 = 规则表 `rules.go` 加一项，或引擎加一种 `Adjustment`；不要在别处再写一份“这张单该收多少”。
3. **只读快照**：改单只读订单自己存的费率、活动规则、券金额，不读门店或活动表“现在”的值。新规则要在 `order_discounts.rule` 或订单列上存下单时的快照。
4. **写手算样例**：在 `TestPricingCheckSamples` 加至少一个手算样例（数字手算，最好另用脚本复核），并把算法写进本文第 4 节。
5. **写场景测试**：按第 3 节找到对应格子，在 app 包里建真实订单，每一步调用 `checked(t, "步骤", orderID)`；新的改单路径要加进 `TestPricingCheckChain` 或另写一条链。如果引擎加了新阶段或新规则，同步更新 `pricing.Check`（C 规则）和本文第 2 节。
6. **前端预估要一致**：前端只显示后端算好的金额；唯一的例外是购物车预估（`web/src/dishPromo.ts`），改了后端算法就要同步改它和 `web/tests/dishpromo.test.mjs`。
7. **跑验算**：`make pricing-check` 全部通过；有真实数据时再跑 `make pricing-check-db`。
8. **PR 描述里写“金额验算”一节**：改了哪条规则、落在第 3 节哪几格、新增了哪些样例和测试、`make pricing-check` 的结果。
9. **验算发现现有算法本身有错（不是这次改动引起的）时，先停下告诉 brian**，说清楚哪张单、哪条规则、错多少钱，等 brian 决定再改。不要改断言去凑现有结果，也不要顺手“修”掉。

### 不允许

- 用浮点数算钱，或者在多个地方各自四舍五入再相加
- 绕开 `saveMoney` 直接 `UPDATE orders` 的金额列、`order_items` 的分摊列、`order_discounts`
- 修改或删除 `order_money_events`（只追加；更正用新的一条）
- 改单时读门店现在的税率、服务费率，或活动现在的类型、门槛、面额
- 为了让测试通过去改第 4 节样例的数字，或跳过、删掉验算测试

## 6. 已知的局限（改到这些地方时要特别小心）

- **币种小数位**：所有币种都按 1/100 存，日元、越南盾、韩元等会出现“半日元”（PRICING_REVIEW.md 问题 6，第 5 步，还没做）。做这一步时要给第 4 节加无小数币种的样例。
- **税的分摊**：包装费那一份税不落在任何一道菜上，所以 C7、D8 只能要求“各道菜税之和 ≤ 税”。按菜退款时这部分不退。
- **配送费**：店员改过的配送费没有单独记原区域运费；配送费不计税。
- **对账和账单**仍按订单和退款表汇总，流水用来核对；改对账逻辑时要同时跑 `TestReconciliation`、`TestBills` 和 D6。
