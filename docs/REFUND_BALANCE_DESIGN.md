# 退款到余额（店铺余额 + 平台余额）设计方案 v0.1（2026-11-27，待 brian 确认）

> 需求（brian 2026-11-27）：商家新增退款功能，分两种：
> 1. **商家退款**：退款退到顾客余额，这个余额只能在该商家用。
> 2. **平台退款（分国家）**：通用余额，在指定国家内可以在任意商家消费。
>
> 余额非常重要，要多考虑安全和漏洞防御。

这份文档只是方案，不改代码。需要你决定的问题集中在**第 13 节**，每题都给了推荐。

---

## 0. 结论先看

1. **余额是“付款方式”，不是“优惠”。** 用余额付款不改订单金额、不改满减门槛、不改税，计价引擎（`pricing.Price`）一行不动。订单多一张“付款明细”：店铺余额付了多少、平台余额付了多少、剩下现金/到付多少。这样 PRICING_CHECK 现有的 C、D、R 规则全部照旧成立，新加一组 W 规则管余额。
2. **两种余额，两本账，互不相通：**
   - **店铺余额**：一个顾客在一家**门店**一个账户（门店下所有品牌、堂食外卖都能用），币种 = 门店币种。钱是门店自己的（顾客付给门店的钱门店没退现金，记成欠顾客的），平台不垫钱、不结算。
   - **平台余额**：一个顾客在一个**国家**一个账户，币种 = 该国货币，只能在同一国家的店用。钱是平台的（平台补偿）或从责任商家扣的；顾客在别的店花掉时，平台按月补给那家店，走现有“平台券补贴结算单”。
3. **余额只进不出：** 不能充值、不能提现、不能转给别人、不能换币种、不能跨国家用。只有两个来源：退款、平台补偿。这样它在各国更容易落在“限定用途 / 退款积分”的豁免里，不变成要牌照的电子钱包（第 2 节）。
4. **复式记账 + 只追加流水：** 每一笔变动是一张“记账凭证”，至少两行，借贷相加等于 0；凭证和明细行数据库层面不能改不能删；账户余额是缓存，每天和流水对一遍。
5. **钱的上限有硬规则：** 一张单所有方式的退款合计 ≤ 顾客实付；原来用余额付的部分只能退回同一种余额；**退回现金的钱 ≤ 用现金付的钱**——这一条堵住“用平台余额买单再退现金”的套现路。
6. **分三批做**：第一批店铺余额（退款进、结算用、门店报表）；第二批平台余额（按国家开关、平台退款、补偿、结算单）；第三批风控和对账任务、代客/堂食用余额要顾客短信验证。

|---|---|---|
| “我的”页余额、奖励金 | `customer_wallet_entries`（迁移 00029），平台后台手工加减，按币种汇总，**不能付款** | 只是单式流水（一行一个数），没有对方科目、没有幂等、没有国家。改成本方案的平台余额（问题 Q8） |
| 按菜退款 | `order_refunds`（迁移 00063），`App.Refund`（`internal/app/voids.go`），只**记录**线下退了多少（现金/转账/其他），钱不经过系统 | 加一种去向：“退到店铺余额”“退到平台余额” |
| 退款上限 | PRICING_CHECK D7：一张单退款之和 ≤ 应付，全部退完正好等于应付 | 余额退款也算进去，规则不变，再加“分去向”的上限（W5、W6） |
| 金额流水 | `order_money_events`，数据库触发器写、只追加、不能改删 | 余额流水照这个做法：触发器拦改删 |
| 平台券补贴结算 | `platform_settlements`：平台按月补给门店 | 平台余额在别的店花掉，也进这张结算单，单独一列 |
| 授权码 | `approvals`（迁移 00055）：经理 6 位授权码，一次一用，几分钟有效 | 大额退到余额要授权码 |
| 权限 | `order.aftersale`（按菜退款）、`reconcile` 等 | 新增 `wallet.refund`、`wallet.view` |
| 币种 | `branches.currency` 跟随国家，订单存当时币种 | 余额账户固定币种，订单币种必须一致才能用 |
| 一店多品牌 | 品牌挂在门店下（`brands.branch_id`），会员按品牌，活动券按品牌 | 店铺余额按门店，不按品牌（问题 Q1） |
| 支付 | **线上支付还没接**：外卖货到付款、堂食到店付；平台不经手钱 | 第一版余额不涉及任何真钱进出；以后接线上支付时“退回原支付方式”另做 |

## 2. 业内怎么做（调研）

### 2.1 外卖和出行平台

| 平台 | 退款去向 | 余额能不能提现 / 有效期 |
|---|---|---|
| foodpanda 菲律宾（pandapay） | 卡付款和**货到付款**的单，退款**默认进 pandapay 余额**；卡付款的可以在 30 天内选择转回原卡 | 新加坡只能用卡充值；马来西亚余额到 RM500 上限后，退款自动退回原支付方式 |
| Uber Eats | **现金单**的退款、补偿、调整默认发 Uber Cash；卡付款的可选原路退回或 Uber Cash（Uber Cash 即时到账） | Uber 出资的补偿性 Uber Cash 可能有有效期 |
| Grab（GrabPay Credits） | 新加坡按《支付服务法》把余额当“相关款项”保管；马来西亚退款使余额超过央行上限的部分，约 3 天内退回原充值来源 | 菲律宾：余额自最后一次消费起 **1 年**有效，过期可没收；菲律宾的 GrabPay 是持牌电子钱包，可提现 |
| 美团 | 原路退回为主；原渠道异常（卡注销等）才退到美团余额 | 储值卡、礼品卡单独管理 |

可以借鉴的三点：

- **货到付款的单退到平台余额是行业常见做法**（foodpanda、Uber 都这样），因为平台手里没有可原路退的钱——我们现在正是这个情况。
- **要给顾客选择**：foodpanda 新加坡和巴基斯坦都有顾客投诉“退款被强制留在平台里花”。所以商家退到余额要有“顾客同意”的记录（第 7.2 节），平台余额的补偿部分和退款部分分开记（第 6.4 节）。
- **余额上限 + 超额退回原路**（Grab、foodpanda 马来西亚）：我们没有原路可退，所以超上限就**不允许退到余额**，改退现金/转账（第 10 节）。

### 2.2 储值的监管（重点：为什么“只进不出”）

> 下面是公开资料的整理，不是法律意见。**平台余额在任何国家开通前，都要请当地律师确认一次**（第 13 节 Q10）。

| 国家 / 地区 | 规定 | 对我们的意思 |
|---|---|---|
| 菲律宾 BSP | 2023 年 Circular 1166 取代 Circular 649。电子货币（e-money）由银行或持牌机构发行，要求流动资产覆盖余额、按面值赎回。新规里“只能在发行人处使用”**不再自动**不算电子货币；但只由“商家兼发行人”自己收的**闭环钱包**仍区别对待；能转给别人的也算电子货币 | 店铺余额 = 一家店自己的退款欠条，闭环，风险低。平台余额能在多家店用，是“有限网络”，最接近监管边界：**不能充值、不能转账、不能提现**是底线，开通前要律师确认 |
| 新加坡 MAS（《支付服务法》2019） | 只用于“限定用途电子货币”（limited purpose e-money）的服务不受该法监管；MAS 表示不打算把普通零售积分当支付服务管。二手资料提到条件是不能退款/提现、余额有上限（约 S$1,000，需核实原文） | 平台余额按“限定用途”设计：不能提现、设上限 |
| 马来西亚 BNM | 2025 年起限定用途电子货币由《Financial Services (Limited Purpose Electronic Money) Order 2024》管，豁免类别里**明确有一类是“给用户退款”**，还有“存放奖励” | 我们的两种余额正好是“退款”和“补偿奖励”两类，按该 Order 第 4 段的条件做 |
| 中国大陆 | 单用途预付卡（只在一个经营者处用）和多用途预付卡分开管；多用途要支付牌照；预付式消费纠纷里法院按实付比例算退费 | 我们没有充值（不是预付卡），店铺余额更像退款欠条；以后如果要做“充值送”，那是另一个方案、另一套合规 |

共同的底线（所有国家都满足才开）：

1. **不能充值**：余额只来自退款和补偿，顾客不能拿钱买余额。
2. **不能提现、不能转账、不能送人**：不出系统，不在顾客之间流动（转账是反洗钱的重点）。
3. **不能跨币种、跨国家**：平台余额按国家开户，各国一套账。
4. **有上限**：单个顾客的平台余额有上限，可按国家设。
5. **讲清楚是谁欠的**：店铺余额页写明“由 XX 门店承担”，平台余额写明“由河马点餐系统在 XX 国家提供”。

## 3. 两种余额对照

| | 店铺余额 | 平台余额 |
|---|---|---|
| 账户 | 顾客 × 门店（一个顾客在每家门店最多一个） | 顾客 × 国家 |
| 币种 | 门店币种 | 该国货币（例：菲律宾 PHP） |
| 能在哪用 | 只在这家门店：门店下所有品牌，堂食、外卖、自取，商城单和品牌专属页面单 | 同一国家、币种一致、开通了平台余额的所有门店；商城单和网店单都能用 |
| 谁能存进去 | 门店员工（有权限）按订单退款 | 平台管理员按订单退款，或平台补偿 |
| 钱是谁的 | 门店的：门店收了顾客的钱没退现金，记成欠顾客 | 平台的（平台出资）或从责任门店扣的（商家承担） |
| 顾客花掉时 | 门店少收现金，账上门店欠款减少，**不涉及平台** | 门店少收现金，**平台补给门店**（月结算单） |
| 有效期 | 退款来的不过期（问题 Q4） | 退款来的不过期；补偿来的 1 年（问题 Q4） |
| 提现/转账/充值 | 都不行 | 都不行 |
| 平台单（Grab、foodpanda 等） | 不适用：平台单由外卖平台自己退款 | 不适用 |

## 4. 账怎么记：复式记账

### 4.1 为什么不能沿用现在的 `customer_wallet_entries`

现在一行就是一个数：`+100`。问题：

- 看不出这 100 是谁出的（门店？平台？）——对不了账。
- 没有幂等键：网络重试会记两次。
- 没有国家、没有门店：无法实现“只能在该商家用”“分国家”。
- 余额靠 `sum()` 临时算：两张单同时扣，都读到够用，都扣成功 → 余额变负。

### 4.2 账户（`wallet_accounts`）

| 种类 `kind` | 归属 | 正常余额 | 说明 |
|---|---|---|---|
| `store_credit` | 顾客 + 门店 | ≥ 0 | 顾客的店铺余额 |
| `platform_credit` | 顾客 + 国家 | ≥ 0 | 顾客的平台余额 |
| `store_refund` | 门店 | 可负 | 门店“退到余额”累计出资（负数 = 门店欠顾客的总额） |
| `store_sales` | 门店 | 可负 | 门店用余额收的款（顾客在本店花余额） |
| `platform_fund` | 国家 | 可负 | 平台出资（补偿、平台承担的退款） |
| `merchant_charge` | 门店 | 可负 | 平台退款里商家承担、要从门店结算里扣的 |
| `platform_payable` | 门店 | 可负 | 平台欠门店的（顾客在这家店花了平台余额） |

每个账户有固定币种。顾客账户 `CHECK (balance >= 0)`，系统账户可以为负。

### 4.3 记账凭证（`wallet_journals` + `wallet_postings`）

一笔业务 = 一张凭证 + 至少两行明细，**明细相加 = 0**，全部同一币种。例子（单位：分）：

| 业务 | 明细 |
|---|---|
| 门店 A 给顾客退 60.00 到店铺余额 | `store_refund(A)` −6000，`store_credit(顾客, A)` +6000 |
| 顾客在 A 用店铺余额付 50.00 | `store_credit(顾客, A)` −5000，`store_sales(A)` +5000 |
| 平台补偿顾客 30.00（菲律宾） | `platform_fund(PH)` −3000，`platform_credit(顾客, PH)` +3000 |
| 平台退款 80.00，商家 A 承担 | `merchant_charge(A)` −8000，`platform_credit(顾客, PH)` +8000 |
| 顾客在 B 用平台余额付 100.00 | `platform_credit(顾客, PH)` −10000，`platform_payable(B)` +10000 |
| 月结算：平台付给 B 100.00 | 记在 `platform_settlements` 上（线下转账），对应凭证 `platform_payable(B)` −10000，`platform_fund(PH)` +10000 |
| 订单取消，退回刚才扣的余额 | 原凭证的反向凭证（一行行取反），不改原凭证 |

凭证上记：种类、**幂等键（唯一）**、订单号、退款号、门店、国家、币种、谁做的（员工/管理员/顾客/系统）、谁授权的、原因、时间。

### 4.4 数据库层面的保护（不靠应用代码自觉）

1. `wallet_journals`、`wallet_postings` **只追加**：触发器拦截 UPDATE/DELETE（和 `order_money_events` 一样）。写错了只能做反向凭证。
2. **借贷平衡**：延迟约束触发器（`DEFERRABLE INITIALLY DEFERRED`），事务提交时检查每张凭证明细之和 = 0、币种都等于凭证币种、每行币种等于账户币种。不平衡整个事务回滚。
3. **余额缓存**：`wallet_accounts.balance` 只能由写明细的那一个函数更新（`postJournal`），同一事务里 `balance = balance + amount`，每行明细存 `balance_after`。顾客账户 `CHECK (balance >= 0)` 兜底。
4. 应用连接数据库的账号对这两张表**只给 INSERT/SELECT**（部署教程 DEPLOY.md 补一节）。
5. 每天夜里核对（第 11 节）：缓存余额 = 明细之和；所有明细总和 = 0。

## 5. 用余额付款

### 5.1 付款明细（`order_payments`）

| 列 | 说明 |
|---|---|
| order_id | 订单 |
| tender | `store_credit` / `platform_credit` |
| amount | 这种方式付了多少（随订单金额变化可减少，见 5.4） |
| journal_id | 扣款凭证 |

订单上**不用存现金那一行**：现金/到付应收 = `orders.total − 余额付款之和`。对账、核款页里“应收现金”改成这个数（现在等于 `total`）。

### 5.2 结算页

- 顾客登录后，结算页“付款方式”卡里多一行“**余额**”：显示本店店铺余额、本国平台余额，开关默认**打开**（问题 Q6）。
- 抵扣顺序：**先店铺余额，再平台余额，剩下的到付**（店铺余额只能在这家用，先用掉对顾客更划算）。顾客可以只关掉其中一种。
- 金额由服务器在下单事务里算：`min(可用余额, 还没付的应付)`。前端传的只是“用不用”，**不传金额**，防止改包。
- 下单事务顺序：报价 → 锁顾客的余额账户（`SELECT … FOR UPDATE`，按账户 id 从小到大锁，防死锁）→ 余额不够就返回“金额有变化”让顾客重新确认（和现在活动、券的做法一样）→ 写订单 → 记扣款凭证 → 写 `order_payments`。
- **余额刚好够付全款**：订单直接 `payment_status = paid`，骑手不用收钱，配送单显示“已付，不收款”。

### 5.3 哪些单能用

| 单的类型 | 店铺余额 | 平台余额 |
|---|---|---|
| 商城单（Hippo-1） | 能 | 能 |
| 网店单（店铺/品牌专属页面） | 能 | 能（平台券不能用在网店单，但余额是顾客自己的，不是营销，所以能用；问题 Q5） |
| 堂食扫码单 | 结账时顾客自己在手机上点“用余额” | 同左 |
| 代客单、店员堂食单 | 第三批：店员发起，顾客手机收短信验证码确认后才能扣 | 同左 |
| 平台单（Grab 等） | 不能 | 不能 |

**店员不能在没有顾客确认的情况下动顾客的余额**——这是防员工盗用的关键。

### 5.4 订单金额变了怎么办

余额付款之后，订单还可能加单、退菜、结账打折、抹零。规则：**余额付的钱永远 ≤ 订单金额**。

- 金额变大（加单）：多出来的部分到付（顾客可以在加单确认页再用余额）。
- 金额变小（退菜、打折）：先减还没收的现金；现金减到 0 还不够，再把余额**按后用先退**退回（先退平台余额，再退店铺余额），每一步都是一张反向凭证。
- 订单取消、拒单、超时：余额全额自动退回（和优惠券退回一样）。
- 配送异常结束（餐已做）：余额不退，和现有券的规则一致；需要时走退款。

### 5.5 和计价引擎的关系

余额**不是**引擎里的 `Adjustment`，不进 `order_discounts`，不影响满减门槛、券、服务费、税、抹零。`loadMoney → choosePromo → priceMoney → saveMoney` 不变；余额的变动都在 `saveMoney` 之后、同一事务里，由新函数 `settleTenders(ctx, tx, orderID)` 按 5.4 调整。R1–R3 重放规则不受影响。

## 6. 退款

### 6.1 一张单的钱分三份

一张单的实付 = 店铺余额付的 + 平台余额付的 + 现金（到付/到店付）付的。退款时**按这三份的比例分开**，每份走自己的路：

| 原来怎么付的 | 退款能去哪 |
|---|---|
| 店铺余额付的 | 只能回**店铺余额**（同一门店） |
| 平台余额付的 | 只能回**平台余额**（同一国家） |
| 现金付的 | 退现金/转账（现在的做法）、或退到**店铺余额**（商家退款）、或退到**平台余额**（平台退款） |

所以：**退回现金的钱 ≤ 现金付的钱**（规则 W6）。平台余额永远变不成现金。

### 6.2 按比例怎么算（不会差一分）

用“累计目标”法，保证最后全部退完时每份正好退回：

```
本次退款 r，已退累计 R，订单实付 T，某一份（现金/平台余额）原付 P、已退 Pr：
  这份本次退 = floor((R + r) × P / T) − Pr
店铺余额那份 = r − 其他各份本次退（零头都落在店铺余额上；没有店铺余额那份就落在平台余额，再没有才落在现金）
```

零头落在“最窄”的余额上，现金永远是向下取整，不会多退一分现金。手算样例见第 12 节。

### 6.3 商家退款（退到店铺余额）

入口就是现在的“按菜退款”（订单详情、堂食账单的退款面板）：

- “退款方式”里多一项“**退到顾客店铺余额**”。只有订单绑了顾客账户（商城单、网店单、扫码堂食单）才出现；代客单、店员堂食单没有顾客账户，不出现（第三批短信验证后再加）。
- 金额还是按现有退款算法算（`App.Refund` 的建议金额），只是多了去向。
- 要勾选“**顾客已同意退到余额**”，选同意方式（当面/电话/聊天）。顾客收到站内消息：“XX 门店退款 60.00 已存入你在本店的余额，只能在本店使用。如有疑问请联系商家。”
- 权限：新权限 `wallet.refund`（店长默认有，接单员默认没有）；单笔超过门店设置的额度（默认等于 2000.00 当地货币，店主可改）要经理授权码；每个员工每天退到余额的合计有上限（默认 5 单或 5000.00，可改）。
- 整单都没送到/没做（订单还没完成）不走这里：那是取消订单，余额和券自动退回。

### 6.4 平台退款（退到平台余额）

入口：平台后台订单详情（和平台客服对话里打开的订单）。

- 只对**本国开通了平台余额**的门店的商城单、网店单、扫码单。
- 管理员选“**谁承担**”：
  - **平台承担**：平台出钱（例：平台的问题、补偿性退款）。
  - **商家承担**：从这家门店的平台月结算里扣（例：商家漏发、错发，商家不处理）。商家在账单里看到这一行，**7 天内可以点“有异议”**，直接打开平台客服对话；不处理视为同意（问题 Q3）。
- 金额和商家退款共享同一张单的上限（D7、W5），不会两边都退一遍。
- 另有“**平台补偿**”（不挂订单的，或超过订单金额的安抚，例：骑手态度差送 20.00）：单独记成补偿，单笔有上限（默认 200.00 当地货币），超过要第二个管理员审批，补偿来的部分 1 年过期（问题 Q4、Q9）。
- 顾客收到站内消息：“河马点餐系统退款 80.00 已存入你的平台余额（菲律宾），可在菲律宾任意门店使用。”

### 6.5 幂等和并发

- 每个退款请求带前端生成的 `Idempotency-Key`（UUID）；后端存到凭证的唯一幂等键（`refund:<订单号>:<key>`）。重复提交返回第一次的结果，不会退两次。
- 退款事务先 `lockOrder` 锁订单（现有做法），再锁余额账户。同一张单的两个退款排队执行，第二个看到的“已退累计”已经包含第一个。
- 扣余额用 `UPDATE … SET balance = balance - $1 WHERE id = $2 AND balance >= $1`，更新 0 行就是余额不够；再加表上的 `CHECK` 兜底。

## 7. 店铺余额细节

### 7.1 为什么按门店，不按品牌也不按整个商家

- 钱是门店收的：门店有自己的钱箱、对账、核款；品牌只是门店下的“招牌”，对账已经能按品牌拆（规则 R）。
- 一个商家的多家门店可能是不同老板（加盟）、不同国家、不同币种。按整个商家通用，就要在门店之间结算，复杂度和平台余额一样。
- 按品牌：顾客在“XX 炸鸡”退的钱不能在同一个厨房出的“XX 面馆”用，顾客会觉得奇怪，商家也没有好处。
- 报表里仍按**来源品牌**、**花费品牌**分列，规则 R（品牌相加 = 合并）同样适用。

（问题 Q1 给了另外两个选项。）

### 7.2 顾客同意

退到余额对商家有利（不用掏现金），容易被滥用成“强制店内消费”。所以：

- 退款面板必须勾选“顾客已同意”，记录同意方式，进审计日志。
- 顾客在“我的 → 余额 → 店铺余额”里能看到每一笔的来源订单。
- 顾客对“退到余额”不满意，可以在订单售后里申请，或找平台客服；平台可以要求商家改退现金（商家退现金后，平台做一张反向凭证把这笔余额扣回——前提是还没花掉）。

### 7.3 门店停业、被删除

- 门店有未用完的店铺余额时，**不能删除门店**（后台提示合计欠顾客多少）。
- 门店停业：平台在后台把这家店的店铺余额“冻结”，顾客看到“门店已停业，请联系平台客服”；平台和商家线下处理退现金，每处理一笔记一张反向凭证（`store_credit` → `store_refund`）。

## 8. 平台余额细节

### 8.1 按国家开关

平台后台“国家设置”新增一块“平台余额”：

| 设置 | 默认 |
|---|---|
| 开通 | **关**（律师确认后再开，问题 Q10） |
| 单个顾客余额上限 | 按国家设（建议约 200 美元等值：菲律宾 10,000.00 PHP、新加坡 300.00 SGD，开通时再定） |
| 单笔补偿上限 | 200.00 当地货币 |
| 补偿有效期 | 365 天 |
| 每个管理员每天平台退款+补偿合计 | 50,000.00 当地货币，超过要第二人审批 |

一个国家只有一种币种；门店币种和国家币种不一致（理论上不会，币种跟随国家）时，这家店不能用平台余额。

### 8.2 平台补给门店（结算）

- 顾客在门店 B 用平台余额付了 100.00，订单**完成**（送达、取走、结账）后算进 B 这个月的“平台应补”。
- 取消的单余额已退回，不算；配送异常结束的单余额不退，照算（门店做了菜）。
- 订单完成后又退款回平台余额的部分，从当月应补里减掉。
- 现有月结算单 `platform_settlements` 加两列：`credit_amount`（平台余额应补）、`charge_amount`（商家承担的平台退款，要扣的）。应付门店 = 平台券补贴 + 平台余额应补 − 商家承担的平台退款。为负时显示“门店应付平台”，线下处理。
- 结算延迟：每月 1 号出上个月的单（和现在一样），自然留出至少几天的退款期。

## 9. 安全和漏洞防御（逐条）

| # | 风险 / 攻击方式 | 防御 |
|---|---|---|
| 1 | **重复退款**：双击、网络重试、两个店员同时点 | 幂等键唯一；锁订单；退款上限每次在锁内重新算 |
| 2 | **并发扣余额**：两部手机同时下单，都读到余额够 | 锁账户行 + 条件更新 + `CHECK (balance >= 0)` 三重 |
| 3 | **改包**：前端把余额抵扣金额改大、把门店 id 改成别的店 | 前端不传金额；账户由服务器按“顾客 + 订单门店/国家”找；币种不一致拒绝 |
| 4 | **退款超过实付**：先退现金，再退余额，再找平台退 | 所有去向共享一个上限（W5），在锁内算 |
| 5 | **平台余额套现**：用平台余额买单，再让商家退现金 | 余额付的只能退回同种余额；退现金 ≤ 现金实付（W6） |
| 6 | **商家和顾客串通刷单**：假单标记完成，再让平台退款到平台余额，到别的店花掉，平台给别的店打钱 | 平台退款默认**商家承担**（问题 Q3），假单的钱从串通商家扣；平台承担的退款和补偿有单笔、每日、每管理员上限和两人审批；风控规则见第 10 节 |
| 7 | **顾客用平台余额在串通商家刷单**：下假单全用平台余额付，商家标完成，平台月结给商家打钱 | 平台余额只来自真实退款和小额补偿，总量受控；结算按月、有异议期；风控：某店平台余额付款占比、同一顾客反复在同一店用余额、同设备/同地址/同电话多账号（第 10 节） |
| 8 | **员工盗用**：员工把退款退到自己或亲友账号 | 余额只能退到**这张单的下单顾客账户**，不能选别的账户；没有顾客账户的单不能退到余额；单笔授权码、每人每天上限；退款记录页可按员工筛选 |
| 9 | **员工替顾客花余额** | 店员发起的单（代客、店员堂食）用余额必须顾客手机短信验证码（第三批）；没有验证不能扣 |
| 10 | **账号被盗**后花掉余额 | 登录本来就要短信验证码；每次余额变动发站内消息；余额不能转出、不能提现，盗号者最多点外卖，损失有限；平台可冻结账户 |
| 11 | **跨国家、跨币种** | 平台余额账户按国家；店铺余额按门店；凭证和每行明细币种必须一致（数据库触发器检查） |
| 12 | **改数据库、改流水**（内部人员、程序 bug） | 只追加触发器；借贷平衡触发器；应用账号无 UPDATE/DELETE 权限；每天核对缓存余额和流水 |
| 13 | **平台管理员滥发补偿** | 新增管理员权限（现在只有 `is_platform_admin` 一个开关）：`wallet.refund`、`wallet.compensate`、`wallet.approve`；超额两人审批（发起人不能自己批）；所有操作写 `audit_logs` |
| 14 | **订单改价后余额多扣** | 5.4 节：余额付款永远 ≤ 订单金额，金额变小自动退回（W4） |
| 15 | **洗钱 / 转移资金** | 不能充值、提现、转账、换币种；平台余额有上限；大额和异常模式报警 |
| 16 | **顾客注销账号** | 有余额时注销页提示余额作废并要二次确认；平台余额作废记凭证（`platform_credit` → `platform_fund`），店铺余额作废进门店报表 |
| 17 | **四舍五入多退** | 整数分；累计目标法；现金向下取整；零头落在最窄的余额上（6.2 节） |

## 11. 对账和报表

### 11.1 每天自动核对（`jobs.go` 加一个任务，结果进平台后台监控页）

- 每个账户：缓存余额 = 明细之和，顾客账户 ≥ 0。
- 每张凭证：明细之和 = 0。
- 每张单：`order_payments` 之和 ≤ `total`；= 扣款凭证 − 退回凭证。
- 每张单：各去向退款之和 ≤ 实付；退现金 ≤ 现金实付。
- 每个门店：店铺余额总欠款 = 所有顾客 `store_credit` 之和 = −(`store_refund` + `store_sales`)。
- 每月：结算单里的平台余额应补 = 当月完成订单的平台余额付款 − 退回。

任何一条不成立：报警，并让 `make pricing-check-db` 失败。

### 11.2 商家端

- 财务下新增“**店铺余额**”页：顾客欠款合计、本月新增（退款进来的）、本月用掉、明细（时间、订单、顾客手机打码、员工、金额、余额），可按品牌、员工筛选，可导出 Excel。
- 对账页：收款方式多“店铺余额”“平台余额”两列；**现金应收 = 订单金额 − 余额付款**；退款按去向分列（现金/转账/退到店铺余额/平台退款），退到余额的不扣钱箱。
- 账单页：平台余额应补、商家承担的平台退款。

### 11.3 平台后台

- “余额”页：按国家看平台余额总量（平台负债）、本月发放（退款/补偿，平台承担/商家承担）、本月使用、风控报警、待审批。
- 顾客详情：两种余额、流水、冻结/解冻。

## 12. 金额验算（PRICING_CHECK 要加什么）

计价引擎不变，所以 C 规则不变。新增：

| 编号 | 规则 |
|---|---|
| W1 | 每张余额凭证明细之和 = 0，所有行币种 = 凭证币种 = 账户币种 |
| W2 | 每个账户缓存余额 = 明细之和；顾客账户 ≥ 0；凭证和明细只追加 |
| W3 | 店铺余额只在开户门店的订单上花；平台余额只在同国家、同币种的门店花；订单币种 = 账户币种 |
| W4 | 每张单余额付款之和 ≤ 订单金额（任何时候，包括加单、退菜、打折、抹零之后）；取消的单余额付款 = 0 |
| W5 | 每张单所有去向的退款之和 ≤ 实付（就是 D7，退到余额的也算进去）；全部退完时正好相等 |
| W6 | 每张单退回同种余额的 ≥ 按比例算的那份；**退现金/转账的 ≤ 现金实付部分** |
| W7 | 每张退款到余额的凭证都对应一条 `order_refunds`，金额相等；幂等键唯一 |
| W8 | 平台结算单的平台余额应补 = 当月完成订单的平台余额付款 − 退回平台余额的部分 |

D2 的“应付”定义不变；对账的“现金应收”改成 `total − 余额付款`，`TestReconciliation`、`TestBills`、规则 R 要跟着更新。

### 手算样例（实现时加进 `TestPricingCheckSamples` 和 PRICING_CHECK.md 第 4 节）

**W-S1 店铺余额 + 现金，店铺原因退一道菜**

订单实付 150.00 = 店铺余额 50.00 + 现金 100.00。按现有退款算法，这道菜该退 60.00。
- 现金那份 = floor(60.00 × 100/150) = 40.00；店铺余额那份 = 60.00 − 40.00 = 20.00（回店铺余额，必须）。
- 现金那份 40.00 商家选“退到店铺余额”（顾客同意）→ 店铺余额 +60.00；选现金 → 店铺余额 +20.00，钱箱退 40.00。
- 之后这张单还能退现金最多 100.00 − 40.00 = 60.00。

**W-S2 三种都有，除不尽**

订单实付 299.00 = 店铺余额 50.00 + 平台余额 100.00 + 现金 149.00。第一次退 99.99：
- 现金 = floor(9999 × 14900 / 29900) = floor(4982.78) = 4982 → 49.82
- 平台余额 = floor(9999 × 10000 / 29900) = floor(3344.15) = 3344 → 33.44
- 店铺余额 = 9999 − 4982 − 3344 = 1673 → 16.73（精确值 16.72，零头 1 分落在店铺余额）

第二次退剩下的 199.01（累计 299.00）：
- 现金 = floor(29900 × 14900 / 29900) − 4982 = 14900 − 4982 = 9918 → 99.18
- 平台余额 = 10000 − 3344 = 6656 → 66.56
- 店铺余额 = 19901 − 9918 − 6656 = 3327 → 33.27

合计：现金 49.82 + 99.18 = 149.00，平台 33.44 + 66.56 = 100.00，店铺 16.73 + 33.27 = 50.00，各自正好退完。

**W-S3 平台余额付款后退菜，订单金额变小**

订单金额 120.00，下单时用平台余额 100.00，到付 20.00（还没收）。顾客原因退一道菜，引擎重算订单金额 = 80.00（减少 40.00）。
- 先减还没收的现金：到付 20.00 → 0，还差 20.00。
- 再退平台余额：100.00 → 80.00，20.00 回到顾客平台余额（反向凭证）。
- 结果：订单 80.00 = 平台余额 80.00 + 现金 0；W4 成立；订单完成后门店 B 的平台应补是 80.00。

**W-S4 平台退款，商家承担，跨店使用**

顾客在 A 店现金实付 200.00（菲律宾 PHP），送达后平台判定 A 漏发，平台退款 80.00 到平台余额，商家承担。
- 凭证：`merchant_charge(A)` −80.00，`platform_credit(顾客, PH)` +80.00。A 本月结算 −80.00。
- 顾客在 B 店下单 150.00，用平台余额 80.00，到付 70.00。凭证：`platform_credit` −80.00，`platform_payable(B)` +80.00。B 本月结算 +80.00。
- 平台自己出的钱 = 0；A 少拿 80.00，B 多拿 80.00；B 店现金收 70.00。

### 场景测试（实现时，真库，每步 `checked`）

第 3 节加一格“19 余额付款和退到余额”，覆盖：下单用两种余额 → 加单 → 退菜（金额变小退回余额）→ 结账打折 → 完成 → 按菜退款三种去向 → 全部退完 → 取消单退回余额 → 并发两单抢同一笔余额只成功一单 → 重复提交退款只退一次 → 跨国家/跨门店使用被拒。

## 13. 需要你决定的问题

| # | 问题 | 选项 | 推荐 |
|---|---|---|---|
| Q1 | 店铺余额在哪里能用？ | A. **这一家门店**（门店下所有品牌通用）<br>B. 只在退款的那个品牌<br>C. 同一商家所有门店（同国家同币种），门店之间要结算 | **A**。钱是门店收的、门店对账；C 以后需要时可以加“连锁通用”开关 |
| Q2 | 两种余额抵扣顺序？ | A. **先店铺余额，再平台余额**<br>B. 先平台余额<br>C. 顾客每次自己选 | **A**，店铺余额用途窄，先用掉对顾客划算；顾客仍可关掉任意一种 |
| Q3 | 平台退款谁出钱？ | A. **管理员每次选“平台承担”或“商家承担”**，商家承担的从月结算扣，商家 7 天内可提异议<br>B. 全部平台承担<br>C. 全部商家承担 | **A**。B 容易被串通刷单套平台的钱；C 平台自己的问题也让商家出不合理 |
| Q4 | 余额过期吗？ | A. **退款来的不过期；平台补偿来的 1 年过期**<br>B. 都不过期<br>C. 都按“最后一次使用起 1 年”（类似 Grab 菲律宾） | **A**。退款是顾客自己的钱，设过期容易引起投诉和消费者保护问题；补偿是平台送的，可以过期 |
| Q5 | 平台余额能不能用在网店单（店铺/品牌专属页面下的单）？ | A. **能**（商城单、网店单、扫码堂食都能）<br>B. 只能用在商城单（和平台券一样） | **A**。余额是退给顾客的钱，不是营销；限制太多顾客会觉得被“锁”住 |
| Q6 | 结算页“用余额”默认开还是关？ | A. **默认开**<br>B. 默认关，顾客自己打开 | **A**，和 Grab、foodpanda 一致；顾客想留着可以关 |
| Q7 | 商家退到店铺余额，要不要顾客同意？ | A. **店员勾选“顾客已同意”并选方式，顾客收到通知，可走售后/客服申诉**<br>B. 顾客在手机上点确认后才入账<br>C. 不用同意 | **A**。B 最严但顾客常常不回，退款卡住；C 有“强制店内消费”的投诉风险 |
| Q8 | 现在“我的”页的余额（平台手工记的）怎么办？ | A. **迁移成平台余额**（按币种找国家，记成平台补偿，不过期），奖励金暂时不动<br>B. 保持原样，新功能另起 | **A**，免得顾客看到两个“余额” |
| Q9 | 要不要“平台补偿”（不挂订单、或超出订单金额的安抚）？ | A. **要**，单笔上限 + 超额两人审批 + 1 年过期<br>B. 不要，只能按订单退款 | **A**，客服常用；风险用上限和审批控制 |
| Q10 | 平台余额什么时候开？ | A. **按国家开关，默认关；你找当地律师确认后在后台打开**<br>B. 做完就在所有国家打开 | **A**。平台余额能在多家店用，最接近电子货币的边界（第 2.2 节）；店铺余额不受这个限制 |
| Q11 | 代客单、店员堂食单（没有顾客账户）能不能用/退到余额？ | A. **第三批做：顾客手机短信验证码确认后才能用或退到余额**<br>B. 不做 | **A** |
