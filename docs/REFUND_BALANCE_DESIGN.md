## 0. 结论先看

1. **余额是“付款方式”，不是“优惠”。** 用店铺余额付款不改订单金额、不改满减门槛、不改税，计价引擎（`pricing.Price`）一行不动。订单多一张“付款明细”：店铺余额付了多少，剩下现金/到付多少。PRICING_CHECK 现有的 C、D、R 规则全部照旧成立，新加一组 W 规则管余额。
2. **一个顾客在一家门店一个账户。** 门店下所有品牌、堂食外卖自取都能用，币种 = 门店币种。钱是门店自己的：门店收了顾客的钱没退现金，记成欠顾客的。平台不垫钱、不结算。
3. **余额只进不出：** 不能充值、不能提现、不能转给别人、不能换币种、不能在别的门店用。唯一来源是这家门店的退款。
4. **复式记账 + 只追加流水：** 每一笔变动是一张“记账凭证”，至少两行，相加等于 0；凭证和明细数据库层面不能改不能删；账户余额是缓存，每天和流水对一遍。
5. **钱的上限有硬规则：** 一张单所有方式的退款合计 ≤ 顾客实付；原来用店铺余额付的部分只能退回店铺余额；**退回现金的钱 ≤ 用现金付的钱**。
6. **员工动不了不该动的钱：** 余额只能退给下单的那个顾客账户；店员不能替顾客花余额；大额要经理授权码；每人每天有上限。
7. **分两批做**：第一批核心功能（退到余额、结算页用余额、改单自动退回、顾客和商家页面、对账口径）；第二批风控、每日核对任务、代客单短信验证、门店停业处理。

## 2. 业内怎么做（调研）

### 2.1 外卖和出行平台

| 平台 | 退款去向 | 余额能不能提现 / 有效期 |
|---|---|---|
| foodpanda 菲律宾（pandapay） | 卡付款和**货到付款**的单，退款**默认进 pandapay 余额**；卡付款的可以在 30 天内选择转回原卡 | 马来西亚余额到 RM500 上限后，退款自动退回原支付方式 |
| Uber Eats | **现金单**的退款、补偿默认发 Uber Cash；卡付款的可选原路退回或 Uber Cash | Uber 出资的补偿性 Uber Cash 可能有有效期 |
| Grab（GrabPay Credits） | 马来西亚退款使余额超过央行上限的部分退回原充值来源 | 菲律宾：自最后一次消费起 1 年有效 |
| 美团 | 原路退回为主；原渠道异常才退到美团余额 | 储值卡、礼品卡单独管理 |

可以借鉴的：

- **货到付款的单退到余额是行业常见做法**，因为没有可原路退的线上支付——我们现在正是这个情况。
- **要尊重顾客的选择**：foodpanda 新加坡和巴基斯坦都有顾客投诉“退款被强制留在平台里花”。所以退到店铺余额要有“顾客同意”的记录（第 6.3 节），顾客能申诉。

### 2.2 储值的监管

> 下面是公开资料的整理，不是法律意见。

| 国家 / 地区 | 规定 | 对店铺余额的意思 |
|---|---|---|
| 菲律宾 BSP | 2023 年 Circular 1166 取代 Circular 649。只由“商家兼发行人”自己收的**闭环钱包**和多家能用的电子货币区别对待；能转给别人的算电子货币 | 店铺余额只在一家门店用、不能转、不能充值，是这家店自己的退款欠条，属于闭环，风险低 |
| 新加坡 MAS | 只用于“限定用途电子货币”的服务不受《支付服务法》监管 | 同上 |
| 马来西亚 BNM | 限定用途电子货币 Order 2024 的豁免类别里**明确有“给用户退款”一类** | 正好对应 |
| 中国大陆 | 单用途预付卡（只在一个经营者处用）由商务部门管，多用途要支付牌照 | 我们没有充值，不是预付卡；以后做“充值送”是另一个方案 |

结论：店铺余额只要守住“**不能充值、不能提现、不能转账、只在这家门店用**”，在这几个地方都是风险最低的形态。平台余额（多家店能用）才接近电子货币的边界，那是附录 A 以后再处理的事。

## 3. 店铺余额是什么

| | 店铺余额 |
|---|---|
| 账户 | 顾客 × 门店（一个顾客在每家门店最多一个） |
| 币种 | 门店币种 |
| 能在哪用 | 只在这家门店：门店下所有品牌，堂食、外卖、自取，商城单和品牌专属页面单 |
| 谁能存进去 | 这家门店有权限的员工，只能按订单退款 |
| 钱是谁的 | 门店的。顾客付了钱，门店没退现金，记成欠顾客 |
| 顾客花掉时 | 门店少收现金，门店欠款减少，**不涉及平台** |
| 有效期 | 不过期（问题 Q2） |
| 提现/转账/充值/别的店用 | 都不行 |
| 平台单（Grab、foodpanda 等） | 不适用：平台单由外卖平台自己退款，也不能用店铺余额付 |

## 4. 账怎么记：复式记账

### 4.1 为什么不能像现在的 `customer_wallet_entries` 那样一行一个数

- 看不出这笔钱从哪来、对方是谁——对不了账。
- 没有幂等键：网络重试会记两次。
- 余额靠 `sum()` 临时算：两张单同时扣，都读到够用，都扣成功 → 余额变负。

### 4.2 账户（`wallet_accounts`）

| 种类 `kind` | 归属 | 余额 | 说明 |
|---|---|---|---|
| `store_credit` | 顾客 + 门店 | ≥ 0 | 顾客的店铺余额 |
| `store_refund` | 门店 | 可负 | 门店退到余额的累计（负数 = 门店因退款欠顾客的总额） |
| `store_sales` | 门店 | 可负 | 门店收到的余额付款 |

每个账户有固定币种。顾客账户 `CHECK (balance >= 0)`。门店欠顾客的总额 = 这家店所有顾客 `store_credit` 之和 = −(`store_refund` + `store_sales`)。

（以后做平台余额时，在同一套表里加 `platform_credit` 等账户种类即可，不用重做，见附录 A。）

### 4.3 记账凭证（`wallet_journals` + `wallet_postings`）

一笔业务 = 一张凭证 + 至少两行明细，**明细相加 = 0**，全部同一币种。例子（单位：分）：

| 业务 | 明细 |
|---|---|
| 门店 A 给顾客退 60.00 到店铺余额 | `store_refund(A)` −6000，`store_credit(顾客, A)` +6000 |
| 顾客在 A 下单用店铺余额付 50.00 | `store_credit(顾客, A)` −5000，`store_sales(A)` +5000 |
| 订单取消，退回刚才扣的 50.00 | 原凭证的反向凭证：`store_sales(A)` −5000，`store_credit(顾客, A)` +5000 |
| 退款记错了，店长撤回（余额还没花） | 反向凭证，不改原凭证 |

凭证上记：种类、**幂等键（唯一）**、订单号、退款号、门店、币种、谁做的（员工/顾客/系统/平台管理员）、谁授权的、原因、时间。

### 4.4 数据库层面的保护（不靠应用代码自觉）

1. `wallet_journals`、`wallet_postings` **只追加**：触发器拦截 UPDATE/DELETE（和 `order_money_events` 一样）。写错了只能做反向凭证。
2. **借贷平衡**：延迟约束触发器（`DEFERRABLE INITIALLY DEFERRED`），事务提交时检查每张凭证明细之和 = 0、币种都等于凭证币种和账户币种。不平衡整个事务回滚。
3. **余额缓存**：`wallet_accounts.balance` 只由写明细的那一个函数（`postJournal`）在同一事务里更新，每行明细存 `balance_after`。顾客账户 `CHECK (balance >= 0)` 兜底。
4. 应用连接数据库的账号对这两张表只给 INSERT/SELECT（DEPLOY.md 补一节，第二批）。
5. 每天夜里核对（第 10 节）。

## 5. 用店铺余额付款

### 5.1 付款明细（`order_payments`）

| 列 | 说明 |
|---|---|
| order_id | 订单 |
| tender | `store_credit`（以后可加别的） |
| amount | 余额付了多少（订单金额变小时可减少，见 5.4） |

订单上不存现金那一行：**现金/到付应收 = `orders.total` − 余额付款**。对账、核款、骑手收款、堂食结账的“应收”都改成这个数（现在等于 `total`）。

### 5.2 结算页

- 顾客登录、并且在这家门店有余额时，结算页“付款方式”卡里多一行“**店铺余额 可用 60.00**”，开关默认**打开**（问题 Q3）。
- 金额由服务器在下单事务里算：`min(可用余额, 应付)`。前端只传“用不用”，**不传金额**，防止改包。
- 下单事务顺序：报价 → 锁顾客这家门店的余额账户（`SELECT … FOR UPDATE`）→ 余额不够了就返回“金额有变化”让顾客重新确认（和活动、券现在的做法一样）→ 写订单 → 记扣款凭证 → 写 `order_payments`。
- **余额刚好够付全款**：订单直接 `payment_status = paid`，骑手不用收钱，配送单显示“已付，不收款”。

### 5.3 哪些单能用

| 单的类型 | 能不能用店铺余额 |
|---|---|
| 商城单、网店单（店铺/品牌专属页面） | 能，顾客自己在结算页选 |
| 堂食扫码单 | 能，顾客结账时在手机上点“用余额” |
| 代客单、店员开的堂食单 | 第二批：店员发起，顾客手机收短信验证码确认后才扣（问题 Q6） |
| 平台单（Grab 等） | 不能 |

**店员不能在没有顾客确认的情况下动顾客的余额**——这是防员工盗用的关键。

### 5.4 订单金额变了怎么办

余额付款之后，订单还可能加单、退菜、结账打折、抹零。规则：**余额付的钱永远 ≤ 订单金额**。

- 金额变大（加单）：多出来的部分到付（顾客在加单确认页也可以再用余额）。
- 金额变小（退菜、打折）：先减还没收的现金；现金减到 0 还不够，再把多出来的余额退回（反向凭证）。
- 订单取消、拒单、超时：余额全额自动退回（和优惠券退回一样）。
- 配送异常结束（餐已做）：余额不退，和现有券的规则一致；需要时商家走退款。

### 5.5 和计价引擎的关系

余额**不是**引擎里的 `Adjustment`，不进 `order_discounts`，不影响满减门槛、券、服务费、税、抹零。`loadMoney → choosePromo → priceMoney → saveMoney` 不变；余额的调整在 `saveMoney` 之后、同一事务里，由新函数 `settleTenders(ctx, tx, orderID)` 按 5.4 处理。R1–R3 重放规则不受影响。

## 6. 商家退款

### 6.1 一张单的钱分两份

一张单的实付 = 店铺余额付的 + 现金（到付/到店付）付的。退款时**按比例分开**：

| 原来怎么付的 | 退款能去哪 |
|---|---|
| 店铺余额付的 | 只能回**店铺余额** |
| 现金付的 | 退现金/转账（现在的做法），或者退到**店铺余额**（顾客同意） |

所以：**退回现金的钱 ≤ 现金付的钱**（规则 W6）。

### 6.2 按比例怎么算（不会差一分）

用“累计目标”法，保证全部退完时两份正好退回：

```
本次退款 r，之前已退累计 R，订单实付 T，现金原付 C，现金那份之前已退 Cr：
  现金那份本次 = floor((R + r) × C / T) − Cr
  店铺余额那份本次 = r − 现金那份本次
```

现金那份永远向下取整，零头落在店铺余额上，不会多退一分现金。手算样例见第 11 节。

### 6.3 退款面板怎么变

入口就是现在的“按菜退款”（订单详情、堂食账单的退款面板），金额还是按现有退款算法算（`App.Refund` 的建议金额），只是多了去向：

- “退款方式”里多一项“**退到顾客店铺余额**”。只有订单绑了顾客账户（商城单、网店单、扫码堂食单）才出现；代客单、店员堂食单没有顾客账户，不出现（问题 Q6）。
- 如果这张单有一部分是余额付的，面板直接显示“其中 20.00 退回店铺余额（原来用余额付的），40.00 按你选的方式退”。
- 选“退到店铺余额”时必须勾选“**顾客已同意**”，并选同意方式（当面/电话/聊天）（问题 Q4）。
- 顾客收到站内消息：“XX 门店退款 60.00 已存入你在本店的余额，只能在本店使用。有疑问请联系商家。”
- 整单还没完成（没送到、没做）不走这里：那是取消订单，余额和券自动退回。

### 6.4 权限和限额

| 规则 | 默认（店主可在门店设置里改） |
|---|---|
| 新权限 `wallet.refund`（退到店铺余额） | 店主、店长有；接单员没有，可用经理授权码 |
| 单笔超过额度要经理授权码 | 2000.00（当地货币） |
| 每个员工每天退到余额的合计 | 5000.00，超过要店主授权码 |
| `wallet.view`（看店铺余额页） | 店主、店长有 |

### 6.5 幂等和并发

- 每个退款请求带前端生成的 `Idempotency-Key`；后端存到凭证的唯一幂等键（`refund:<订单号>:<key>`）。重复提交返回第一次的结果，不会退两次。
- 退款事务先 `lockOrder` 锁订单（现有做法），再锁余额账户。同一张单的两个退款排队执行，第二个看到的“已退累计”已经包含第一个。
- 扣余额用 `UPDATE … SET balance = balance - $1 WHERE id = $2 AND balance >= $1`，更新 0 行就是余额不够；再加表上的 `CHECK` 兜底。

## 7. 其他规则

### 7.1 为什么按门店，不按品牌也不按整个商家

- 钱是门店收的：门店有自己的钱箱、对账、核款；品牌只是门店下的“招牌”，对账已经能按品牌拆（规则 R）。
- 一个商家的多家门店可能是不同老板（加盟）、不同国家、不同币种。按整个商家通用，门店之间就要结算。
- 按品牌：顾客在“XX 炸鸡”退的钱不能在同一个厨房出的“XX 面馆”用，顾客会觉得奇怪，商家也没好处。
- 报表里仍按**来源品牌**、**花费品牌**分列，规则 R（品牌相加 = 合并）同样适用。

### 7.2 顾客不满意“退到余额”

- 顾客在“我的 → 余额”里能看到每一笔来自哪张订单。
- 可以在订单售后里申请，或找平台客服。平台可以要求商家改退现金：商家退现金后，店长在店铺余额页对这笔点“撤回”（反向凭证），前提是这笔余额还没花掉。

### 7.3 门店停业、被删除

- 门店有未用完的店铺余额时，**不能删除门店**（后台提示一共欠顾客多少）。
- 门店停业：平台后台把这家店的店铺余额“冻结”，顾客看到“门店已停业，请联系平台客服”；平台和商家线下处理退现金，每处理一笔记一张反向凭证。（第二批）

### 7.4 顾客注销账号

有店铺余额时，注销页提示“你在以下门店还有余额，注销后作废”，要二次确认；作废记反向凭证，进门店报表。

## 8. 安全和漏洞防御（逐条）

| # | 风险 / 攻击方式 | 防御 |
|---|---|---|
| 1 | **重复退款**：双击、网络重试、两个店员同时点 | 幂等键唯一；锁订单；退款上限每次在锁内重新算 |
| 2 | **并发扣余额**：两部手机同时下单，都读到余额够 | 锁账户行 + 条件更新 + `CHECK (balance >= 0)` 三重 |
| 3 | **改包**：前端把抵扣金额改大、把门店改成别的店 | 前端不传金额；账户由服务器按“顾客 + 订单门店”找；币种不一致拒绝 |
| 4 | **退款超过实付**：先退现金，再退余额 | 所有去向共享一个上限（W5），在锁内算 |
| 5 | **用余额换现金**：余额买单，再让店员退现金 | 余额付的只能退回余额；退现金 ≤ 现金实付（W6） |
| 6 | **员工把退款退到自己或亲友账号** | 只能退到**这张单的下单顾客账户**，界面和接口都不能选别的账户；没有顾客账户的单不能退到余额；授权码、每人每天上限；退款记录页可按员工筛选 |
| 7 | **员工替顾客花余额** | 店员发起的单用余额必须顾客手机短信验证码（第二批），没有验证不能扣 |
| 8 | **员工和顾客串通**：假单标完成再退到余额 | 损失只在这家门店内部（余额只能在本店用，变不成现金、不涉及平台的钱）；授权码 + 每日上限 + 店主能看到每个员工退到余额的明细和报警（第 9 节） |
| 9 | **账号被盗**后花掉余额 | 登录要短信验证码；每次余额变动发站内消息；余额不能转出、不能提现，最多在这家店点餐；平台可冻结账户 |
| 10 | **跨门店、跨币种** | 账户按门店；凭证和每行明细币种必须一致（数据库触发器检查） |
| 11 | **改数据库、改流水**（内部人员、程序 bug） | 只追加触发器；借贷平衡触发器；应用账号无 UPDATE/DELETE 权限；每天核对 |
| 12 | **订单改价后余额多扣** | 5.4 节：余额付款永远 ≤ 订单金额，金额变小自动退回（W4） |
| 13 | **商家强迫顾客收余额**（消费者投诉） | 必须记录顾客同意；顾客能申诉；平台能要求改退现金 |
| 14 | **四舍五入多退** | 整数分；累计目标法；现金向下取整（6.2 节） |
| 15 | **平台管理员乱动商家的钱** | 平台管理员只能查看、冻结/解冻，**不能**给顾客加店铺余额；所有操作写 `audit_logs` |

## 10. 对账和报表

### 10.1 每天自动核对（`jobs.go` 加一个任务，结果进平台后台监控页；第二批）

- 每个账户：缓存余额 = 明细之和，顾客账户 ≥ 0。
- 每张凭证：明细之和 = 0。
- 每张单：余额付款 ≤ 订单金额；= 扣款凭证 − 退回凭证。
- 每张单：各去向退款之和 ≤ 实付；退现金 ≤ 现金实付。
- 每个门店：所有顾客店铺余额之和 = −(`store_refund` + `store_sales`)。

任何一条不成立就报警；`make pricing-check` 和 `make pricing-check-db` 也跑这些检查（第一批就加）。

### 10.2 商家端

- 财务下新增“**店铺余额**”页：顾客余额合计（门店欠顾客多少）、本月退进来多少、本月用掉多少、明细（时间、订单、顾客手机打码、员工、金额、余额），可按品牌、员工筛选，可导出 Excel。
- 对账页：收款多一列“店铺余额”；**现金应收 = 订单金额 − 余额付款**；退款按去向分列（现金/转账/退到店铺余额），退到余额的不扣钱箱。
- 账单页：营业额照旧按订单金额（余额付款也是营业额）；另列“退到店铺余额”“店铺余额收款”。

### 10.3 顾客端

“我的 → 余额”里，现有的平台余额（手工记的）下面列出“**店铺余额**”：每家有余额的门店一行（店名、余额、去点餐），点进去看流水。

### 10.4 平台后台

顾客详情里能看到这个顾客在各门店的店铺余额和流水，可以冻结/解冻。

## 11. 金额验算（PRICING_CHECK 要加什么）

计价引擎不变，所以 C 规则不变。新增：

| 编号 | 规则 |
|---|---|
| W1 | 每张余额凭证明细之和 = 0，所有行币种 = 凭证币种 = 账户币种 |
| W2 | 每个账户缓存余额 = 明细之和；顾客账户 ≥ 0；凭证和明细只追加 |
| W3 | 店铺余额只在开户门店的订单上花；订单币种 = 账户币种 |
| W4 | 每张单余额付款 ≤ 订单金额（任何时候，包括加单、退菜、打折、抹零之后）；取消的单余额付款 = 0 |
| W5 | 每张单所有去向的退款之和 ≤ 实付（就是 D7，退到余额的也算）；全部退完时正好相等 |
| W6 | 每张单退回店铺余额的 ≥ 按比例算的那份；**退现金/转账的 ≤ 现金实付部分** |
| W7 | 每张退到余额的凭证都对应一条 `order_refunds`，金额相等；幂等键唯一 |

D2 的“应付”定义不变；对账的“现金应收”改成 `total − 余额付款`，`TestReconciliation`、`TestBills`、规则 R 要跟着更新。

### 手算样例（实现时加进 `TestPricingCheckSamples` 和 PRICING_CHECK.md 第 4 节）

**W-S1 店铺余额 + 现金，店铺原因退一道菜**

订单实付 150.00 = 店铺余额 50.00 + 现金 100.00。按现有退款算法，这道菜该退 60.00。
- 现金那份 = floor(60.00 × 100/150) = 40.00；店铺余额那份 = 60.00 − 40.00 = 20.00（必须回店铺余额）。
- 现金那份 40.00 选“退到店铺余额”（顾客同意）→ 店铺余额 +60.00；选现金 → 店铺余额 +20.00，钱箱退 40.00。
- 之后这张单还能退现金最多 100.00 − 40.00 = 60.00。

**W-S2 除不尽**

订单实付 299.00 = 店铺余额 50.00 + 现金 249.00。第一次退 99.99：
- 现金 = floor(9999 × 24900 / 29900) = floor(8326.93) = 8326 → 83.26
- 店铺余额 = 9999 − 8326 = 1673 → 16.73（精确值 16.72，零头 1 分落在余额，现金少退不多退）

第二次退剩下的 199.01（累计 299.00）：
- 现金 = floor(29900 × 24900 / 29900) − 8326 = 24900 − 8326 = 16574 → 165.74
- 店铺余额 = 19901 − 16574 = 3327 → 33.27

合计：现金 83.26 + 165.74 = 249.00，店铺余额 16.73 + 33.27 = 50.00，各自正好退完。

**W-S3 用余额付款后退菜，订单金额变小**

订单金额 120.00，下单时用店铺余额 100.00，到付 20.00（还没收）。顾客原因退一道菜，引擎重算订单金额 = 80.00（少 40.00）。
- 先减还没收的现金：到付 20.00 → 0，还差 20.00。
- 再退余额：100.00 → 80.00，20.00 回到顾客店铺余额（反向凭证）。
- 结果：订单 80.00 = 店铺余额 80.00 + 现金 0；W4 成立；骑手不用收钱。

### 场景测试（实现时，真库，每步 `checked`）

PRICING_CHECK 第 3 节加一格“19 店铺余额付款和退到店铺余额”，覆盖：下单用余额 → 加单 → 退菜（金额变小退回余额）→ 结账打折 → 完成 → 按菜退款两种去向 → 全部退完 → 取消单退回余额 → 并发两单抢同一笔余额只成功一单 → 重复提交退款只退一次 → 到别的门店、别的币种使用被拒 → 多品牌门店在 A 品牌退、B 品牌用。

## 14. 实现记录（2026-11-27）

两批一起实现：

- 迁移 `00083_store_credit.sql`：`wallet_accounts`（`store_credit` 顾客余额、`store_refund` 店铺退款出资、`store_sales` 店铺用余额收的款）、`wallet_journals`（`refund`、`spend`、`return`、`revoke`，`idem_key` 唯一）、`wallet_postings`；触发器保证凭证和明细只追加、账户余额只能由记账改、提交时每张凭证借贷平衡；顾客余额 CHECK ≥ 0；`orders.credit_paid` ≤ 应付（提交时检查）；`order_refunds` 加 `cash_part`、`to_credit`、`consent`；`branches` 加两个限额；`wallet_verifications`（短信验证码，和登录验证码分开）；`wallet_check_runs`。
- 后端：`internal/app/wallet.go`（记账、用余额、退回、退款拆分、限额）、`wallet_verify.go`（短信验证码）、`wallet_views.go`（顾客、商家、平台的页面和撤回、冻结）、`wallet_check.go`（W1–W7、每日核对）；接口在 `internal/httpapi/wallet.go`。
- 前端：结算页“用店铺余额”、订单金额里“店铺余额抵扣 / 还需支付”、“我的 → 店铺余额”（`/me/store-credit`）、退款面板的“退到哪里”、商家后台 财务 → 店铺余额（`/merchant/credit`）、代客单和堂食结账“用店铺余额”（短信验证码）、骑手按“还要收的”收钱、对账和账单、平台后台顾客页（冻结）和后台任务页（每日核对结果）。12 种语言都有。
- 验算：样例 W-S1、W-S2（`TestRefundSplitSamples`、`TestMulDivFloorSamples`），W-S3 和第 19 格场景见 PRICING_CHECK.md。

和方案不同的地方：

1. 用余额付的钱记在订单的 `credit_paid` 一列，没有另建“付款明细”表：现在一张单只可能有“余额 + 另一种方式”，一列够用，验算也简单。
2. 全部用余额付清的单，不在下单时标“已付”，而是在送达、取走、关台时标“已付”（付款方式记“店铺余额”）；这样中间退菜、加单、取消都走原来的流程。
3. 扫码堂食的顾客在桌上不付款（还没有线上支付），所以堂食用余额是收银员在结账页点“用店铺余额”，给顾客发短信验证码。
4. 现在没有“顾客注销账号”的功能，第 7.4 节以后有了注销再接上（注销前要先处理余额）。
5. 门店停业：平台后台可以一键冻结这家店所有顾客余额；删除商家或门店时，只要还有顾客余额就会被拒（`CREDIT_OWED`）。
6. 退款面板选“退到店铺余额”时，一次授权同时覆盖“售后”和“退到余额”两项权限（接单员没有这两项时请经理输一次授权码）。

验算时发现的现有算法问题（没改，等 brian 定）：按菜退款时，把一张单的菜全部退完，没有活动的单会少退包装费那一份（包装费和它的税，例如应付 92.34 的单最多退 81.14，差 11.20）；有活动的单因为每次建议金额封顶到“还能退的”，会退满。PRICING_CHECK.md D7 写的“把菜全部退完时正好等于应付”只在后一种情况成立。
