## 1. 要解决什么

brian 的原话：还需要新增退菜的功能，堂食和外卖都需要。

- **堂食**：PR #105 已经有一个简单的退菜（账单里点菜 → 退菜 → 选份数和原因）。缺的是：
  - 看不到退了以后账单变成多少；
  - 后厨屏只是把退掉的菜悄悄藏起来，厨师可能已经在做了也不知道；
  - 不管菜做没做，限量库存都加回去，做好的菜退掉也不算损耗；
  - 接单员什么都能退，没有权限和经理授权码；
  - 结账以后就没法退了；
  - 没有地方看“今天退了哪些菜、谁退的”。
- **外卖、自取**：完全没有。顾客打电话说“炸鸡不要了”或者某道菜沽清了，店员只能取消整单重下，或者送完再走售后。加单（PR #107）已经能往单里加菜，退菜是它的反方向。

## 2. 业内怎么做

| 产品 | 怎么退 | 要点 |
|---|---|---|
| Toast | 送厨后的菜不能删，只能“作废（void）”，必须选预设原因 | 没有退菜权限的员工要经理刷卡或输码授权；报表里有“作废的菜”“按授权人统计” |
| Square for Restaurants | 还没做的菜用“作废（void）”从账单拿掉；已经在做或已上桌的用“赠送（comp）”免单 | 原因必选，原因印在小票上；作废不会自动打印到厨房，要自己告诉后厨（官方 FAQ 写明这个短板） |
| 客如云、美团收银、哗啦啦 | 桌台账单里点菜 → 退菜，选份数和原因 | 退菜要授权（可设置），退菜单打印到对应的出品打印机；报表有“退菜明细” |
| Uber Eats / DoorDash 商家端 | 菜卖完了，商家可以把这道菜从单里拿掉，平台给顾客退这道菜的钱并通知顾客 | Uber 零售接口有 `REMOVE_ITEM`，顾客收到“商家移除了缺货商品并已退款”；DoorDash 有“订单调整”接口 |
| 美团、饿了么外卖 | 顾客申请“部分退款”，商家同意 | 部分退款时券一般不退，整单退才退券 |

结论：

1. **送厨后的菜不删，只“退”**：留下原因、谁退的、什么时候，账单上划掉而不是消失。我们现在堂食就是这么做的（拆出一行 `cancelled`）。
2. **按“做没做”分两种**：还没开始做的，退了就退了，库存回去；已经在做或做好了的，菜已经浪费，要通知厨房、算损耗，而且通常要更高权限或经理授权（Toast、客如云都这样）。
3. **一定要告诉厨房**：Square 的短板正好是没有自动通知厨房。我们有后厨屏，退菜要在后厨屏上醒目提醒，厨师确认看到；有打印的工位打一张退菜单。
4. **外卖退菜要通知顾客**，写明退了什么、少收多少钱（Uber 的做法）。
5. **收完钱以后**就不是“退菜”而是“退款”了：按菜算出退多少钱，记录退款方式。

## 3. 现在系统里已经有什么

| 已有 | 和退菜的关系 |
|---|---|
| `VoidItem`（`internal/app/dinein.go`）和 `POST /merchant/bill-items/{id}/void` | 按份退：整行退直接把这一行改成 `cancelled`；退一部分时拆出一行 `cancelled`，原行减份数。**外卖直接复用这段拆行逻辑** |
| `order_items.prep_status`（`pending` / `preparing` / `ready` / `cancelled`）、`served_at`、`void_reason` | 判断这道菜“做没做”；退掉的行就是 `cancelled` |
| 堂食设置 `dine_presets.void_reasons` | 退菜原因的预设（点错了、顾客不要了、上太慢、菜品有问题、沽清了），外卖也用这一份 |
| 加单的金额重算 `priceWithAddon`（`internal/app/addon.go`） | 外卖退菜也要重算满减、税；写一个反方向的版本（第 6 节） |
| `orders.manifest_version`、打包的 `MANIFEST_CHANGED` | 退菜后加 1，已经打包的单要重新核对 |
| 骑手推送 `pushRider`、顾客通知 `notifyCustomer` | 加新事件 `item_voided` |
| 小票 `/ticket/:id?batch=` | 加 `?void=` 打退菜单 |
| 经理授权码（`approvals.go`，现在能授权“取消订单”“售后和退款”） | 加一项“退已做的菜” |
| 售后 `order_aftersales`（每单一条，只记录，钱线下退） | 收完钱以后的“按菜退款”挂在这里（第 7 节） |
| 货到付款 `cash_collections` | 送达时按订单总额记应收；送达前退菜只要改总额 |

## 4. 什么时候能退

| 订单 | 能退菜 | 之后 |
|---|---|---|
| 外卖 | 骑手取餐之前（和加单同一个截止点），待接单的也能退 | 骑手取餐后到送达前：不能退菜（菜在骑手手上，骑手到门口按单收钱）。送达收款后：走“按菜退款”（第 7 节） |
| 自取 | 顾客取走之前 | 取走后：按菜退款 |
| 堂食 | 结账关台之前（现在就是） | 结账后：按菜退款 |
| 顾客自己加的、还在等确认的菜 | 不叫退菜，用加单里现有的“拒绝” | |
| 已取消、已拒单、配送失败 | 不能 | |

- **外卖最后一道菜不能退**：全部退掉就是取消订单，按钮提示“这是最后一道菜，要取消整单请用‘取消订单’”（取消会退券、退活动名额，规则不一样）。堂食可以全部退掉（客人走了），关台时应付 ₱0。
- 截止由后端判断，和交接锁同一张订单，骑手刚好取餐时只会有一个成功。

## 5. 按菜做到哪一步分两种

| 这道菜 | 后厨 | 限量库存 | 损耗 | 谁能退 |
|---|---|---|---|---|
| **还没开始做**（`pending`） | 后厨屏上划掉、写“已退”，1 分钟后消失；有打印的工位打退菜单 | 加回去 | 不算 | 有这张单操作权限的人：外卖 `order.handle`，堂食 `table.use`（和现在一样） |
| **已经在做 / 做好了 / 已上桌 / 已打包**（`preparing`、`ready`、`served_at` 有值） | 后厨屏上红色“退 1 份”提醒，**厨师点“知道了”才消失**；打退菜单 | 不加（菜已经用掉了） | 算损耗，按菜价记 | 要新权限“退已做的菜”（`order.void`）。没有的人点“退菜”时弹经理授权码，和“取消订单”一样 |

- 退菜面板上会写清楚这道菜现在的状态：“还没开始做，退了不浪费”或“厨房已经在做（4 分钟），退了算损耗，需要经理授权”。
- 原因属于“店铺原因”（做错了、上太慢、菜品有问题、沽清了）还是“顾客原因”（点错了、顾客不要了）：预设原因在设置里各带一个标记，影响满减怎么算（第 6 节）和统计。手写的原因由店员点选算哪一种，默认“店铺原因”。

## 6. 钱怎么算

原则：**退掉的菜按下单时的价格从单里减掉，整单重算一次；配送费、包装费不变；券保留；满减看是谁的原因。**

| 项目 | 规则 |
|---|---|
| 菜品 | 退掉的份数 × 下单单价（含规格加价）。同一道菜分几批点的，退哪一行就按哪一行的价格 |
| 配送费、包装费 | 不变（骑手照样跑一趟） |
| 门店活动（满减等） | **顾客原因**：按剩下的菜重新算，可能降档或不再满足，面板上明确写“满减从减 ₱60 降到减 ₱30”。**店铺原因**：满减保持原来的金额不降（但不超过剩下的菜品金额），顾客不因店里的问题吃亏 |
| 原单用的店铺券、平台券 | 保留，金额不变，但不超过剩下的菜品金额（券的门槛只在下单时判断）。整单取消才退券（现在的规则） |
| 服务费、税 | 按重算后的菜品金额算 |
| 复购礼券（送券） | 按订单完成时的最终金额判断，退菜后不够门槛就不送 |
| 平台券账单 | 平台券金额没变就不变；被“不超过菜品金额”压低时，账单按实际抵扣的金额算 |
| 堂食 | 不参加优惠（已确认），只是减菜价、重算服务费和税 |

例子（效果图 01）：外卖单菜品 ₱565（海南鸡饭 ₱199、干炒牛河 ₱126、冻柠茶 ₱35、珍珠奶茶 ₱85、盐酥鸡 ₱120），满 ₱500 减 ₱60，配送费 ₱49，包装费 ₱10，应付 ₱564。退掉盐酥鸡 ₱120：

| | 退菜前 | 顾客原因（顾客不要了） | 店铺原因（沽清了） |
|---|---|---|---|
| 菜品 | ₱565 | ₱445 | ₱445 |
| 满减 | −₱60（满 500 减 60） | −₱30（降到满 300 减 30） | −₱60（不降） |
| 配送费 + 包装费 | ₱59 | ₱59 | ₱59 |
| **应付** | **₱564** | **₱474（少收 ₱90）** | **₱444（少收 ₱120）** |

### 6.1 收钱

- **外卖、自取（货到付款 / 到店付）**：只改订单总额。骑手 App 和打包单上显示新的应收，写“退菜后 ₱564 → ₱474”，送达按新总额收钱，核款也按新总额。
- **堂食**：结账前退菜，结账页金额跟着变（现有的 `expected_manifest_version` 会拦住拿旧金额收款）。
- **以后有线上支付或“已收款”时**：退菜的差额自动变成“要退给顾客 ₱90”，走第 7 节的退款。这次只在数据上记下每次退菜前后的总额，留好位置。

## 7. 收完钱以后：按菜退款

外卖送达、自取取走、堂食结账后，菜已经吃了或带走了，不能再“退菜”，但顾客可能说“盐酥鸡是凉的”“少了一杯奶茶”。现在只能在售后里写一句“已处理”，钱是多少没有记录。

- 订单详情（和售后申请）里一个“**按菜退款**”：勾选哪几道菜、几份，金额按第 6 节自动算出来（可以改小，不能改大，最多退到订单实付），选原因和**退款方式**（现金退回、原付款方式退回如 GCash，堂食按当时的付款方式默认）。
- 权限用现有的“售后和退款”（`order.aftersale`），没有的人弹经理授权码（现在就支持）。
- 记录进新表 `order_refunds`，订单详情、顾客订单详情显示“已退款 ₱120（盐酥鸡 ×1）”。顾客有售后申请的，退款后申请自动变“已处理”，回复里带上退款明细。
- 核款和账单：当天的现金退款从这家店的现金应收里扣掉；“按菜退款”在退菜记录页（第 8.7 节）单独一栏。
- 系统不碰真实的钱（没有线上支付），这里只是**记录**店员线下退了多少，方便对账。以后接线上支付时，这里改成原路退回。

## 8. 页面

### 8.1 商家订单详情（外卖、自取）（效果图 01、02）

- 每道菜右边（状态标签旁）一个小的“退菜”按钮。不能退的时候（骑手已取餐、已取消）按钮不出现，订单抬头写“骑手已取餐，不能再退菜；送达后可以按菜退款”。
- 点了弹出**退菜面板**，和堂食的退菜面板长得一样（大按钮、点选）：
  - 退几份（默认 1 份，−/＋）；
  - 原因（预设按钮 + 手写，必选）；
  - 这道菜的状态：“还没开始做”（绿）或“厨房已在做 4 分钟，退了算损耗”（橙）；
  - **金额前后对比**：“应付 ₱564 → ₱474，少收 ₱90”，满减降档时金色一行写“满减从减 ₱60 降到减 ₱30（顾客原因）”；
  - 已派骑手时写“会通知骑手 王师傅，收款改为 ₱474”；已打包时写“已打包，退菜后要从袋里拿出来再确认”；
  - 需要授权时，按钮写“请经理授权”，点了弹出现有的授权码框，授权后自动执行。
- 退完：这一行划掉，下面一行小字“已退 1 份 · 沽清了 · 13:05 店员 小林”。底部弹出“已退菜”，自动复制给顾客的话术（和加单一样可改）：

  ```
  陈小姐，您的订单 #A1086 退了：
  盐酥鸡 ×1（沽清了，抱歉）
  订单合计改为 ₱444（原 ₱564），其他菜照常送出。
  查看订单：https://…/o/xxxx
  ```

### 8.2 堂食账单（效果图 03）

- 沿用现在 `DineBill` 的退菜面板，加上：金额前后对比（“应付 ₱567 → ₱408”）、这道菜的状态、需要授权时的授权码。
- 已退的行照现在一样灰掉，小字写原因、谁退的、什么时候。
- 结账后账单里多一个“按菜退款”（第 7 节）。

### 8.3 后厨屏（效果图 04）

- 还没做的菜被退：这一行划掉、写“已退”，1 分钟后自动消失。
- 已经在做或做好的菜被退：订单卡顶上一条红色“**退菜 1 份：盐酥鸡（沽清了）**”，卡片描红边并响一声，厨师点“知道了”才消失（记下谁点的、什么时候）。整张卡的菜都退光了也一样要点“知道了”。
- 有打印的工位：自动打一张**退菜单**，大字“退菜”，写单号/桌号、菜名、份数、原因、时间（`/ticket/:id?void=<退菜记录 id>`，订单详情里也能手动重打）。
- 和烹饪进度（PR #108）的关系：那边的页面本来就不算 `cancelled` 的菜，退菜后自然少一道；它的后厨屏颜色改动和这里的红色提醒放在不同位置，实现时谁后合并谁对齐。

### 8.4 打包

- 退菜后 `manifest_version` 加 1。还没打包的：清单上划掉这道菜。已经打包的：回到“等核对”，打包单上写“**已打包 2 袋，要拿出 盐酥鸡 ×1**”，打包员确认后重新点“打包完成”。拿旧清单点“打包完成”会被拦下（现有规则）。

### 8.5 骑手

- 已派骑手（还没取餐）：推送“#A1086 退了 1 份菜，收款改为 ₱444”。骑手 App 应收金额旁写“原 ₱564”。

### 8.6 顾客（效果图 05）

- 外卖、自取订单详情：顶部一条通知“商家退了 1 份菜：盐酥鸡（沽清了）· 少收 ₱120”；菜品里这一行划掉，写“商家已退”；金额区写新的应付，旁边小字“原 ₱564”。
- 站内消息和短信（店铺开了短信的话）发同样的内容，事件 `item_voided`。
- 堂食扫码账单页：退掉的菜划掉写“已退”，合计跟着变。堂食不另外发消息（人在桌上）。
- 顾客自己不能在页面上退菜（要退请联系商家或在聊天里说），和加单不同：退菜会让店里浪费，要店员判断。

### 8.7 退菜记录页（效果图 06）

- 导航“订单”下新加“**退菜记录**”（`/merchant/voids`），按日期看：
  - 顶部合计：退菜几次、退菜金额、其中损耗金额（已做的菜）、按菜退款金额；
  - 按原因、按员工、按菜品的小计（找出哪道菜老被退、哪个员工退得多）；
  - 明细列表：时间、单号/桌号、菜、份数、金额、原因、做到哪一步、谁退的、谁授权的、厨房确认时间。点单号打开订单。
- 权限：看这一页要 `order.void`（店长默认有）。平台后台不加。

## 9. 权限

| 操作 | 权限 | 接单员默认 | 店长默认 | 能用授权码 |
|---|---|---|---|---|
| 退还没开始做的菜 | 外卖 `order.handle`，堂食 `table.use` | ✓ | ✓ | — |
| 退已经在做 / 做好的菜 | 新增 `order.void`（“退已做的菜”） | ✗ | ✓ | ✓ |
| 收完钱以后按菜退款 | 现有 `order.aftersale` | ✓ | ✓ | ✓ |
| 看退菜记录 | `order.void` | ✗ | ✓ | — |

- 注意：现在堂食接单员能退任何菜（PR #105 只用 `table.use`）。按上面的默认值，上线后接单员退**已经在做的菜**要经理输授权码。这改变了现有行为，见第 12 节问题 2。
- 授权码框、“某某已授权”的显示、操作记录里的 `approved_by` 都沿用 STAFF_ACCESS_DESIGN 第 7 节。

## 11. 不做

- **顾客自己在页面上退菜**：要退请联系商家（第 8.6 节）。
- **换菜**：用“退菜 + 加单”两步完成。
- **赠菜 / 免单（comp）**：Square 把“已上桌但不收钱”叫赠送，和退菜分开。我们这次把它算在退菜里（原因写“菜品有问题”，记损耗）。以后要做“送一道菜”再单独加。
- **骑手取餐后到送达前改单**：菜在骑手手上，骑手到门口按单收钱；顾客当场不要某道菜，送达后走按菜退款。
- **线上原路退款**：没有线上支付，只记录。

## 12. 已确认（brian 2026-11-24：全部按括号里的推荐）

1. **满减怎么算**：退菜后满减降不降档？（顾客原因按剩下的菜重算，可以降档；店铺原因（沽清、做错、上太慢、菜品有问题）不降。也可以选“一律不降”或“一律重算”）
2. **已经在做的菜**：退了算损耗、不退库存，而且要新权限“退已做的菜”，接单员默认没有、要经理授权码？（是。这会改变现在堂食接单员随便退的做法；还没开始做的菜仍然随便退）
3. **收完钱以后**（送达、取走、结账后）：不能退菜，改成“按菜退款”记录金额和退款方式？（是，钱线下退，系统只记录，挂在售后上）
4. **外卖退菜要不要顾客同意**？（不用。店员和顾客沟通后操作，系统通知顾客，给店员一段可复制的话术）
5. **外卖最后一道菜**：不能退，要用“取消订单”？（是。堂食可以全部退掉）
6. **后厨确认**：退已经在做的菜，后厨屏要厨师点“知道了”才消失？（是。没开始做的只划掉 1 分钟）
7. **退菜记录页**：这次一起做吗？（做，在“订单”下，店长能看，按原因、员工、菜品小计）
8. **骑手取餐后、送达前**：要不要也能退？（不能，送达后按菜退款）
9. **券**：退菜后券不退、金额不变（最多抵到剩下的菜品金额）？（是。整单取消才退券，和美团等平台一致）
