# 海外餐饮外卖系统 · 技术选型 v1.0

2026-11-21 · 技术评审稿

## 选型结论

**首版采用 Vue 3 + TypeScript + Vite、FastAPI、PostgreSQL 和 Docker Compose。** 顾客手机、门店 iPad、商家后台、后厨和骑手先用网页。后端采用一个按业务模块组织的应用，另运行一个后台任务进程。订单、桌次、制作、打包、交付和收款共享同一业务核心。

这套组合适合先试点再扩门店。你已经用过 Vue、FastAPI、PostgreSQL、Docker Compose 和 Cloudflare R2，调试链路熟悉。首版优先保证点单成功只生成一次、厨房不漏单、已打包与已交接分开，以及旧桌次不会被下一桌看到。

| 层或功能 | 首选 | 选它的理由与使用范围 |
|---|---|---|
| 顾客手机与店内 iPad | Vue 3、TypeScript、Vite、Vue Router、Pinia、Vue I18n | 顾客点开门店链接或桌码即可点菜。自助 iPad 用同一顾客应用的横屏布局，店员单独绑定桌位。 |
| 商家后台 | Vue 3、TypeScript、Element Plus | 用现成表格、表单、抽屉和筛选器。顾客点菜和后厨布局仍按效果图定制。 |

## 前端布局与终端取舍

建议一个前端仓库，按顾客、商家、后厨、骑手分成独立入口，复用中文文案、金额、菜品规格和订单状态展示。店内 iPad 是顾客应用的一种入口与布局。门店模板采用「应用内已有布局 + 可配置品牌样式」；后台按入口发布模板及主题。模板配置存布局名称、颜色、图片和少量显示选项，三套模板共用菜单、报价和提交逻辑。

**顾客优先轻量 H5。** 门店链接、扫码、微信或 Messenger 内置浏览器到结账都需试测。首屏图片用缩略图和延迟加载，点餐入口避免要求安装应用。门店链接需要社交分享封面或搜索收录时，优先评估预渲染；公共门店页需要服务端渲染时再引入 Nuxt。后厨与后台不依赖其渲染能力。

**iPad 优先浏览器或主屏 Web 应用。** 门店先验收绑定桌位、结束桌次、唤醒、长时间挂屏、连续点单和换客清除旧内容。单店可在目标设备验证 Apple「引导式访问」是否适合店内使用。Apple 对 iOS／iPadOS Web Push 的支持有主屏应用和权限条件，所以新单提醒在前台 KDS 和店员屏内做，锁屏提醒不作为首版承诺。需要联网打印、强制锁定、后台定位或复杂硬件时，针对目标设备再选本地桥接、受管理终端或原生应用。  
[Apple 引导式访问](https://support.apple.com/en-gb/111795) · [WebKit 主屏 Web Push](https://webkit.org/blog/13878/)

**骑手优先 H5；原生留给明确的后台能力。** 首版由店员指派，骑手确认状态或联系门店处理异常。导航使用 Google Maps URL 等深链；走 URL 打开路线本身无需 Google API 密钥。内嵌路线、实时 ETA、轨迹后台采集有不同成本与权限，若后续确需连续定位或可靠的后台派单，再评估 Flutter 或原生壳，并在目标设备实测。  
[Google Maps URLs](https://developers.google.com/maps/documentation/urls/get-started)

## 后端和数据的一致性

按职责划分菜单与模板、门店与桌次、定价活动、订单、后厨制作、打包与交接、配送、支付、外部平台。应用可分别运行 API 和 Worker；前端的各类终端共享这套业务规则。

桌台身份、当前桌次、iPad 设备身份分别管理。门店固定桌码只用于识别桌位，不能长期用来查看旧账单。扫码顾客使用当前桌次的受限凭证，开新桌次使旧权限失效。门店员工按商户、门店、岗位授权；骑手只看到自己已获指派的任务。后厨显示制作所需的信息，打包和骑手分别只取交接所需的字段。市场规则按国家、门店时区和币种配置，示例菲律宾时区采用 Asia/Manila；活动日期按门店日历判断。

| 核心问题 | 首版技术处理 |
|---|---|
| 顾客关闭页面或网络超时后重下 | 每次提交有可复用的业务操作标识。重试返回原结果，避免把点击次数当订单数量。后台接单、加菜、送达和收款同样保护重复提交。 |
| 两个人同时改同一单 | 以数据库行锁或版本比较约束状态变化。失败方看到最新状态，人工动作不得越级覆盖订单。 |
| 历史单遇到菜单改价 | 确认落单时保存菜名、规格、数量、价格、活动、费用和币种。金额用最小货币单位或精确十进制结算，采用同一舍入口径。 |
| 厨房按品分工，打包按整单 | 制作任务关联订单、批次和制作项，可跨多个工位。同一单的制作、打包、交接、配送、付款分别维护，状态推进检查对应前置条件。 |
| 已送厨加菜或订单取消 | 加菜只发布新批次。取消或撤回写操作记录并提醒受影响工作台。已打包未交付的订单有变更时退回装袋核对。 |
| 后续扩门店 | 核心读写、文件、报表及推送均按商户和门店授权。数据库使用普通应用账号，关键表可用 RLS 做防线之一；同时验证跨商户读写与推送，RLS 不替代业务权限。 |

[PostgreSQL 行级权限](https://www.postgresql.org/docs/current/ddl-rowsecurity.html)

## 后厨实时、断线与任务重试

把 SSE 当成「有新变化，需要刷新」的通知。页面首开取得当前授权范围的完整状态；接到事件后按版本取新数据，断线重连先取快照，有足够保留期时可以按事件游标补取。客户端只推进到已确认的版本。路由要让反向代理保留长连接和心跳、关闭流缓冲，并验证同门店多屏能收到同一变化。FastAPI 官方已提供 SSE 组件，支持事件 ID 与断线恢复所需的请求信息。  
[FastAPI SSE](https://fastapi.tiangolo.com/tutorial/server-sent-events/)

- **业务确认写在前。** 接单或送厨时，订单变化、必需的制作任务与待发布事件在同一事务提交。后台进程领取已提交的任务，安排定时重试、告警和人工补偿。多进程领取可利用 PostgreSQL 队列表的 SKIP LOCKED；执行外部请求时避免长时间持有锁。重试以重复尝试、结果只生效一次为设计目标。
- **画面可恢复。** 后厨断网示警并显示最后同步时间，保留当前画面供核对；未得到服务端应答的动作仍是待确认。重连后核对状态，必要时轮询。静态资产和公开菜单可适当缓存；订单、地址和门店后台响应按授权控制，不放入公共缓存。
- **扩容按观测决定。** 多实例推送需要跨进程广播时，可加 Redis 作为刷新通知或缓存层。队列待处理、已确认订单和补取依据仍由持久化存储承载。Redis Pub/Sub 在断线时可能丢失通知；要求可重放、多消费组或任务堆积明显时再评估 Redis Streams、RabbitMQ 或其他消息系统。
- **首版以联网为准。** 若试点门店必须断网仍可开台、下单、出单，需要单独验证门店局域网服务、恢复后的订单冲突以及本地打印；这个要求会改变部署方案。

[PostgreSQL 队列读取与锁](https://www.postgresql.org/docs/current/sql-select.html) · [Redis Pub/Sub 投递语义](https://redis.io/docs/latest/develop/pubsub/)

## 部署与数据保护

| 环境 | 建议 |
|---|---|
| 开发和测试 | Docker Compose 跑 API、Worker、数据库和前端。测试环境用独立数据库、私有素材及平台测试凭证。应用发布和数据库迁移都有回退步骤。 |
| 生产试点 | 一套云端入口通过 Nginx 提供 HTTPS，Web 静态页面和 API 按入口路由；后台 Worker 独立运行，生产数据库优先托管。根据首发城市真机测试云区链路，菲律宾可把新加坡列入对比；机房选择还需核对适用的数据存储要求。 |
| 数据与文件 | 菜图可走公开 CDN，原始 Excel、导出和内部素材走受限访问。Excel 限制类型、大小和行数，防止压缩膨胀和 XML 风险；只提取业务字段。数据库做定期备份和时间点恢复，并实际演练恢复。 |
| 运维 | 关注提交成功率、待接单积压、送厨延迟、屏幕断线、任务重试年龄、支付／平台回调失败及订单对账差异。日志按订单串联，去掉顾客电话、完整地址、令牌和支付凭证。 |
| 扩展触发 | 推送广播开销大时先优化查询和连接、再增加实例或缓存。更高可用性需要应用和入口冗余，以及托管数据库故障恢复。微服务拆分等独立负载和团队边界明确再评估。 |

[openpyxl 官方安全说明](https://openpyxl.readthedocs.io/en/stable/) · [Docker Compose 生产部署](https://docs.docker.com/compose/how-tos/production/)

## 替代方案和触发条件

| 可选方案 | 何时更合适 | 目前决策 |
|---|---|---|
| NestJS 或 Go 作为后端 | 团队形成统一 TypeScript 后端规范，或有强 Go 运维积累和独立高负载服务 | 首版用熟悉的 FastAPI。优先验证订单并发、数据库和设备体验。 |
| Nuxt 顾客站 | 公共门店页需要 SEO、按店定制分享元数据或服务端渲染 | 先用 Vite H5 验证扫码与分享链接；保留单独升级顾客入口的边界。 |
| Flutter／iOS 原生 | 必须后台定位、设备管控、本地硬件或可验证的后台接单体验 | 先网页验证业务。满足这些硬性需求后独立开发对应终端。 |
| WebSocket | 需要高频双向会话、持续定位流，或已有可用的双向设备通道 | 首版动作走 HTTPS、更新走 SSE。 |
| Redis／专用消息中间件 | 活跃屏显实例多，或独立队列、回放、消费组成为明确需求 | PostgreSQL 持久化任务起步，Redis 可按监控指标加。 |
| 本地门店节点 | 云断网期间仍需继续受理与可靠送厨，或需与本地打印、收银硬件深度协作 | 作为独立验证项，不把普通 Web 缓存当离线 POS。 |
